## Scope decision: why this is a slice of each Part, not the whole Part

Both features' full Part 1 (per their specs' §8) is larger than what this session built, and the session brief for M0 chunks 0.7/0.8 explicitly named the narrower scope below. Both specs are left at `in-progress`, not `done`.

- **F-OP-07 Part 1** in full is "Settings foundation + school profile + branding": `school_profiles` RLS, the `school_public_settings` view, the settings shell UI, the profile form, logo upload, and the branding live-PDF-preview page. This session built only `resolve()` + its defaults table + the read/patch repository + the `updateSchoolSettings`/`getSchoolSettings` server action — the "cross-feature gate" every other settings consumer needs, per the session brief. The UI (W1–W2, §6) is explicitly out of scope for this slice.
- **F-ID-07 Part 1** in full is "Taxonomy, `notifications` table, `app.notify`": a migration for `notifications`/`notification_preferences`/`notification_event_catalog`, `app.notification_category`, `app.notify` with dedupe/grouping/preference checks, RLS, and pgTAP. This session built only the typed catalogue skeleton, its contracts mirror, and the CI parity test (`scripts/check-notification-catalog-parity.mjs`) — no new migration, no `app.notify`, no RLS, no pgTAP. (The `notifications` table itself, with a first cut of `app.notify`, already exists in `supabase/migrations/20260917010300_plans_and_notifications.sql` from the foundation branch; it does not yet know about this catalogue, which is the follow-up work.)

Two other spec-vs-DATA-MODEL reconciliations, both resolved in DATA-MODEL.md's favour per CLAUDE.md ("DATA-MODEL.md wins"):

- `attendance_policy`/`cover_policy` key names in this build (`min_attendance_bp`, `missed_punch_grace_minutes`, …) follow `DATA-MODEL.md` §1.3 and the already-committed `school_profiles` column comments, not the slightly different names in `F-OP-07-school-settings.md` §3.2 (`min_attendance_percent`) — a fictional example of exactly this drift is one of `resolve()`'s own unit tests.
- `fourth_subject_bonus_threshold_gp` and a Ramadan/Eid closure mode were named in the session brief but live on `academic_years` (F-AC-01, DATA-MODEL.md §2) and F-AC-11's calendar, not on `school_profiles.academic_settings`; they are out of scope for this resolver and noted in `packages/domain/src/settings/defaults.ts`'s file header.

### Notable cases proven

- `resolve()` never throws on a `null`/`undefined` row, a non-object blob, a wrong-type value, an array where an object was expected, or an out-of-range `working_days` array — always falls back to the documented default.
- `resolve()` drops keys that are not in the defaults object (the exact "renamed key never gets read" failure mode F-OP-07 §5.1 names), including a simulated legacy `min_attendance_percent` key from an earlier draft of the spec.
- `resolve()` applies each blob's override independently and merges `branding`'s nullable string fields correctly (a real bug caught by the test suite during development: a `null` default was being type-matched via `typeof`, which rejected every non-null override — fixed before this report).
- A cross-package test (`resolve.test.ts`) asserts `packages/domain`'s default-key sets exactly match `packages/contracts`' Zod patch-schema key sets for all five blobs, so the two cannot silently drift.
- `updateSchoolSettings` (repository) merges a patch onto the **stored** jsonb, not the resolved one — a test proves an unrelated previously-stored override survives a patch to a sibling key, and that only the blobs present in the patch are sent to the database.
- `updateSchoolSettings` (repository) is a no-op (no `UPDATE`, no audit row) when the patch is empty.
- The notification catalogue: every entry has a known category, priority, non-empty `action_url` and `recipients`; every security-category event has `inAppLocked`; only `billing.payment_failed` has `emailLocked`; only `platform.broadcast` has `priorityVaries`; a snapshot test locks the 54-event id list so a rename is a deliberate, reviewed diff.
- A cross-package test asserts the domain catalogue's event-id list exactly matches `packages/contracts`' `notificationEventIdSchema` enum.
- The CI parity script was verified against two induced failures (a `notify("made.up", …)` call with an undeclared event id; a deleted `en.json` string) and confirmed it fails with a clear `::error` line in both cases, then the induced failures were reverted.
- `policies.manage`: owner and admin both pass, teacher/staff/parent do not; the pre-existing owner-only `settings.manage` test (modules/danger-zone surfaces) is untouched and still passes.
