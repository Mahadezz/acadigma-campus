## 1. Scope

**What this Part is.** The reusable plans/limits engine other areas gate on: the
`plans`/`plan_limits`/`plan_modules`/`plan_prices` catalogue (already schema-complete
in `20260917010300_plans_and_notifications.sql`), a hardened `app.set_access_mode`,
two new lookup functions (`app.workspace_plan`, `app.within_limit`), a
`platform_settings` table carrying the D-39 AI top-up placeholders, and the
TypeScript engine: `packages/domain/src/plans/*` (pure `assertWithinLimit`,
`hasModule`, trial and proration math), `packages/db/src/repositories/{plans,
subscriptions,usage}.ts` (including the `requireWritable` PLAN_READ_ONLY guard),
and `packages/contracts/src/plans.ts` (Zod schemas per §7).

No UI shipped — the spec's Parts 1-3 scope is schema + server engine; `/platform/plans`
and the plan badge are UI work for a later Part.

**Acceptance criteria covered** (from spec §9):

| #    | Criterion                                                  | Covered by                                                           |
| ---- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| AC-4 | Free/limited school: 340 visible, add blocked at the limit | `packages/domain/src/plans/limits.test.ts` (assertWithinLimit)       |
| AC-5 | Edit/delete an existing row succeeds while over-limit      | `packages/domain/src/plans/limits.test.ts` (isWriteAllowedOverLimit) |
| AC-6 | A module-gated route 404s, not 403s (entitlement half)     | `hasModule` unit tests; DB: `plan_modules` fees seeding test         |
| AC-7 | Upgrade proration worked example: due exactly ৳3,000.00    | `packages/domain/src/plans/proration.test.ts`                        |
| —    | Subscriptions are not client-writable                      | `supabase/tests/07_plans_limits.sql`                                 |
| —    | access_mode set/cleared only by a privileged caller (D-29) | `supabase/tests/07_plans_limits.sql`                                 |

**Out of scope for this Part** — and where it is handled instead:

- Checkout, proration wiring into `createOrder`, invoices, dunning: Parts 4-8.
- `/platform/plans` editor UI, `/app/billing` overview, the plan badge: UI Parts, not built here.
- Wiring `checkLimit`/`requireWritable` into the six guarded write sites (students, files, AI, etc.): owned by F-AU-02/F-AC-0x/F-OP-0x/F-TE-0x, which do not exist yet in this chunk.

**Risk areas:**

- The AI-credit key rename (D-39) and the plan matrix numbers are owned by a
  parallel agent rewriting `20260917010300`'s seed on `chore/foundation`; this
  migration was kept additive and does not touch that seed (see §8).
- `app.set_access_mode` previously had no caller check at all (any authenticated
  user could flip any workspace's access_mode) — this migration closes that gap.

### Notable cases proven

- Proration worked example (§5.4): Starter→Pro, 30-day cycle, 12 elapsed → due
  exactly ৳3,000.00 (`amountDuePaisa: 300_000`), plus day-0 and last-day-of-cycle
  edge cases and the "new plan cheaper" never-negative case.
- `assertWithinLimit`: landing exactly AT the limit succeeds (`<=`, not `<`);
  a null limit and an absent limit key both default to unlimited; the structured
  `LIMIT_EXCEEDED` payload carries `limitKey/limit/current/planCode/suggestedPlanCode`.
- `isWriteAllowedOverLimit`: read/export/update/delete allowed, only `create` blocked
  — the exact §5.6 semantics, isolated from the limit-math function above.
- `requireWritable` fails closed on a query error (never treats an unreadable
  workspace as writable).
- `getSubscription` returns `not_found` for a workspace with no subscription row
  (the personal-workspace case, §5.9), not an error.
