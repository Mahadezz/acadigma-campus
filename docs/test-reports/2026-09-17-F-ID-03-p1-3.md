### Specifically proven (by inspection, not execution — flagged honestly)

- Self-role escalation denied by the pre-existing guard trigger before `can()` runs (attack path 1).
- Cross-tenant read/write returns zero rows / raises 42501 on insert (attack path 2), plus the **new** `school_profiles` freeze case: an owner of two workspaces (School A and School C) cannot move A's profile row onto C, which — traced through `school_profiles_update`'s `with check` policy — would otherwise have succeeded before this migration.
- Membership self-insert-as-owner denied, including via an `ON CONFLICT DO UPDATE` upsert attempt (attack path 3).
- A removed member sees zero rows of their former workspace and only their own row in `workspace_members` (attack path 4).
- `switch_workspace` raises `WORKSPACE_NOT_MEMBER` by name for a non-member; `list_my_workspaces` never leaks a workspace the caller never joined; `log_tenancy_context_rejected` writes exactly one audit row tagged to the attempted workspace and rejects a null id; `anon` holds `EXECUTE` on none of the three new functions.

The pgTAP suite in §4 was authored without a database. It has now run in CI (GitHub Actions `db` job, fresh Postgres + pgTAP, all migrations applied).

**Root cause of test 26.** The test counted `audit_events` while logged in as Teacher A2, who is not an owner of School B. The `audit_events` read policy (owner + platform staff, D-36) hides that row from the caller, so the count was 0 although `app.log_audit_event` had written it. The migration was correct; the test read through the wrong role. The fix asserts both halves: the caller sees **0** rows (a forger cannot read back what the tripwire recorded), and after `tests.logout()` exactly **1** row exists.

**§4 status is superseded:** every `NOT RUN` pgTAP row above is now **PASS** in run 35959261121. The §4 note "26 assertions" is out of date — the file plans 32.

**§5 status is unchanged:** `forged-workspace-header.spec.ts` ran for the first time once `db` went green and failed at sign-in (`/login`), because CI has no live Supabase project yet. It now carries the same `E2E_LIVE_SUPABASE` skip guard as the other seeded-account journeys, so it reports **skipped**, not passed. It will run for real once OQ-26 (Supabase secrets) and OQ-27 (`E2E_LIVE_SUPABASE=1`) are done. The DB-level half of AC-1 (audit row written) is proven by `09_tenancy.sql` above.
