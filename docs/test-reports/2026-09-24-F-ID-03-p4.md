## 1. Scope

**What this Part is.** A signed-in user with more than one workspace can now switch between them from a chip in every shell's top bar (phone and desktop), and lands on the shell that actually matches the workspace they switched to. The backend half of this Part — `switchWorkspace`/`listMyWorkspaces` server actions calling the `switch_workspace`/`list_my_workspaces` RPCs, and `resolveLandingRoute` implementing F-ID-03 §4.4's table — was already built in Parts 1–3 and F-ID-05 Part 1; this session's real net-new work is the **UI** (`WorkspaceSwitcher`), and the **shell layout gate** the M0 wrap-up review (PR #17) flagged as missing: `(school)/app/layout.tsx` picked its nav tree from `getNavConfig(ctx.workspaceType, ctx.role)` with no check that the resolved context actually belongs to `/app` — a `parent` role or a `personal` workspace would render a curated nav tree whose `/family/*`/`/personal/*` hrefs did not exist yet. This Part adds that gate (`resolveShellGate`, a pure domain function reusing `resolveLandingRoute`) to the school shell, and ships the minimal `(personal)`/`(family)` shells so those hrefs are real destinations instead of 404s.

**Acceptance criteria covered** (from spec §9):

| #     | Criterion                                                                                                          | Covered by                                                                                                                       |
| ----- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| AC-8  | Switching to the personal workspace at 360×800 changes the URL and shell                                           | `e2e/journeys/switch-workspace.spec.ts` (E2E_LIVE_SUPABASE-gated); unit-proven by `resolveLandingRoute.test.ts` (Part 1-3)       |
| AC-9  | A personal-only context reaching `/app/dashboard` is redirected to `/personal`, not shown an empty dashboard       | `e2e/journeys/shell-gate.spec.ts`; `shellGate.test.ts` (`resolveShellGate("school", {workspaceType:"personal",...})` → redirect) |
| AC-10 | A `parent` member of school S lands on `/family`, `/app/*` is not reachable, and `has_role(...)` is false for them | `e2e/journeys/shell-gate.spec.ts`; `shellGate.test.ts` (school/parent → allow for "family", redirect for "school")               |

**Out of scope for this Part** — and where it is handled instead:

- The real `/personal` and `/family` screens (tutoring students, child switcher, 13 guardian views) — F-ID-06 and F-AC-10 (ROADMAP M3 3.7/3.8). This Part's `(personal)`/`(family)` shells are deliberately a guard + one placeholder `EmptyState` page each, with **no bottom nav/sidebar wired** — wiring the already-curated `personal:owner`/`family:parent` nav trees here would link to the same not-yet-built routes this Part exists to stop happening.
- "Create or join a workspace" (the onboarding chooser/wizard) — F-ID-05 Parts 2–4 (PR #24, open at the time of this PR). The switcher's footer link points at `/onboarding`, which that PR adds.
- Team & Access roster, role changes, removal, ownership transfer — Parts 5–7.

**Risk areas** — what was most likely to break, and therefore where the testing effort went:

- The gate silently doing nothing (the exact PR #17 bug) — covered by a full `(shell × workspaceType × role)` matrix in `shellGate.test.ts`, not just the two paths the acceptance criteria name.
- The gate being too strict and locking an owner out of their own school — covered by an explicit "happy path is unaffected" e2e assertion in `switch-workspace.spec.ts`.
- `resolveShellGate` drifting from `resolveLandingRoute` (two tables that must never disagree) — avoided structurally: the gate calls the landing resolver rather than re-deriving the table.
- PR #24 (open, not yet merged) extends `resolveLandingRoute`'s input with two optional forced-onboarding fields. `resolveShellGate` only destructures `workspaceType`/`role` (`Pick<LandingResolutionInput, ...>`), so it cannot be affected by that addition regardless of merge order — verified by reading PR #24's diff before writing this file.

### Accessibility (axe, WCAG 2.1 AA)

Both new spec files call `expectNoA11yViolations` after the switcher sheet and each new shell's placeholder page render (`switch-workspace.spec.ts`, `shell-gate.spec.ts`). **Not exercised in this session** — same `E2E_LIVE_SUPABASE` gate as above. Manually reasoned through instead:

- `WorkspaceSwitcher`'s chip has an explicit `aria-label` naming the current workspace; the sheet/dialog gets its accessible name from `FormSheet`'s `title` prop (`SheetTitle`/`DialogTitle`, already axe-clean per `form-sheet.tsx`'s own coverage).
- Each row is a real `<button>` (keyboard-operable, `disabled` while a switch is in flight), not a `div` with a click handler.
- The single-workspace case renders a plain, non-interactive `<span>`/`<div>` rather than a disabled button — avoids a focusable control that does nothing (§6: "not tappable ... no chevron").
