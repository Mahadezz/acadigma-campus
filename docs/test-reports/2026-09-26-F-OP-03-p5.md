## 1. Scope

**What this Part is.** An owner, admin or teacher can now generate one merged A4 PDF containing every student's report card in a section for one exam, ordered by roll number or name, with duplex padding (a blank page after any student block that would otherwise leave the next student starting on an even page) so the printed stack can be cut and stapled per student for double-sided printing. Rendering is a new `report_card_bulk` run kind on the existing pipeline (D-205's synchronous, in-request pattern) — `getReportCardData` (the seam, D-206) is called once per student; a student the seam refuses (missing data today, and — once F-AC-06 Part 5 lands — a real result with no roll number, D-305) is recorded as a `failed` `report_run_items` row and excluded from the merge, never silently dropped, and the run still succeeds for everyone else.

**Acceptance criteria covered** (from spec §9, the bulk-specific ones; §10's own AC10-14 describe the full spec's split-file/publish scope, which this demo cut does not build — see "Out of scope"):

| #     | Criterion                                                                         | Covered by                                                                                                                                                                           |
| ----- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC-10 | N `report_run_items` exist reflecting the roster attempted                        | `report-card-bulk.test.ts` ("records ... never dropped"); written once after render (D-207 item 3, a deliberate narrowing of "before rendering starts" — no progress UI in this cut) |
| AC-11 | A student with no data → `failed` item, the rest render, merged PDF excludes them | `report-card-bulk.test.ts` "records a student with no roll number... as a failed item"                                                                                               |
| (new) | Duplex: every student starts on an odd page                                       | `packages/pdf/src/merge.test.ts` (unit, mixed page counts); `bulk-perf.test.ts` + pymupdf (real 40-card PDF)                                                                         |
| (new) | Ordering: roll (default) or name                                                  | `report-card-bulk.test.ts` "sorts by roll number ascending" / "sorts by name when order is 'name'"                                                                                   |
| §10   | Bulk 40 students ≤ 25 s                                                           | `packages/pdf/src/bulk-perf.test.ts` — measured 3.4 s (no duplex) / 2.9 s (duplex), see §6                                                                                           |

**Out of scope for this Part** (task's own narrowing, and spec §8 Part 5 items not built):

- **Split files** (one PDF per student) and **publish to parents** — explicitly out of scope; publish is F-AC-06 Part 7.
- **Progress UI / chunked rendering / a drainer** — still synchronous in-request (D-205's precedent), consistent with every kind this pipeline has shipped so far; `report_run_items` rows are written once, after rendering, not pre-created before rendering starts (a narrowing of AC10's literal wording, acceptable because there is no progress screen reading them mid-run in this cut).
- **Real section/exam data.** F-AC-06 Part 5 (marks/results, billing lane PR #68) is not on `main` yet. This Part renders the same D-206 fixture (one Class 6-ক section, `FIXTURE_SECTION_ID`), refused in production exactly like the single-card seam. **The demo button is hidden in production.**
- **The results-preview "Print all report cards" button.** The lead's review named the real UI home as the exam results preview (`/app/exams/[id]/results`, F-AC-06 Part 5). That page does not exist on `main` yet, so this PR ships a temporary demo button on `/app/reports` (same pattern as the single card's `GenerateReportCardButton`) and documents in D-207 item 8 that it moves once PR #68 merges and this branch merges `origin/main`.
- **The teacher's class-teacher limit** on `report.render.report_card_bulk` — interim, not enforced while the source is a fixture (same D-206 precedent), enforced by RLS on `results` when real data lands.

**Risk areas** — where the testing effort went:

- **Duplex padding must be correct for the general case, not just "always pad every card."** Verified with mixed page-count fixtures (a 2-page card followed by a 1-page card) in `merge.test.ts`, proving the algorithm re-checks parity after every card rather than hard-coding "one card = one pad."
- **A per-student failure must never silently vanish.** `report-card-bulk.test.ts` proves a seam refusal (simulating D-305's real "no roll number" message) produces a `failed` item with that exact message, that the successful student still renders and merges, and that the failed student's buffer never reaches `mergeReportCardBulkPdf`.
- **The seam's call signature must not change**, so this Part's roster-resolution code survives the swap to real data untouched except for `getReportCardBulkStudentIds`'s own body — proven by `report-card-bulk.test.ts` mocking `getReportCardData` at its real `(supabase, ctx, studentId, examId)` signature, independent of the fixture.
- **The real 40-card render, not just mocked unit tests.** `bulk-perf.test.ts` builds 40 DTOs directly (no fixture import — this test must keep working after `report-card-fixture.ts` is deleted) and runs the actual `@react-pdf/renderer` + `pdf-lib` path end to end, then a Python/pymupdf script independently re-opens the produced PDF files and checks page counts and per-page text.
- **The security-hardening migration must not regress existing report_card visibility.** `43_report_card_bulk_kind.sql` includes a regression assertion that the owner still sees every run (including the new bulk kind) after the tightened SELECT policy.

### Notable cases proven

- `createReportRun` checks `report.render.report_card_bulk` (not `report.render.report_card`), writes `report_run_items` via `createReportRunItems`, and sets `item_count` on the finished run — `actions.test.ts`.
- `GET /api/pdf/[runId]` streams the merged buffer from the same shared `renderReportCardBulkPdf` orchestration function actions.ts uses, and 403s a role without the bulk action even if it can view reports — `route.test.ts`.
- `report.render.report_card_bulk` is granted to owner/admin/teacher, denied to staff/parent/platform — `permissions.test.ts`.
