## 1. Scope

**What this Part is.** A visitor can create an account with email + password, verify it by email, sign in and out, and recover a forgotten password — the account-lifecycle floor everything else in the product stands on. Part 1's Supabase Auth wiring (`packages/db` clients, session-refresh middleware, `handle_new_user()` trigger, `profiles` + RLS) had already shipped on `chore/foundation`; this PR adds the rate-limit ledger, the account-audit RPC, and Parts 2-4's contracts, server actions and screens on top of it.

**Acceptance criteria covered** (from spec §9):

| #     | Criterion                                                                         | Covered by                                                                                                                                                                                        |
| ----- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-1  | Valid register submission → account + workspace + `/verify`                       | `e2e/journeys/register-verify.spec.ts` ("a valid submission lands on /verify...")                                                                                                                 |
| AC-2  | Duplicate email → "already has an account", no second account                     | `e2e/journeys/register-verify.spec.ts` ("AC2: registering the seeded owner email…") — blocked in this run, see §5                                                                                 |
| AC-3  | `password123` rejected, named rule, no client call to Supabase                    | `e2e/journeys/register-verify.spec.ts` (`AC3:`) + `packages/domain/src/auth/passwordPolicy.test.ts`                                                                                               |

**Out of scope for this Part:** phone OTP, magic link (Part 5); sessions/devices list, revoke (Part 6); account deletion (Part 7); axe/Lighthouse hardening pass (Part 8, though every screen built here is already axe-checked inline).

**Risk areas** — where the testing effort went: the rate-limit logic (new SQL + a client-side live countdown), the enumeration-safety of registration vs. reset (deliberately asymmetric per §4.1/§4.5 — easy to get backwards), and `safeReturnTo` (the actual security boundary for AC16, so it got the most exhaustive unit coverage of anything in this PR).

### Notable cases proven

- `checkPassword`: `"password123"` rejected as `too_common` before the byte/strength checks run (AC3's exact wording — "the specific failed rule").
- `checkPassword`: identity-similarity rejects a password containing the email local-part or full name, and does **not** false-positive on a coincidental 3-character substring.
- `safeReturnTo`: 11 attack-payload cases (protocol-relative `//`, backslash and double-backslash, single/double percent-encoding, an embedded encoded newline, absolute http/https URLs) all fall back and report `rejected: true`; the literal AC16 payload (`https://evil.example/`) is asserted by name.
- `auth_throttle`/`throttle_record_failure` (pgTAP, not run live — see §4): the 6th of 5 allowed attempts blocks, the 5th does not.
- `email_log`/`log_auth_event`/service-role hardening: confirmed **live**, by accident of the environment — `logAuthEmail`'s `withServiceRole` call threw `Missing environment variable SUPABASE_SERVICE_ROLE_KEY` during the `forgot-reset` Playwright run (no service key in this sandbox), and the request still completed with the correct user-facing generic-success message, proving the try/catch hardening added in this PR (`apps/web/lib/email-log.ts`) actually works under a real failure, not just in theory.
