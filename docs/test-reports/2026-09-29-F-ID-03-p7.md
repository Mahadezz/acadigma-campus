## 1. Scope

**What this Part is.** On Team & access, an owner or admin can now remove a member (a "Remove …" step in the member sheet that lists what happens, then "Yes, remove"). Their access ends on their next request, even if the school is read-only. A new page, **Your membership** (`/app/settings/membership`, linked from "How this school works" for every role), lets any member leave the school and lets an owner hand ownership to an active admin or teacher — pick the person, optionally stay an owner too, see what changes, enter your password and type the school's name. Decisions: D-112.

**Acceptance criteria covered:**

| Criterion (spec §8 Part 7 / §2 invariants)                    | Covered by                                                                                                                                                |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Removed member loses access on the next request (two clients) | `members-part7.integration.test.ts` "a removed teacher loses access on their very next request"; `39c_` (member_role null, roster invisible)              |
| Last owner blocked at every entry point                       | remove: guard `23514` (`03_`/`39c_`); leave: `39c_` "the sole owner cannot leave", integration "the sole owner cannot"; transfer keeps ≥1 owner by design |
| An admin cannot remove an owner                               | `39c_` "an admin cannot remove an owner"; repo pre-check `FORBIDDEN_OWNER_TARGET` (`members.part7.test.ts`)                                               |
| Transfer is one transaction                                   | `39c_` "the target is an owner and the previous owner an admin, in one step"; integration test; refused transfer "changed nothing"                        |
| Only an owner transfers; only eligible targets                | `39c_` admin / other school's owner refused; staff, removed, parent, other school's member → `TARGET_NOT_ELIGIBLE`                                        |
| No self-change of role/status outside these two flows         | `39c_` smuggled change, self re-activation, parent, direct owner self-demotion, the `app.ownership_transfer` marker alone; `03_` test 3 (now `pending`)   |
| Re-authentication before transfer                             | `settings/membership/actions.test.ts` (name before password, throttled, wrong password records a failure and never transfers)                             |

**Out of scope for this Part:** notifications (F-ID-07), resource orphaning (no resources table), "Leave and archive" / `archiveWorkspace` (Part 8), OTP re-auth, leaving from the switcher / personal area (F-ID-06). All in D-112.

**Risk areas:** the guard carve-outs (`v_leaving`, `v_transfer`) — each pinned by positive and negative pgTAP; the definer `transfer_ownership` — escalation tests for non-owner, cross-school and every ineligible target; removal bypassing `requireWritable` — deliberate (D-300), pinned by the EXEMPT list and pgTAP "leaving works on a read-only plan".
