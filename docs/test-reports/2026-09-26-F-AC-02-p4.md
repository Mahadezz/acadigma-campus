## 1. Scope

**What this Part is.** An owner or admin opens a student, taps "Invite {guardian} to the parent app", and gets a single-use link for that child (30 days) to copy or send on WhatsApp. The guardian opens it, signs in or registers, sees the school and child, and accepts. They become a parent of the school linked to that child only, and `/family` lists the child and their published results. The owner or admin can remove the access, which ends at once.

**Acceptance criteria covered** (spec §9 and the lead's brief):

| #     | Criterion                                                                                 | Covered by                                                                                  |
| ----- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| AC-5  | invite → accept → a `parent` membership + active link; `/family` shows exactly that child | `38_guardian_linking.sql` B, D; `e2e/journeys/guardian-invite.spec.ts`                      |
| AC-6  | a parent reads no other family's child                                                    | `38_guardian_linking.sql` B ("P reads L1 and no other student"), `56_publish_results.sql` D |
| Brief | accepted once; any other account refused afterwards                                       | `38` B (double tap ok, stranger `INVITATION_ACCEPTED`)                                      |
| Brief | expires; a replaced link is dead                                                          | `38` (`INVITATION_EXPIRED`, `INVITATION_REVOKED`)                                           |
| Brief | cannot link a different student; cannot cross schools                                     | `38` A (`GUARDIAN_NOT_FOUND`), C (composite FK refuses forged rows, 23503/23514)            |
| Brief | a revoked link hides the child and the published result                                   | `38` F; the journey's last step                                                             |
| Brief | two children at one school                                                                | `38` D (one membership, two links, reads exactly L1 and L3)                                 |
| Brief | invite creation rate-limited                                                              | `38` G (61st in an hour → `RATE_LIMITED`)                                                   |

**Out of scope** (D-108 "Deferred"): phone binding (needs phone OTP), SMS/email delivery, a pending-invitations list, decline, class-teacher invites, notifications, revoking links on transfer-out/soft delete.

**Risk areas:** a link reaching the wrong child or school (composite FK + tests), a parent reading another child (RLS tests), a staff account turned into a parent (`MEMBERSHIP_CONFLICT`), the token leaking (fragment only, POST bodies, `no-referrer`).

## 4. Security checks

- Only the SHA-256 of the token is stored; the raw token is returned once and never written to a table or log (`38` A).
- The token travels in the URL fragment and reaches the server only in server-action POST bodies; the page sets `referrer: no-referrer` and drops the fragment from history.
- Every function is SECURITY DEFINER with `search_path = ''`, granted to `authenticated` only (anon has no execute, `38` B).
- A link cannot name another student or another school (composite FK), and acceptance links only the invitation's own guardian and student.
- Known trade-off (D-108): whoever holds the link can accept it. Mitigated by one child per link, single use, 30 days, a new link killing the old one, the accepting account shown to the school, and revoke.

## 5. Known issues

1. Possession-bound links until phone OTP exists (D-108 item 3).
2. The journey shares one parent account across both viewports; run with one worker (two concurrent first acceptances by the same account can race on the membership insert). Locally, `next start` names its own origin `localhost` in the callback redirect while cookies live on `127.0.0.1`, so the sign-up test checks the redirect's path and continues on the page's origin; production has one origin.
3. No invitations list: a school cannot see a pending link or revoke it except by issuing a new one.
4. A teacher who is also a parent at the same school is refused (`MEMBERSHIP_CONFLICT`) — one membership per school.
5. Screenshots were taken locally (Playwright), not from a live deploy.
