## 1. Scope

**What this Part is.** A verified, workspace-less user who signs in for the first time now reaches `/onboarding` and sees exactly two choices — "Create a school" and "Join a school" — plus a quiet text link for tutoring solo, instead of the prototype's three contradictory landing paths. Choosing the tutoring link marks onboarding complete and lands on `/personal`, permanently (no forced re-entry). `onboarding_progress` exists so a mid-wizard draft (added by Parts 3-4) is resumable, and `getOnboardingState`/`saveOnboardingDraft`/`completeOnboarding` are the three server contracts everything downstream (the wizard, the join flow) builds on. **The first sentence above was false until an Opus review caught it** — see the "Opus review round" risk-area bullet below; it is true as of this report's final revision.

**Acceptance criteria covered** (from spec §9 — this Part covers a slice of AC3, AC4 and AC11; AC1-2, 5-10, 12-16 belong to Parts 1 and 3-5):

| #    | Criterion                                                                                                                                  | Covered by                                                                                                                                                                  |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| AC4  | The chooser at 360×800 uses design-system tokens only, respects light/dark, both cards in the bottom two-thirds                            | `packages/ui/src/primitives/{choice-card,onboarding-shell}.test.tsx`; manual token review (no hardcoded hex anywhere in this Part's new files)                              |
| AC11 | Choosing "I'm tutoring on my own" sets `onboarding_completed_at`, lands on `/personal`, and signing in later never forces onboarding again | `packages/db/src/repositories/onboarding.test.ts` (`markOnboardingComplete`), `packages/domain/src/onboarding/exit.test.ts`, `apps/web/e2e/onboarding.spec.ts` (live-gated) |

**Out of scope for this Part** — and where it is handled instead:

- The create-school wizard's five steps and `app.create_school_workspace()` — Parts 3-4.
- The join-with-code screens and the first-run checklist — Part 5.
- The nightly `onboarding_progress` draft-cleanup cron — spec §7, not in this Part's §8 build list.
- The account menu named in §6's chooser wireframe row — no such primitive exists anywhere in this codebase yet (see spec §11's Part 2 status note).

**Risk areas** — where the testing effort went:

- RLS on a brand-new user-scoped table with a support-read carve-out (platform staff SELECT) and an intentionally absent DELETE grant — the highest-consequence part of this Part, since a mistake here either leaks another user's in-progress form data or silently allows deleting the resumability guarantee §4.7 promises.
- The `now()`-is-constant-per-transaction trap in pgTAP: an earlier draft of `17_onboarding_progress.sql` asserted `updated_at > started_at` after an UPDATE, which is **always false** inside a single `begin;`/`rollback;` transaction (Postgres's `now()` is the transaction timestamp, not the statement timestamp) — caught before push, replaced with a `pg_trigger` catalog check.
- The `draft` column's nullability: the spec's own prose ("nulling draft") contradicts every other jsonb column in this feature area (`not null default '{}'`) — resolved in favour of the spec's literal words, documented explicitly so it doesn't read as an oversight.
- A route-group path bug: `apps/web/app/(onboarding)/page.tsx` resolves to `/`, not `/onboarding` (Next.js route groups add no path segment) — collided with the marketing `/` page at build time and was caught by `next build`, not by `tsc` or `vitest`. Fixed by moving the screen to `apps/web/app/(onboarding)/onboarding/page.tsx`.
- `/onboarding` was missing from `middleware.ts`'s `PROTECTED_PREFIXES`, so a signed-out visit fell through to the page's own redirect (a bare `/login`, no `?next=`) instead of middleware's `?next=` redirect — caught by CI's `e2e` job (this Part's own `onboarding.spec.ts` signed-out-redirect case), not locally, since this repo's Playwright suite only runs in CI (no Docker on this laptop). Fixed in a follow-up commit on this PR; `docs/plan/HANDOFF-2026-09-24.md`'s "verify rebases" caution does not apply here (no force-push, no rebase — an ordinary additional commit).

**Opus review round (both blockers, plus 5 smaller issues — full detail in spec §11's Part 2 status note):**

- **BLOCKER — the forced-onboarding redirect (§8's own build-list line) was never actually wired.** `handle_new_user()` gives every account an active personal-workspace membership at registration, so `resolveLandingRoute` (F-ID-03 §4.4) resolved `workspaceType: 'personal'` for a brand-new user and sent them straight to `/personal` — only the verify-email callback's hardcoded `next=/onboarding` ever reached the chooser at all. Fixed by extending `resolveLandingRoute`'s pure input (`packages/domain/src/workspace/resolveLanding.ts`) with `onboardingCompletedAt`/`hasActiveSchoolMembership`, both required together so `switchWorkspace` (which omits them) is never affected. 10 new unit tests (5 domain-level matrix cases, 5 wiring-level cases in `apps/web/lib/resolve-landing-route.test.ts`, including a fail-closed case for an errored membership probe).
- **BLOCKER — the chooser counted the auto-created personal workspace as "already has a membership."** Showed "Back to {personal}" and hid the tutoring exit link for every user, including brand-new ones (violating AC3 and §4.6). Fixed by filtering to `type === 'school'` in `onboarding/page.tsx` and renaming `chooser.ts`'s field to `hasActiveSchoolMembership`. 2 new unit tests.
- 44px touch targets added to `tutoring-exit-link.tsx`, `start-over-link.tsx` and `onboarding-shell.tsx`'s back link (`min-h-11`).
- `TutoringExitLink`'s silent failure (`if (!result.ok) return`) now shows an `InlineAlert` with a retry affordance.
- `onboarding_progress.draft` gained a database-level 32000-byte `CHECK` constraint (`17_onboarding_progress.sql` test 7, `23514`) — the Zod cap alone is not a boundary against a direct authenticated write.
- The two `ChoiceCard`s that link to not-yet-built routes now render `disabled` with a "Coming soon" badge (a non-interactive `aria-disabled` card) instead of a link that 404s.
- `D-60` recorded: `onboarding_progress`'s repository is keyed on `userId`, not `WorkspaceContext` — the documented exception to rule 6 for the one table class (user-scoped, DATA-MODEL.md §0.3) where a `WorkspaceContext` cannot exist by construction.

**`coverage.sql`:** not applicable to this table — it checks only tables carrying a `workspace_id` column, and `onboarding_progress` deliberately has none (user-scoped, per §1's design). `scripts/check-coverage-test-files.mjs` confirms this: it still reports "16 workspace_id tables; 16 named" — unchanged by this PR, because `onboarding_progress` was never expected to be in that count.

### Specifically proven

- A second user querying by the first user's `user_id` sees zero rows, and cannot insert or update on their behalf (RLS `USING`/`WITH CHECK` both key on `user_id = app.current_user_id()`).
- No role — not even the row's own owner — can `DELETE`: the table has no DELETE grant to `authenticated` at all, so the failure is a grant-level `42501` raised before RLS is ever evaluated (not a policy that could later be loosened).
- Platform staff (`profiles.is_platform_admin = true`) can read another user's row — the one SELECT branch beyond "your own row," for support.
- `app.attach_updated_at`'s trigger is actually attached to the table (checked against `pg_trigger`/`pg_proc`, not by comparing `now()` values — see §1's note on why the latter cannot work inside pgTAP's single transaction).
- A 40000-byte draft is rejected with `23514` by the new database-level CHECK constraint (Opus review addition), proven as the row's own authenticated owner, not just as a privileged role.
