## 1. Scope

**What this PR is.** `e2e-live` starts a real local Supabase stack in CI, seeds it and runs every Playwright journey un-skipped (`E2E_LIVE_SUPABASE=1`) — the 106 of ~126 tests that otherwise never execute anywhere, because they carry the live-Supabase skip guard. Every run of this job since it was introduced failed inside the first minute of every shard, always at sign-in. This PR diagnoses and fixes that, so `e2e-live` can eventually become a required check.

**Not a feature Part** — no new user-facing behaviour, no migration that changes application data, no new acceptance criteria. The template below is adapted accordingly; sections that don't apply to CI-infrastructure work say so.

**Root cause, found by iterating on real CI runs** (see Decision Log D-76 for the full account): seeded `auth.users` rows left four columns GoTrue scans as non-nullable Go strings (`confirmation_token`, `email_change`, `email_change_token_new`, `recovery_token`) at their `NULL` default. A row's very first login does not touch these columns and succeeds; every later request that does 500s with GoTrue's generic `"Database error querying schema"`. That is why the symptom looked like "the whole suite is broken" rather than "four columns are wrong": every shard's owner sign-in worked exactly once, then failed forever after, for the rest of that shard's run.

**Risk areas** — where the diagnosis effort went, in order:

1. Whether the (inherited, mid-flight) sign-in throttle change itself was the cause — reviewed, tested, found correct, committed separately.
2. Why the failure showed no server-side evidence at all — found the webServer's `stdout` was unconditionally discarded in CI.
3. With evidence restored, the actual GoTrue error code/message — found the NULL-column root cause.
4. Whether the branch itself was stale relative to `main` — it was, 3 commits behind, merged in.
5. Whether the job's timeout was realistic now that tests actually run — it wasn't; raised.

## 5. End to end (Playwright) — `e2e-live`

**Before this PR (baseline, run 36457859794):** all 4 shards failed. Every owner sign-in past the very first one in a shard's lifetime returned a bare HTTP 500 from GoTrue, with zero server-side evidence visible in the CI log (stdout discarded).

**After the stdout fix (36510216612):** same failures, but now visible: `status: 500`, no `code` — an untyped GoTrue error.

**After adding `error.message` to the log (36512053201):** `"Database error querying schema"` — the root cause (auth#1940-class NULL token columns).

**After the seed fix (36515888007):** zero schema errors, zero 500s. Every `"sign-in rejected"` log line for the rest of the suite is a legitimate `"Invalid login credentials"` — the deliberate wrong-password tests (`rate-limit.spec.ts`, `signin-signout.spec.ts`) working as designed. This is the load-bearing result: **the CI infrastructure bug this PR exists to fix is confirmed closed.**

**After merging `main` (which the branch was 3 commits behind) and raising the shard timeout 20→30 min (36521111530 and the final run below):** the suite now genuinely executes real journeys end to end, which surfaced two classes of pre-existing issues the suite had never had the chance to find before (see §8).
