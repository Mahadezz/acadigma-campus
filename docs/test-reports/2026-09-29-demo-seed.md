## 6. Security checks

- Workflow: `workflow_dispatch` only, job gated to `refs/heads/main`, `production` environment, no inputs, `contents: read`, concurrency group without cancel.
- The demo password is a GitHub secret passed only to the Auth API over HTTPS; the SQL never sees it. The service key is masked (`::add-mask::`) before use and never echoed; on an Auth API error only the status, error code and message are printed.
- Security review of #107 (MEDIUM, fixed): an existing demo email is taken back — password reset to the secret, `app_metadata.acadigma_demo` set, all sessions revoked when it was not already the seed's — and the SQL refuses unmarked accounts or ones belonging to any other workspace. LOW: D-80 now says the accounts are effectively public; rotate the secret after demo days and re-run. INFO: exam status moves by RLS updates as `setExamStatus` does (D-80 wording fixed); `SUPABASE_DB_PASSWORD` stays, as `supabase link` / `db query --linked` connect to the database.
- Every tenant write is made with `role = authenticated` and the acting member's claims, so RLS and the functions' role checks decide — the seed has no more power over the demo school than its owner and teacher in the app.
- Guards: name ambiguity and ownership checked before any write; the history step re-checks that the workspace id it received is the demo school owned by the demo owner.

## 7. Known issues

1. **The production path is untested in CI.** `supabase db query --linked` goes through the Management API, which CI cannot reach; the local stack exercised `--local`. The SQL is one statement either way. Risk: the Management API's session role or statement handling differs (e.g. `set_config('role', …)`). Mitigation: it is one transaction, so a failure writes nothing — the lead reads the job log and reports.
2. **The service-key lookup is untested** (`supabase projects api-keys --reveal -o json`, then `service_role` or the first `secret` key). If it fails the job says so; the owner then adds `SUPABASE_SERVICE_ROLE_KEY`.
3. **Trial expiry:** the demo school goes read-only 30 days after the first run (D-62); no reviewed platform path extends a trial, so none is used. The job summary's "Trial ends on" line comes from a second `db query --linked`, untested in CI.
4. **No top-up:** attendance history ends the day before the first run; later runs add nothing by design.
5. **Past registers carry `edited_after_window`** (entered by the owner outside the 2-day window, D-104).
6. **The walkthrough was not rehearsed on production** — it cannot be until the lead runs the workflow. Screen names follow the current `en.json`/`bn.json`; the class hub (PR #82) is not merged.
