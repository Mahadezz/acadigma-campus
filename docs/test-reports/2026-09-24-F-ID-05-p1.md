## 1. Scope

**What this Part is.** Every new account gets exactly one personal workspace and one `owner`/`active` membership, created in the same database transaction as the `auth.users` row, with no path anywhere — application code or direct database access — that lets an authenticated client mint a second one. Most of the bootstrap already shipped in M0 (`20260917010100_identity.sql`) before this spec was written down; this Part's delta closes the gap between that shipped behaviour and PRODUCT-DECISIONS §1.2's promise ("enforced by a partial unique index").

**Security fix mid-PR (Opus review):** the first draft of this PR added only the unique index. Review found that alone insufficient — an authenticated client could `PATCH` their personal workspace's `created_by` to `null`, then `POST` a fresh `type='personal'` row (the insert policy checked `owner_id = created_by = auth.uid()` but never `type`), repeating indefinitely for unlimited free-tier workspaces, each with a real owner membership. Fixed in the same migration: `created_by` joins `type`/`owner_id`/`invite_code` as immutable in `app.tg_workspaces_guard()`, and the `workspaces_insert` policy's `WITH CHECK` now requires `type = 'school'` — personal workspaces are created exclusively by `app.handle_new_user()` (`SECURITY DEFINER`, unaffected by client-facing RLS). See spec §11 deviations for the full exploit chain.

**Acceptance criteria covered** (from spec §9):

| #    | Criterion                                                                                                                                                                          | Covered by                                                                                                                                                                                |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-1 | A brand-new registration produces exactly one `workspaces{type='personal'}` and one `workspace_members{role='owner',status='active'}` row, in the same transaction as the account. | `supabase/tests/15_personal_workspace_registration.sql` tests 1-6                                                                                                                         |
| AC-2 | A forced failure rolls back the whole signup — no `auth.users` row survives, never a half-account.                                                                                 | `15_personal_workspace_registration.sql` tests 7-11 (failure injected in `app.tg_workspace_bootstrap()`, last in the chain, so a real partial-write scenario is what is proven to unwind) |

**Out of scope for this Part** — and where it is handled instead:

- The onboarding chooser UI, `/onboarding` route, `onboarding_progress` table — Part 2.
- The create-school wizard, `app.create_school_workspace`, grade levels, academic years, join codes, trial subscriptions — Parts 3-4.
- The join-with-code path, `resolveLandingRoute` wiring into onboarding exits, first-run checklist — Part 5.
- A curated `workspace.created` audit action distinct from the generic `workspaces.insert` row the existing `app.attach_audit()` trigger already writes — recorded as D-58, not a gap.

**Risk areas** — what was most likely to break, and therefore where the testing effort went:

- Whether the M0 bootstrap trigger chain (`app.handle_new_user()` → `app.tg_workspace_bootstrap()`) actually gives transactional atomicity, or only appears to by never having been tested against a forced failure. Verified directly with a transaction-local, savepoint-scoped substitution of `app.tg_workspace_bootstrap()` — the LAST function in the chain — that unconditionally raises, proving a genuine partial-write scenario (profile + preferences + workspace already inserted) unwinds, not just a failure on the first statement.
- Whether a second personal workspace for the same creator, or any personal workspace at all, was actually rejected for an authenticated client before this PR. Neither was — confirmed by grepping every migration for a `created_by`-immutability check or a `type` condition on `workspaces_insert` and finding none; both are closed in `20260925000100_personal_workspace_uniqueness.sql`, alongside the unique index.

**`coverage.sql`:** exists on `main` since PR #17/#18 (D-56) and runs in CI's `db` job; this PR does not add a new `workspace_id`-bearing table, so it does not change `coverage.sql`'s pass/fail — the earlier draft of this report incorrectly described it as an incomplete, warning-only gate, which was true before PR #17 merged but is not true after the merge this PR now includes.

### Specifically proven

- A signup produces exactly one `workspaces{type='personal'}` row and one `workspace_members{role='owner',status='active'}` row, and the new owner's `app.has_role()` is true immediately, as themselves (not as a privileged caller).
- A raised exception in the LAST function of the bootstrap chain rolls back the entire `auth.users` insert — a genuine partial-write scenario (profile, preferences and the workspace row already present) — confirmed by direct assertion (row counts of zero across four tables), not inferred from reading the trigger or from failing on the first statement.
- The bootstrap chain is unaffected by having been temporarily replaced inside a `SAVEPOINT` for the atomicity test — proven by a second, independent registration succeeding immediately after the `ROLLBACK TO SAVEPOINT`.
- `workspaces_one_personal_per_creator` actually enforces "exactly one, ever" at the database layer for a privileged caller, by name (the exact constraint name appears in the expected error message).
- `created_by` is immutable through plain client DML, closing the first half of the two-step exploit an Opus review found.
- An authenticated client cannot insert ANY personal workspace directly — not just a second one — closing the second half of that exploit, while a school-type insert (the one legitimate client path) is unaffected.
