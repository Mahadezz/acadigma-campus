## 1. Scope

**What this Part is.** Before this Part, there was no row anywhere that said "this person works at this school, in this role, from this date, at this rate." This Part ships that row and the security boundary around it: `staff_records`, a period-versioned `staff_compensation` table with an exclusion constraint so no two rates can ever overlap, `staff_documents`, the `staff_directory` safe-subset view, the `app.staff_hourly_rate` point-in-time function, `app.can_open_staff_document`, the trigger that keeps a staff record's status in step with the person's actual membership status, and default `custom_labels` seeding for new schools. It is schema, RLS, contracts, domain-adjacent row shapes and a read-only repository — no server actions, no UI. Nobody can yet open `/app/staff`; that is Part 2.

**Acceptance criteria covered** (from spec §9 — the subset a schema/RLS-only Part can prove; the rest need Parts 2-5's UI/server actions):

**Out of scope for this Part** — and where it is handled instead:

- Directory/person-sheet UI, search, filters, quick actions (AC-1, AC-2, AC-5, AC-6, AC-31) — Part 2.
- Record editor, section-scoped saves, `forbidden_section` server error (AC-3, AC-4) — the RLS/trigger half of AC-3 (self cannot patch `employment_type`) is proven here; the server-action error code is Part 3.
- Documents UI, expiry chips, nightly notification (AC-13, AC-15) — Part 3.
- Compensation UI, the payslip view, custom labels CRUD (AC-12a-e) — Part 4.
- Offboarding, the revoke transaction, rejoining (AC-17, AC-19-28) — Part 5, and depends on F-OP-01 (hiring) which has not shipped.
- Seat-limit enforcement (AC-20) — depends on `inviteMember`/hire server actions, not built yet.

**Risk areas** — where the testing effort went:

- The compensation exclusion constraint's interaction with the period-closing trigger (forward-dated vs. genuinely-overlapping inserts needed two different fixture shapes to exercise both code paths).
- The self-update column guard vs. the membership-link trigger's own nested UPDATE — a real risk that the invitee's own first-time invitation acceptance would trip the very guard meant to protect their record (see Known issue resolution in DECISION-LOG D-63 and the `pg_trigger_depth()` exception); proven with a `SECURITY DEFINER` test helper run as the invitee, not as `postgres`.
- `app.staff_hourly_rate` never leaking a rate across the tenant boundary, and never erroring in a way that would confirm a row's existence to an unauthorized caller (always `null`, both when the row does not exist and when the caller may not see it).

### Specifically proven (in `20_staff_schema.sql`, pending CI execution)

- A School A admin reads zero School B rows across all three tables, by direct select.
- A teacher reads exactly their own `staff_records`/`staff_compensation` row and cannot reach a colleague's compensation row through a join, not just an unqualified select.
- `app.staff_hourly_rate` never returns a colleague's rate to a teacher, returns `null` (not zero) when no compensation row exists, and returns `null` for a caller from a different workspace than the row it would read.
- The compensation exclusion constraint refuses a genuinely overlapping insert (`23P01`) after the forward-dated closing trigger has already run.
- A teacher can update their own contact/emergency fields but is refused (`42501`) patching `employment_type`, `employment_status` or `staff_code` on their own record.
- The invitee's own first-time invitation acceptance (simulated via a `SECURITY DEFINER` helper, logged in as the invitee — not as `postgres`) does **not** trip the self-update guard on their own record, proving the `pg_trigger_depth()` exception added for exactly this case.
- `app.can_open_staff_document` returns true for an admin or the document's own owner and false for a colleague.
- A new school workspace is seeded with the ten default `custom_labels` rows.
- `anon` has no privileges on any of the three tables and cannot execute either new `app.*` function.

**Threat-model checks specific to this Part** (manual review, not yet an automated test):

- Deny-by-default (D-54): `app.staff_hourly_rate` and `app.can_open_staff_document` both have an explicit `revoke all ... from public, anon` followed by an explicit `grant execute ... to authenticated, service_role` — verified by `20_staff_schema.sql` §8's `has_function_privilege` assertions.
- RLS checks membership AND role, never `workspace_id` alone (non-negotiable rule 3): every policy on all three tables goes through `app.has_role(workspace_id, ...)` or a `staff_records.user_id = app.current_user_id()` self-check — never a bare `workspace_id = current_setting(...)` comparison.
- The audit trigger (`app.attach_audit`) is attached to all three tables, with `emergency_contact`/`address`/`notes` on `staff_records`' freetext list (nulled in the audit trail, name kept) since they carry PII the generic secret/sensitive/contact column-name patterns cannot reach.
