## 1. Scope

**What this Part is.** Every new account gets exactly one personal workspace and one `owner`/`active` membership, created in the same database transaction as the `auth.users` row, with no code path anywhere that lets a user trigger a second one. Most of this already shipped in M0 (`20260917010100_identity.sql`) before this spec was written down; this Part's actual delta is a database-level partial unique index closing the one gap between the shipped behaviour and PRODUCT-DECISIONS §1.2's promise ("enforced by a partial unique index"), plus the pgTAP coverage proving all of it, including atomicity under a forced failure — which had no test before this PR.

**Acceptance criteria covered** (from spec §9):

| #    | Criterion                                                                                                                                                                          | Covered by                                                                                                            |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| AC-1 | A brand-new registration produces exactly one `workspaces{type='personal'}` and one `workspace_members{role='owner',status='active'}` row, in the same transaction as the account. | `supabase/tests/13_personal_workspace_registration.sql` tests 1-5, 6                                                  |
| AC-2 | A forced failure inside `handle_new_user()` rolls back the whole signup — no `auth.users` row survives, never a half-account.                                                      | `13_personal_workspace_registration.sql` tests 7-9, plus test 10 proving the function still works normally afterwards |

**Out of scope for this Part** — and where it is handled instead:

- The onboarding chooser UI, `/onboarding` route, `onboarding_progress` table — Part 2.
- The create-school wizard, `app.create_school_workspace`, grade levels, academic years, join codes, trial subscriptions — Parts 3-4.
- The join-with-code path, `resolveLandingRoute` wiring into onboarding exits, first-run checklist — Part 5.
- A curated `workspace.created` audit action distinct from the generic `workspaces.insert` row the existing `app.attach_audit()` trigger already writes — deferred; see spec §11 deviations and Known issue #1 below.

**Risk areas** — what was most likely to break, and therefore where the testing effort went:

- Whether the M0 bootstrap trigger chain (`app.handle_new_user()` → `app.tg_workspace_bootstrap()`) actually gives transactional atomicity, or only appears to by never having been tested against a forced failure. Verified directly with a transaction-local, savepoint-scoped substitution of `app.handle_new_user()` that unconditionally raises — proves AC2 rather than assuming it from reading the trigger definitions.
- Whether a second personal workspace for the same creator was actually rejected anywhere before this PR. It was not — confirmed by grepping every migration for a unique constraint touching `workspaces.type = 'personal'` and finding none; `workspaces_one_personal_per_creator` (`20260925000100_personal_workspace_uniqueness.sql`) closes this.

**`coverage.sql`:** not run locally (no Docker); CI's `db` job currently only warns that repo-wide RLS/grant coverage tooling is not complete (pre-existing, tracked in the M0 wrap-up Part per `docs/plan/HANDOFF-2026-09-24.md`) — unaffected by this PR.

### Specifically proven

- A signup produces exactly one `workspaces{type='personal'}` row and one `workspace_members{role='owner',status='active'}` row, and the new owner's `app.has_role()` is true immediately, as themselves (not as a privileged caller).
- A raised exception anywhere in the bootstrap chain rolls back the entire `auth.users` insert — confirmed by direct assertion (row counts of zero across three tables), not inferred from reading the trigger.
- The bootstrap chain is unaffected by having been temporarily replaced inside a `SAVEPOINT` for the atomicity test — proven by a second, independent registration succeeding immediately after the `ROLLBACK TO SAVEPOINT`.
- `workspaces_one_personal_per_creator` actually enforces "exactly one, ever" at the database layer, not just at the one call site that happens to run once per signup.
