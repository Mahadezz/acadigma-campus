## 1. Scope

An owner or admin admits a student in one sheet (English and Bangla names, gender, date of birth, section, optional roll number, one guardian's name, relation and mobile), finds students by name or student ID with a class filter, and opens a profile. Date of birth and guardians are shown only to owner/admin and the student's class teacher; everyone else sees a locked note. See D-103 for the split and what is deferred.

| #    | Criterion                                                                         | Covered by                                                                                                                                                     |
| ---- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC1  | Quick admit writes code, primary guardian and active enrolment in one transaction | `33_` (codes, roll numbers, one correlation id, refused admissions write nothing); `quick-admit-student.spec.ts`                                               |
| AC2  | Concurrent admits never collide                                                   | `app.next_id` advisory lock + section row lock + unique indexes; `33_` `ROLL_TAKEN`. The 100-session concurrency test is **not run** (pgTAP is single-session) |
| AC6  | Another family / another school gets nothing, by RLS                              | `33_` isolation: another school's owner reads 0 rows of all four tables and of the roster view; a parent member reads 0                                        |
| AC7  | A subject teacher sees a locked block                                             | `33_` (subject teacher and staff read 0 private rows and 0 guardians); `student-profile.test.tsx` locked case                                                  |
| AC14 | Soft-deleted students hidden, visible to the owner                                | `33_` soft-delete cases                                                                                                                                        |
| AC15 | The roster payload is one page, never the table                                   | `students.test.ts` (range 0..50, one extra row for "more"); `student_roster` has no private column                                                             |

## 4. Database (pgTAP)

`33_students_and_guardians.sql` **62/62** locally (after the PR #54 review fixes); every other file passes (`12_function_grants_invariant.sql` 10/10 with `admit_student` allow-listed). `51_readonly_join_and_seed.sql` uses psql meta-commands and does not run in the local harness (pre-existing; it runs in CI).

- admission: sequential codes, roll 1, 2 …, a replayed key returns the first student, a reused key with a new body is refused, `ROLL_TAKEN`, the same roll is fine in another section, `SECTION_ARCHIVED`, `YEAR_CLOSED`, `SECTION_NOT_FOUND`; a future DOB, a non-E.164 phone, an unknown gender and a missing last name are `VALIDATION`; no direct INSERT, even for an owner; an enrolment date before the year or in the future is `VALIDATION`, a given one is kept;
- rules: one active enrolment per year, the enrolment's year must be its section's, no cross-school student in an enrolment or guardian (composite FKs), `workspace_id` frozen, one primary guardian;
- visibility: the class teacher reads the roster, and DOB and guardians of their own section only; a subject teacher and staff read the roster and the roster view (class, section, roll) but no DOB or guardian; a parent member reads nothing; another school's owner reads nothing and cannot admit here;
- escalation: a teacher cannot admit, add a guardian or update students/enrolments; a teacher removed as class teacher loses guardian access at once; the class teacher of a past year's section reads no DOB or guardian;
- soft delete hides a student from teachers, not from the owner; read-only mode refuses admission and guardian edits; `created_by` immutable; anon has no privilege on the tables, the view or the function; audit rows written, guardian phone masked `+8801*****678`, date of birth null in the audit row but named in `changed_fields`, one correlation id per admission.

## 6. Performance

`/app/students` first-load JS 226 kB gzipped, `/app/students/[id]` 232 kB (budget 250 kB). The profile first measured 263 kB: a server component importing `Button`/`Badge` shipped the whole `radix-ui` barrel; making `student-profile.tsx` a client module fixed it. Search latency at 3,000–5,000 students (spec budget p95 < 200 ms) **not measured**; trigram indexes exist on both name columns.

## 7. Known issues

1. No admissions/`ADM-` numbers, duplicate or capacity warnings, guardian invites, edit or soft-delete actions yet (D-103 point 4).
2. Offset paging (`?page=`), not a cursor; fine at class sizes, revisit for large schools.
3. `{YYYY}` in the code is the calendar year (`app.next_id`), equal to the academic year only for a January–December year.
4. No 100-session concurrency test (AC2); correctness rests on the advisory lock, the section row lock and the unique indexes.
5. Screenshots come from a local preview, not the live demo login.
