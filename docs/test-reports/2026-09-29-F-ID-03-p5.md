## 1. Scope

**What this Part is.** An owner or admin opens `/app/staff/team` and sees the school's staff by status — Active, Waiting (join requests), Removed — searches it by name or email on the server, pages through it 25 at a time, and approves or turns down a waiting request with one tap. An approved person resolves the school on their very next request; a turned-down one never does. Decisions: D-110.

**Acceptance criteria covered** (spec §9):

| #     | Criterion                                                                | Covered by                                                                                                                                                         |
| ----- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC-3  | A teacher cannot change their own role/status                            | `39a_team_roster.sql` "a joiner cannot approve themselves" (the guard, not new code)                                                                               |
| AC-4  | An admin touching an owner gets refused                                  | `39a_team_roster.sql` "an admin cannot remove the owner through the same update"                                                                                   |
| AC-7  | A removed member re-approved reactivates the same row                    | **not covered** — approve accepts only `pending` in this Part (D-110 §3); re-approval of a removed member is left to Part 7                                        |
| AC-16 | 400-member roster: server-side search, first page ≤ 50, no full download | `list_workspace_members` search + keyset paging (`39a_` A), 25 per page (`members.test.ts`), `team-roster.spec.ts` (search sets `?q=`); no 400-row fixture was run |
| Demo  | Approve a pending teacher; they gain access on the next request          | `members.integration.test.ts` "approving lets the joiner in on their next request" (two real PostgREST clients)                                                    |

**Out of scope for this Part** — and where it is handled instead:

- Teacher/staff directory cards (§2) — F-OP-06 Part 2's `/app/staff` (D-110 §2).
- Role change, staff fields, labels, member detail sheet — Part 6.
- Removal, leaving, ownership transfer — Part 7.
- `join_request.*` notifications — F-ID-07 (no fan-out exists yet).
- `SEAT_LIMIT_REACHED` — every school plan has `max_teachers` null.
- Invite button — F-ID-04.

**Risk areas:** the definer function (it reads profiles RLS hides, so its own owner/admin check is the boundary) — hence pgTAP escalation for every other role and a stranger, plus the security review; the idempotent decide logic (double taps, a colleague deciding first).

## 8. Known issues

1. Approve/turn-down have no Playwright run and no screenshots (see §5) — the approve path is proven only by the `db-integration` test.
2. AC-7 (re-approving a removed member) is not built.
3. No notification tells the joiner they were approved or turned down.
4. A read-only school cannot turn down requests from the screen although the database would allow it (D-110 §6).
5. The repository's already-decided fallback reads the row under SELECT RLS; a caller who could read but not write a row would get "success" for a row already in the target state (typescript review, HIGH). The server action admits only owner/admin, who can both read and write every row, so it is not reachable from the app; no data changes either way.
6. The DB review suggested making a cursor also match the tab's status; not done — a keyset position stays valid if the anchor row changes status, and erroring there would break paging whenever a colleague approves someone mid-browse.
