## 1. Scope

**What this Part is.** A daily cron job (`GET`/`POST /api/cron/billing/tick`, `CRON_SECRET`-protected) that finds every school subscription whose Pro trial has passed `trial_ends_at` and puts that workspace into `access_mode = 'read_only'` — reads, exports, edits and deletes keep working; only creating new rows is blocked, and the school shell now shows a banner explaining why. D-62 records why this is "read-only", not "the plan becomes Free" as the spec text originally said: the `free` school plan was retired by D-42 before this Part was built, so there is nothing left to downgrade a lapsed trial onto.

**Acceptance criteria covered** (from spec §9, as narrowed by D-62 — see §11's "Part 4 status" note):

| #    | Criterion                                                                                       | Covered by                                                                |
| ---- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| AC-1 | A new school gets a trialing subscription with no card (pre-existing, Part 2) — unchanged here. | `16_billing_bootstrap_guard.sql` (pre-existing)                           |
| AC-2 | (T-3 nudge) — **not built this Part**, no email adapter exists yet.                             | Deferred — see §11 status note                                            |
| AC-3 | A trial that expires moves the workspace to read-only; zero rows are deleted anywhere.          | `supabase/tests/19_trial_expiry_billing_tick.sql` tests 4-9               |
| AC-4 | A read-only school's existing rows stay visible/exportable; creating a new one is blocked.      | Pre-existing `requireWritable`/`checkLimit` (Part 3); not re-tested here  |
| —    | The job is idempotent — a second run the same day changes nothing further.                      | `19_trial_expiry_billing_tick.sql` tests 15-16                            |
| —    | A paying (`active`/`past_due`) subscription is never touched, even with a past `trial_ends_at`. | `19_trial_expiry_billing_tick.sql` tests 12-14                            |
| —    | Only a privileged (service-role) caller may run the job.                                        | `19_trial_expiry_billing_tick.sql` tests 1-3 (grant-level, not throws_ok) |
| —    | `CRON_SECRET` missing/wrong/absent-header → 401, before any service-role work happens.          | `apps/web/app/api/cron/billing/tick/route.test.ts` (4 tests)              |

**Out of scope for this Part** — and where it is handled instead:

- T-3 trial-ending-soon email + banner: needs an email adapter, not built anywhere yet. Deferred to whichever Part adds one.
- Scheduled-downgrade application: needs `changePlan`/Part 5's downgrade-scheduling flow, unbuilt.
- The one-email-per-day dunning guard, renewal reminders, `past_due`/grace/`lapsed`: Part 7, unbuilt.
- `runSubscriptionJobs`'s fuller `{remindersSent, pastDue, lapsed, downgradesApplied}` response: added when the above land. Today's response is `{trialsExpired}` only.

**Risk areas** — what was most likely to break, and therefore where the testing effort went:

- Never touching a paying school (tested directly: an `active` subscription with a past `trial_ends_at` is left untouched).
- Idempotency on a re-run (tested directly: second run returns 0, no duplicate event).
- The function surface: `app.*` is unreachable from a Supabase client at all (only `public` is PostgREST-exposed), so the new `public.expire_pro_trials()` wrapper's grants were checked directly against `has_function_privilege` rather than assumed.
- The audit trail: confirmed the read-only transition is recorded via the existing, catalogued `workspace.access_mode_read_only` action (no new application-code audit write).

### Notable cases proven

- `runTrialExpiryJob` maps the RPC's numeric return to `{trialsExpired: n}`, including the `0` case (not treated as an error) and a malformed/non-numeric RPC result (`internal`).
- The cron route 401s on: no `Authorization` header, a wrong secret, `CRON_SECRET` unset entirely (fail closed), and a bare secret with no `Bearer ` prefix — `withServiceRole` is never called in any of these.
- The route accepts both `GET` (what Vercel Cron actually invokes — it cannot be configured to call a route with `POST`) and `POST` (manual/scripted trigger), running the identical check and job.
- A failed job maps to the error's own HTTP status (`httpStatusForError`), not a hardcoded one — proven with `dependency_unavailable` → 503.
