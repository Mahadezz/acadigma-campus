## 1. Scope

**What this Part is.** Every signed-in user gets a `text_size` preference (Normal/Large/Extra large) that scales the whole app's root font size, server-rendered with no flash. Owner/admin/teacher additionally get a `ui_mode` (full/basic) switch, hidden for `staff`; turning it on saves the preference, mirrors it to a cookie, and lands on `/app/home`. Both settings are reachable from `/app/settings/display`, and "Switch to basic mode" is now in the full app's user menu. `/app/home` in this Part is a minimal placeholder — Parts 2-3 build the real class-by-class home and hub.

**Acceptance criteria covered** (spec §9):

**Out of scope for this Part** (per the design-lane brief, explicit descope beyond spec §8 Part 1's own wording): the real class-by-class `/app/home` (`TodayStrip`, `ClassBlock`, `getBasicHome`) and the class hub — F-ID-10 Parts 2-3. AC-4 through AC-13, AC-16, AC-17 are not this Part's to prove.

**Risk areas:** (1) `user_preferences` already existed on `main` with a different shape than the spec described — getting the migration and RLS expectations right against the _real_ table, not the spec's stale description, was the main risk (D-404). (2) The text-size root-scaling mechanism (`<html data-text-size>` + CSS) needed to apply with zero flash — proven by asserting the attribute immediately after `page.goto`, not after any client-side settle time. (3) An inline per-page Server Action closure on `/app/home` was found to add ~70 kB gzipped to that one route's First Load JS in a local production build; replaced with the codebase's existing client-component-calls-a-shared-action pattern, which brought it back in line with every other `/app/*` route.

## 4. Database (pgTAP)

**Ran in CI** ([run 36196552807](https://github.com/Mahadezz/acadigma-campus/actions/runs/36196552807), `db` job): **13/13 assertions PASS** (`Files=35, Tests=972, 5 wallclock secs` for the whole suite this file joined).

| Table                                           | Isolation assertions                                                                                     | Escalation assertions                                                                                                                          | Result           | File                                                                    |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------- |
| `user_preferences` (`ui_mode`/`text_size` only) | 4 (own-row read, stranger read = 0 rows, stranger write = 0 rows affected, anon has no SELECT privilege) | 4 (platform admin gets 0 rows and 0 rows affected on another user's row; both enum types reject an out-of-range value, pinned `22P02` message) | PASS — 13/13, CI | `supabase/tests/60_user_preferences_ui.sql` (13 assertions, `plan(13)`) |

**Two real defects the `db` job caught and this report's authoring session fixed, across two CI iterations:**

1. **A data-modifying CTE nested inside `is()`'s argument.** `with upd as (update ... returning 1) select count(*) from upd` used as a scalar subquery passed to `is(...)` is refused by Postgres ("a WITH clause containing a data-modifying statement must be at the top level"). Fixed by hoisting the `WITH` to the top of each statement: `with upd as (...) select is((select count(*) from upd), ...)`.
2. **An assertion that can never pass inside pgTAP's transaction model.** The original test compared `updated_at > created_at` after an edit; every `now()` call inside one `begin;`/`rollback;` transaction returns the identical value, so the two timestamps are always equal there, never `>`. Replaced with the same catalog check `17_onboarding_progress.sql` already uses for the identical problem: `exists(select 1 from pg_trigger t join pg_class c ... join pg_proc p ... where c.relname = 'user_preferences' and p.proname = 'tg_set_updated_at')` — proves the trigger is attached, which is what the test actually needed to prove.

A third, smaller fix in the same job: the pinned `throws_ok` messages said `invalid input value for enum public.ui_mode: "bogus"`; Postgres's real message omits the schema qualifier (`enum ui_mode`, not `enum public.ui_mode`) — corrected to match.

**`coverage.sql` / `scripts/check-coverage-test-files.mjs`:** ran locally (the static half only — no `workspace_id` column on `user_preferences`, so this table isn't in that gate's scope at all): **PASS**, 39/39 `workspace_id` tables named, 0 `KNOWN_GAPS`.

### Specifically proven (by the pgTAP file's assertions, confirmed in CI)

- A brand-new user's row defaults to `ui_mode='full'`, `text_size='normal'` with no extra insert (the existing `handle_new_user()` trigger already creates the row).
- A direct `UPDATE` aimed at another user's `user_id` affects zero rows (RLS's `USING` clause, not an application-level check).
- A platform admin gets zero rows and zero rows affected against another user's preferences — this table has no platform-admin bypass, unlike `onboarding_progress`'s documented deviation.
- The pre-existing `attach_updated_at` trigger is still attached to `user_preferences` (catalog check against `pg_trigger`, not a `now()` comparison — pgTAP runs the whole file in one transaction, so `created_at`/`updated_at` are not distinguishable by timestamp there, the same reasoning `17_onboarding_progress.sql` documents).
- An out-of-range `ui_mode`/`text_size` value is rejected by Postgres itself (`22P02`), with the exact message pinned per the 4-arg `throws_ok` rule.

**Found and fixed during this Part:** the first version of `/app/home` used an inline `"use server"` closure as a `<form action>` handler; that alone measured **264 kB gzipped**, over budget and ~70 kB heavier than every other route sharing the same shell layout. Replacing it with a small client component (`switch-to-full-app-button.tsx`) calling the already-exported `updateUiPreferences` action — the same `useTransition` + `router.push` shape `DisplaySettingsForm`/`UserMenu` already use — brought it to 194 kB. Root cause not fully diagnosed (suspected: Next's per-page action-reference chunking not de-duplicating against the shared bundle); recorded as a known issue for whoever next reaches for an inline page-level server action in this codebase.

Lighthouse (LCP, INP, the §5.5 150 KB budget specifically for `/app/home`): **not run** — the existing Lighthouse CI job needs a deployed/served build; `/app/home` and one class hub are meant to be added to its URL list per spec §5.5/Part 2, and since this Part's `/app/home` is a placeholder that Part 2 replaces wholesale, that addition is deferred to Part 2 rather than pointed at a page about to be rewritten.
