## 1. Scope

**What this Part is.** Every active, non-parent member of the school can now open `/app/staff`, search and filter the people who work there, and open a read-only person sheet for anyone — including a member who has no `staff_records` row yet (which, before this Part's `staff_directory` fix, D-209, meant the school's own owner on day one).

**Acceptance criteria covered** (from spec §9):

| #     | Criterion                                                                         | Covered by                                                                |
| ----- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| AC-1  | Any non-parent member sees every active member; no compensation/NID/document data | `supabase/tests/46_staff_directory.sql`; `staff-directory.spec.ts`        |
| AC-2  | A parent is redirected, `listStaff`-equivalent read is never reachable            | `staff-directory.spec.ts` ("a parent is redirected"); `requireShell` gate |
| AC-29 | Tenant isolation on the widened view                                              | `supabase/tests/46_staff_directory.sql` (School C / School D)             |
| AC-31 | 360×800: search reachable without scrolling, no horizontal scroll                 | manual viewport check (below); Playwright at 360×800                      |

AC-3/4/5/6 (edit own contact, designation change notification, labels Pro gate, `permissions.can()` never reads labels) belong to Parts 3/4 and are out of scope here, per the spec's own Parts breakdown.

**Out of scope for this Part** — and where it is handled instead:

- Record editor, documents, compensation, offboarding — Parts 3-5, unchanged.
- Message and View timetable quick actions — deferred; no messaging (F-OP-05) or timetable UI exists anywhere in the app yet (D-209 item 7). Only `tel:` Call is wired.
- The invite entry point named in the Part 2 scope line — deferred; no invitation server action or UI exists anywhere in the codebase yet, for any feature (D-209 item 7).

**Risk areas** — where the testing effort went:

- The `staff_directory` view's widened FROM clause (D-209) is the highest-risk change: it had to add every active member without ever admitting compensation, NID or document data, and had to keep tenant isolation exact under a different join shape than Part 1's pgTAP proved.
- The dashboard's "staff records" KPI silently changing meaning if left pointed at the widened view (fixed: moved to `staff_records` directly).

### Notable cases proven

- `listStaff` maps a directory row with `id: null` (no `staff_records` row) correctly, and paginates via `membershipId` keyset (`packages/db/src/repositories/staff.test.ts`).
- `getStaffDirectoryRow` returns `not_found`, not an error, for a bad/inaccessible membership id — matching every other by-id lookup in the package.
- `listStaffInputSchema` accepts role+status+q+cursor together and rejects `role: "parent"` (not a valid base role for the directory).
- `staffDirectoryRowSchema` accepts a null `id` and requires `membershipId` (contract test proves both directions).
- `permissions.test.ts`'s exhaustive `Record<Action, readonly Role[]>` table asserts `staff.view` for real: exactly owner/admin/teacher/staff, never parent or platform.
- `apps/web/lib/implemented-routes.test.ts` (pre-existing, D-400) now proves `/app/staff` is listed — the nav link the domain config already carried was dead until this Part built its destination.

## 6. Performance

Not measured with Lighthouse this session (no running server locally). This Part adds one server-filtered, cursor-paginated list query and one by-id lookup, both indexed the same way Part 1's `staff_records`/`staff_compensation` queries already are (`(workspace_id, ...)` prefix); no N+1 (`listSubjects` on the person sheet is one extra query, not per-row). CI's `lighthouse` job is authoritative.

**First-load JS budget (`node scripts/check-bundle-budget.mjs`, ran locally against a real `pnpm --filter @acadigma/web build`):**

| Route                           | First-load JS gzipped | Budget | Result |
| ------------------------------- | --------------------- | ------ | ------ |
| `/(school)/app/staff/page`      | 210 kB                | 250 kB | PASS   |
| `/(school)/app/staff/[id]/page` | 196 kB (see below)    | 250 kB | PASS   |

`/app/staff/[id]` first measured at **275 kB, over budget**. Root cause: `<Button asChild>` (wrapping the `tel:` link) pulled in Radix's unified `radix-ui` package's `Slot`, which tipped this route into becoming a co-owner of a webpack-shared chunk that also bundles several unrelated Radix primitives used elsewhere in the app (Tabs/Popover/Select/Dialog/Toast — confirmed by inspecting the chunk's contents), ~65 kB gzipped this route did not otherwise need. Fixed by rendering the Call action as a plain `<a>` styled to match the outline Button variant exactly (no visual change) — this page has no other client boundary besides `Avatar` (kept; only ~8 kB and needed for the avatar image/fallback behaviour). Every other route under `/(school)/app` was re-measured after the fix and stays within budget (183–250 kB, see the full local run).
