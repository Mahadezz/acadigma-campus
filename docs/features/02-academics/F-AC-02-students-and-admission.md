## 1. Purpose

The student record is the spine of the product: the admissions officer creates it, the class teacher looks at it every day, the parent portal reads it, and every mark, absence and behaviour note points at it. This feature covers the record itself (a small required core plus deep optional groups), the **draft admission wizard** that can be abandoned and resumed, **guardians** and the invitation that turns a guardian into a parent account, **private documents** (health records, NID scans, birth certificates, transfer certificates), **sequential** `STU-` and `ADM-` identifiers, **enrollment** of a student into exactly one section per academic year, **transfer** between sections and **promotion** at year end, **bulk CSV import** with a real validation report, and a printable **ID card with a signed QR code**. "Done": an admissions officer on a phone admits a student in under two minutes with five fields, the record shows up in the class roster instantly, and the guardian receives an invite link that binds them to that child and nothing else.

**Base44 intent vs reality.** The prototype's `Student` had 100+ fields, an unvalidated 9-step wizard whose red asterisks were decorative and whose Submit was never disabled, random collision-prone IDs (`STU-<year>-<5 random digits>`, `ADM-<year>-<3 random digits>`), siblings stuffed into a JSON string, a draft-resume route nothing ever linked to, a welcome email that swallowed its own errors, and a CSV importer that split on commas, looped unguarded `await`s and left its `failed` array permanently empty. Parents were matched to children by a case-sensitive email comparison performed _in the parent's browser after downloading every student in the school_ — including other families' health data and NID numbers. There was no enrollment concept (`Student.class_id` was a single mutable pointer, so moving a student erased their history), no transfer certificate, no ID card and no QR.

## 3. Data

> Proposed; **`docs/architecture/DATA-MODEL.md` wins.** Tenant key `workspace_id` on every table.

**`students`** — the required-minimum core plus optional groups. Soft delete (`deleted_at`) because schools expect undo (ARCHITECTURE §4).
_Required core:_ `student_code text` (`STU-2026-00001`, from `app.next_id`), `first_name text`, `last_name text`, `full_name text generated`, `date_of_birth date`, `gender student_gender` (`male|female|other`), `status student_status` (`draft|active|inactive|transferred_out|graduated|removed`).
_Optional identity:_ `middle_name`, `full_name_bn`, `blood_group`, `religion`, `nationality text default 'Bangladeshi'`, `photo_file_id uuid null references files`, `student_unique_id text null` (the government IEIMS/EMIS student ID, once issued by the board — see §8 Part 9, the IEIMS/EMIS export). `birth_certificate_no` and `nid_no` as raw text columns are **dropped**; see `id_attestation` below.
_Optional contact/address:_ `present_address jsonb`, `permanent_address jsonb`, `student_phone`, `student_email`.
_Optional school history:_ `previous_school`, `previous_class`, `tc_number`, `tc_date`.
_Optional health:_ `health jsonb` (allergies, conditions, medications, physician, notes) — **flagged sensitive**, see §5.14.
_Optional identity attestation:_ `id_attestation jsonb null` — `{type: 'nid' | 'birth_certificate', last4, verified_at, verified_by}`, mirroring F-CM-02's seller KYC attestation pattern. **The full NID/birth-certificate number is never stored** — only the last 4 digits, who verified it and when; the scanned document itself lives in `student_documents` under the retention rule in §3 "Private files". An admin can trigger **"Re-request this document"** from the Documents tab (§4.10) when the scan is missing, expired or illegible; this does not touch the attestation record itself, only the underlying file.
_Optional other:_ `interests text[]`, `photo_consent_records bool null` (consent to keep the photo in the student's records), `photo_consent_print_id bool default false` (consent to print the photo on an object the child carries, e.g. an ID card — **defaults to OFF** and is checked at render time by every print surface, not just the ID card), `heard_from text`, `notes text`.
_Operational:_ `needs_attention bool default false`, `attention_reason text null`, `attention_set_by uuid null`, `attention_set_at timestamptz null` (human flag; F-AC-09 must never clear it), `risk_score int null`, `risk_band text null` (written by F-AC-09), `admission_id uuid null references admissions`.
Indexes: `unique (workspace_id, student_code)`, `index (workspace_id, status)`, GIN trigram index on `full_name` for search, `index (workspace_id, deleted_at)`.

**`admissions`** — the application/draft envelope, so a half-finished form is not a half-finished student: `admission_no text` (`ADM-2026-0001`), `student_id uuid null` (set when submitted), `status admission_status` (`draft|submitted|approved|rejected|cancelled`), `applied_on date`, `class_sought_grade_level_id`, `target_section_id null`, `academic_year_id`, `wizard_step int`, `payload jsonb` (the in-progress form), `submitted_at`, `decided_at`, `decided_by`.
Indexes: `unique (workspace_id, admission_no)`, `index (workspace_id, status)`.

**`guardians`** — data, not users (PRODUCT-DECISIONS 1.13): `student_id`, `relation guardian_relation` (`father|mother|brother|sister|uncle|aunt|grandparent|legal_guardian|other`), `name`, `name_bn`, `phone` (E.164, BD default `+880`), `alt_phone`, `email`, `occupation`, `workplace`, `education`, `id_attestation jsonb null` (**sensitive**) — `{type: 'nid', last4, verified_at, verified_by}`, same shape as the student's, F-CM-02 pattern; the full NID number and `monthly_income_bdt` are **dropped**, not stored at all, `address jsonb`, `is_primary bool`, `is_emergency_contact bool`, `can_pick_up bool`, `photo_file_id`, `sort int`.
Indexes: `index (workspace_id, student_id)`, partial `unique (student_id) where is_primary`, `index (workspace_id, phone)`.

**`guardian_users`** — the link that binds an account to children: `guardian_id`, `user_id`, `student_id` (denormalised so `app.is_guardian_of(student_id)` is one index probe), `status guardian_link_status` (`invited|active|revoked`), `invited_at`, `accepted_at`, `revoked_at`, `invitation_id uuid null references workspace_invitations`.
Indexes: `unique (guardian_id, user_id)`, `index (user_id, student_id) where status = 'active'`.

**`enrollments`** — one student, one section, one academic year: `student_id`, `academic_year_id`, `section_id`, `roll_number int null`, `status enrollment_status` (`active|transferred|withdrawn|completed`), `enrolled_on date`, `ended_on date null`, `previous_enrollment_id uuid null` (transfer chain), `reason text null`.
Indexes: partial `unique (student_id, academic_year_id) where status = 'active'`, partial `unique (section_id, roll_number) where status = 'active' and roll_number is not null`, `index (workspace_id, section_id, status)`.

**`student_documents`** — metadata over private files: `student_id`, `file_id references files`, `kind student_document_kind` (`photo|birth_certificate|nid|transfer_certificate|marksheet|medical|vaccination|guardian_nid|other`), `is_sensitive bool`, `issued_on date null`, `expires_on date null`, `note text`.
Index: `index (workspace_id, student_id, kind)`.

**`student_import_batches`** — the validation report survives the page: `filename`, `status import_status` (`validating|preview|importing|completed|failed`), `total_rows int`, `valid_rows int`, `error_rows int`, `created_count int`, `report jsonb` (per-row: line number, raw values, errors[], resulting student_code), `finished_at`.
Index: `index (workspace_id, created_at desc)`.

**`id_cards`** (issuance log, so a lost card can be invalidated): `student_id`, `serial int`, `qr_token_hash text`, `issued_on date`, `valid_until date`, `revoked_at timestamptz null`, `print_job_id uuid null`.
Index: `index (workspace_id, student_id, serial)`.

**Enums**: `student_gender`, `student_status`, `admission_status`, `guardian_relation`, `guardian_link_status`, `enrollment_status`, `student_document_kind`, `import_status`.

**RLS in words.** `students`: SELECT for active members with role owner/admin/teacher/staff **plus** a separate parent policy `exists (guardian_users gu where gu.user_id = auth.uid() and gu.student_id = students.id and gu.status = 'active')`. The sensitive columns are **not** protected by column-level RLS (Postgres RLS is row-level); instead the repositories expose two projections — `StudentPublicRow` and `StudentSensitiveRow` — and only the sensitive repository method is callable behind `students.read_sensitive`, with a pgTAP test asserting the public view (`v_students_public`) omits health/NID and that parents can only reach the row through the parent policy. INSERT/UPDATE/DELETE: owner/admin, plus a narrow UPDATE policy letting the class teacher of the student's current active enrollment change `photo_file_id`, `roll_number` (on `enrollments`) and emergency contact only. `guardians` and `student_documents`: owner/admin write; teacher read only when `is_sensitive = false`; parent read only their own linked guardian row. `guardian_users`: insert/update by owner/admin only; a parent may read their own rows and may set `status='revoked'` on themselves. `enrollments`: owner/admin write, everyone else read. `student_import_batches`: owner/admin only. `id_cards`: owner/admin plus class teacher read. Everywhere `workspace_id` is immutable and soft-deleted rows are excluded by every default policy except the owner/admin "Removed" filter.

**Private files.** Every `student_documents.file_id` points at a `files` row with `visibility = 'private'` in the `private` bucket. Access is only ever through `GET /api/files/[id]`, which checks the policy, issues a 5-minute signed URL and writes `file_access_log`. Health records and NID scans additionally require `students.read_sensitive`. Student photos are private too (they are children) — the roster renders them through the same signed-URL route with a longer-lived CDN-safe variant generated server-side. **NID and birth-certificate scans are purged at admission decision + 14 days** (not 90 — schools are told this explicitly at onboarding, "we do not archive these documents," so they adjust their own paper filing instead of relying on us). The purge deletes the file and nulls `student_documents.file_id`; the `id_attestation` record (last4, verified_at, verified_by) on `students`/`guardians` is retained as proof the check happened.

## 4. Workflows

**4.1 Quick admit (the 2-minute path).**
_Trigger:_ admin taps the FAB on `/app/students`.
_Steps:_ one sheet with exactly the required minimum per PRODUCT-DECISIONS 2.11 — name, date of birth, gender, section, and one guardian (name + phone + relation). Tap **Admit**.
_Outcome:_ `app.next_id` issues `STU-2026-00001` and `ADM-2026-0001`; an `admissions` row (`status='approved'`), a `students` row (`status='active'`), a `guardians` row (`is_primary`) and an `enrollments` row (active, roll number auto-assigned) are written in one transaction. The roster refreshes optimistically.
_Notifications:_ `student.admitted` in-app to admins; optional guardian SMS/email invite offered on the success sheet ("Invite Rahim's father to the parent portal?").
_Audit:_ `student.created`, `admission.approved`, `enrollment.created` under one correlation id.
_Failures:_ duplicate name + DOB in the same section → a soft warning with "this may be a duplicate, view record / continue anyway"; never a hard block. Section full → capacity warning, continue allowed.

**4.2 Full admission wizard with drafts.**
_Trigger:_ `/app/students/admission` (or "More details" from the quick-admit success sheet).
_Steps:_ 7 groups, each its own screen on a phone: 1 Student · 2 Guardians · 3 Contact & address · 4 Previous school · 5 Health · 6 Documents · 7 Review. **Only group 1 and group 2's first guardian are required**; every other group can be skipped. "Save draft" is always visible; leaving the screen autosaves after 2 s of inactivity into `admissions.payload` + `wizard_step`.
_Resume:_ `/app/students/admission?admission=<id>`, reachable from a real **Drafts** tab on `/app/students` (the Base44 resume route existed but nothing linked to it — inventory §6.28).
_Outcome:_ on Submit, the same transaction as 4.1 plus the optional groups; the draft admission flips to `approved`.
_Notifications:_ `student.admitted`; guardian invite if requested; welcome email through `adapters/email` with a row in `email_log` and a visible result on the success sheet (the prototype swallowed both the error and the confirmation — §6.26).
_Audit:_ `admission.submitted`, `student.created`, `enrollment.created`.
_Failures:_ a Zod failure on Submit returns a per-group error map and jumps to the first failing group; the draft is never lost. If `app.next_id` contends, the advisory lock serialises it — no duplicate codes.

**4.3 Guardian invitation.**
_Trigger:_ admin taps "Invite to parent portal" on a guardian row (guardian must have an email or a phone).
_Steps:_ creates a `workspace_invitations` row with role `parent` and metadata `{guardian_id, student_ids[]}`, sends email (Resend) and/or SMS-ready link, and creates a `guardian_users` row with `status='invited'`. The parent opens `/invite/[token]`, signs up or signs in, and the acceptance handler creates the `parent` membership and flips every listed `guardian_users` row to `active`.
_Outcome:_ the parent sees exactly the linked children in `/family` — never an email-string match, never a client-side filter (the Base44 hole, §6.40).
_Notifications:_ `invite.received` to the parent, `guardian.linked` to admins.
_Audit:_ `guardian.invited`, `guardian.linked`.
_Failures:_ expired token → re-issue flow; an already-linked guardian is idempotent; revoking a link (`guardian_users.status='revoked'`) cuts portal access instantly because RLS reads `status='active'`.

**4.4 Transfer between sections (mid-year).**
_Trigger:_ admin on a student profile → "Move to another section"; or bulk from the roster (multi-select → Move).
_Steps:_ choose target section, effective date (default today), reason. The current `enrollments` row is closed (`status='transferred'`, `ended_on`), a new row is created with `previous_enrollment_id` and a fresh roll number. **Attendance, marks and behaviour already recorded stay attached to the old enrollment** and remain visible on the student's timeline with the section they were recorded in.
_Outcome:_ the student appears in the new section's roll-call from the effective date; attendance sessions before that date still count them in the old section.
_Notifications:_ `student.transferred` to both class teachers.
_Audit:_ `enrollment.transferred` with before/after.
_Failures:_ target section archived → `SECTION_ARCHIVED`; effective date before `enrolled_on` → `DATE_BEFORE_ENROLMENT`; a bulk move reports per-student results and never partially fails silently.

**4.5 Transfer out / withdrawal.** Status → `transferred_out` with a reason and an optional generated **Transfer Certificate** PDF (F-OP-06). The active enrollment closes (`withdrawn`). The record is retained, not deleted; the parent link is revoked on the effective date. Audit `student.transferred_out`.

**4.6 Promotion at year end.**
_Trigger:_ admin closes the academic year (F-AC-01 §4.4) or opens `/app/students/promotion`.
_Steps:_ choose source year → target year; the wizard lists each section with a default mapping (Class 6 – A → Class 7 – A) and a per-student decision: **promote** (default), **repeat** (stay in the same grade, next year), **graduate** (final grade), **hold** (decide later). Results from F-AC-06 pre-fill the default: a student who failed per the pass rule defaults to "repeat" with the reason shown. Review screen shows counts. Commit.
_Outcome:_ one transaction per section: old enrollments → `completed`, new enrollments in the target year, roll numbers re-sequenced by the school's rule (§5.6), students in the final grade → `status='graduated'`.
_Notifications:_ `student.promoted` digest to admins; the parent portal shows the new class after the target year becomes current.
_Audit:_ `enrollment.promoted` per student, one correlation id per section.
_Failures:_ target section missing → the wizard offers to create it inline (calls F-AC-01 `createSection`); a student with an unpublished result shows a warning but does not block.

**4.7 Bulk CSV import.**
_Trigger:_ `/app/students` → "Import".
_Steps:_ (1) download the template CSV (headers documented, with an example row and the BD phone format); (2) upload — parsed **server-side** with a real RFC 4180 parser (`papaparse` in a route handler, not `split(',')` — §6.19); (3) **validate**: every row checked against `StudentImportRowSchema`, section names resolved, duplicates detected (same name + DOB, or same `student_code`), phone numbers normalised to E.164; (4) **preview** screen: "312 rows · 298 valid · 14 with errors", error rows listed with line number, the offending column highlighted, and a "download errors as CSV" button; (5) **Import valid rows** (errors can be fixed and re-uploaded).
_Outcome:_ one batched insert per 500 rows inside a transaction; `student_import_batches.report` persists the full result so the tab can be closed and reopened. Guardian invites are **not** auto-sent (the prototype fired one email per row, §6.26); the success screen offers "Invite 298 guardians" as a separate, queued, rate-limited job.
_Audit:_ `student.imported` with the batch id; one `audit_events` row per created student referencing the batch.
_Failures:_ a malformed file fails at step 2 with the parser's line number; a mid-import failure rolls back that chunk only and the report marks the chunk `failed` with a retry button; the batch is idempotent by `idempotency_key` so a double-tap never duplicates students.

**4.8 ID card with QR.**
_Trigger:_ student profile → "ID card", or roster multi-select → "Print ID cards".
_Steps:_ server renders an ID card PDF (React-PDF, Bengali font embedded) with the school header from `school_profiles`, the student photo **only when `photo_consent_print_id = true`** (otherwise a placeholder silhouette renders, same treatment as a missing photo — the consent is honoured at render time, not just at capture time, and defaults to OFF per §3), `student_code`, class/section/roll, guardian phone, and a **QR code encoding a signed token** — `HMAC-SHA256` over `{workspace_id, student_id, card_serial, exp}` with a server-only secret, base64url, prefixed `ACS1:`. The card row goes into `id_cards`; the PDF lands in `files` and, if requested, a `print_jobs` row with copies = selected count (PRODUCT-DECISIONS 6.4).
_Outcome:_ printable now; scannable later — F-AC-03's `attendance_scan_events` hook verifies the HMAC and resolves the student, refusing revoked serials.
_Audit:_ `id_card.issued`, `id_card.revoked`.
_Failures:_ no photo → the card renders a placeholder and the UI warns; QR secret missing in env → 500 with a clear operator message, never a card without a QR.

**4.9 Phone flow.** `/app/students` is a virtualised `DataList` of cards (photo, name, class, `student_code`) with a **server-side** search box (trigram, debounced 250 ms) and filter chips (Section · Status · Needs attention · Drafts) — never `list()`-then-filter-in-browser (§6.39). Multi-select is a long-press that turns the bottom bar into an action bar (Move · Status · Flag · Print ID · Export). The profile page is a sticky header (photo, name, class, code, attendance % and GPA chips) with tabs: Overview · Attendance · Results · Assignments · Behaviour · Guardians · Documents · Timeline. Sensitive tabs render a lock state for roles without `students.read_sensitive`.

**4.10 Re-request a document.** _Trigger:_ admin, on the Documents tab, taps "Re-request" on a missing, expired or illegible NID/birth-certificate scan (or a guardian NID). _Steps:_ the document's `student_documents` row is marked pending-resubmission and a note is added; the guardian is notified (in-app now, SMS-ready) with what is needed. _Outcome:_ the next upload replaces the file; the `id_attestation` record is re-verified (`verified_at`/`verified_by` updated) once an admin checks the new scan. _Audit:_ `student.document.re_requested`. This is explicit and human-triggered — there is no automatic re-request job.

## 5. Business rules and calculations

1. **Required minimum** (PRODUCT-DECISIONS 2.11): `first_name`, `last_name`, `date_of_birth`, `gender`, a target `section_id`, and at least one guardian with a valid phone. Nothing else may block submission, ever. The wizard's asterisks are generated from the Zod schema, so they can never drift from validation (the Base44 asterisks were decorative — §3 feature 14).
2. **Sequential identifiers** (PRODUCT-DECISIONS 2.6). `student_code = format(pattern, year, next)` where the default pattern is `STU-{YYYY}-{00000}` and `admission_no` defaults to `ADM-{YYYY}-{0000}`; both patterns are editable per school in settings. The counter comes from `app.next_id(workspace_id, kind)`, which takes a transaction-level advisory lock on `hashtext(workspace_id || kind)` and increments `id_counters` — collision-free and gap-free under concurrency. `{YYYY}` is the **academic year's** start year, not the calendar year.
3. **Age on a date** = `date_part('year', age(on_date, date_of_birth))`. Displayed as "10 y 4 m". An admission age outside the grade's expected band (`grade_levels.ordinal + 5 ± 2` years by default) shows an advisory chip, never a block.
4. **One active enrollment.** A student has at most one `enrollments` row with `status='active'` per academic year (partial unique index). All roster, attendance and marks queries join through the active enrollment, so a mid-year transfer is history-preserving by construction.
5. **Roll number assignment.** Default rule `roll_rule = 'alphabetical'` (school setting, alternatives `admission_order`, `manual`, `previous_result`). On section creation/promotion, roll numbers are assigned 1..n by the rule; they are unique per active enrollment in a section. Renumbering a section is an explicit action that writes one audit event listing all changes.
6. **Promotion defaults** read F-AC-06: `result = pass` → promote; `result = fail` → repeat; unpublished → hold. The admin may override every row; the override reason is stored on `enrollments.reason`.
7. **Duplicate detection** on admission and import: `lower(first_name || last_name) = lower(...)` **and** `date_of_birth` equal, within the same workspace and not soft-deleted. Match → warning with a link; never an automatic merge.
8. **Phone normalisation.** Input is normalised to E.164 with default region `BD`: `01712345678` → `+8801712345678`. Invalid numbers fail validation with the expected format shown. Stored normalised; displayed in local format.
9. **Guardian primacy.** Exactly one guardian per student may have `is_primary = true` (partial unique index); setting a new primary clears the old one in the same statement. The primary guardian's phone is what absence alerts and report-card notifications use.
10. **Parent scoping.** A parent's visibility is **only** `guardian_users` rows with `status='active'`; `app.is_guardian_of(student_id)` is the single helper and is used by every parent-facing policy across the whole product. No email matching anywhere (the Base44 case-sensitivity bug, §6.59, is structurally impossible here).
11. **Soft delete.** `students.deleted_at` set; the row disappears from all default queries, the active enrollment closes as `withdrawn`, parent links are revoked, and an owner/admin can restore within the retention window. Hard delete is a platform-staff operation only, and cascades are `restrict` — marks and attendance are never silently destroyed.
12. **Status machine.** `draft → active` (on admission submit) · `active ↔ inactive` (long absence, fees) · `active → transferred_out | graduated` · any → `removed` (soft delete). Attendance sessions never include non-`active` students; marks already recorded remain.
13. **Student search** is server-side: `full_name ILIKE %q%` via the trigram index, plus exact match on `student_code`, `admission_no` and guardian phone. Results are cursor-paginated at 30 per page. No screen downloads the roster (§6.39–40).
14. **Sensitivity classification.** `health`, the `id_attestation` record (student and guardian), `present_address`, `permanent_address` and `photo_file_id`, and every `student_documents` row with `is_sensitive = true` are **sensitive**: readable only with `students.read_sensitive`, never included in the roster payload, never in CSV export unless the exporter explicitly ticks "include sensitive" (which writes an audit event `students.sensitive_exported`). The **`staff` base role's default `students.read` projection is restricted to name, class and roll only** — no address, no photo — since staff do not hold `students.read_sensitive` (§2). A **whole-school** sensitive CSV export additionally requires: a **row cap** (school-configurable, default 500), **two-person approval** (a second owner/admin must confirm before the file is generated), a **per-export watermark** (exporter name, timestamp and a unique export id stamped into the file), and a **school-level switch** (`school_profiles.sensitive_export_enabled`, default true) that can disable the whole-school export entirely. `students.sensitive_exported` now carries the approver id and the watermark id.
15. **ID card QR token.** `token = base64url(payload) || '.' || base64url(HMAC_SHA256(secret, payload))` where `payload = {v:1, w:workspace_id, s:student_id, n:card_serial, exp:iso_date}` — **written rule: this payload never gains a name, photo URL or date of birth**, now or in any future revision. Default validity: **the current term's end date** (shortened from the academic year's `ends_on` + 60 days — schools reissue the card each term instead of holding one valid all year). On loss, the card is **actually revoked** via `id_cards.revoked_at` rather than left to expire on its own. Verification requires: signature valid, not expired, `id_cards.revoked_at is null`, and the student `status='active'`. Re-issuing a card increments `serial` and revokes the previous one. **Before M7**, a DPIA and a stated retention period for `attendance_scan_events` (F-AC-03) are required, since a scanned QR resolves to a student through that table.
16. **Profile completeness %** (shown as a ring on the profile) = `round(100 × filled / total)` over a fixed weighted checklist: required core (weight 5 each: name, DOB, gender, section, primary guardian phone), photo (3), address (2), previous school (1), health (2), `id_attestation` present (2), second guardian (1), documents ≥ 1 (2). Total weight 25 + 13 = 38. Purely informational; it gates nothing.
17. **CSV template columns** (v1, order fixed): `first_name, middle_name, last_name, date_of_birth (YYYY-MM-DD), gender (male|female|other), section (e.g. "Class 6 – A"), roll_number, student_code (optional, else generated), religion, blood_group, present_address, guardian1_relation, guardian1_name, guardian1_phone, guardian1_email, guardian1_occupation, guardian2_relation, guardian2_name, guardian2_phone, previous_school, notes`. `birth_certificate_no`/`nid_no` are **not** import columns — identity attestation is captured through the document upload + verification flow (§3), never as a bulk-imported raw number. Unknown extra columns are reported as warnings, not errors.

## 9. Acceptance criteria

1. **Given** an admin on a 360×800 phone, **when** they complete the quick-admit sheet with name, DOB, gender, section and one guardian phone, **then** a student with a sequential `STU-2026-000NN` code, an approved admission, a primary guardian and an active enrollment exist, created in one transaction.
2. **Given** two admins admitting simultaneously, **when** 100 admissions run in parallel, **then** 100 distinct, gap-free `student_code` values are issued and no unique-violation error reaches the user.
3. **Given** an in-progress admission at step 4, **when** the browser is closed and reopened, **then** the Drafts tab lists it as "Step 4 of 7" and resuming restores every entered value.
4. **Given** a required field is missing, **when** the wizard is submitted, **then** the response is a per-group error map, the wizard jumps to the first failing group, and no partial student row is created.
5. **Given** a guardian with an email, **when** an admin invites them and the guardian accepts, **then** a `parent` membership and `guardian_users.status='active'` exist, and the parent's `/family` shows exactly the linked children.
6. **Given** a parent of student X, **when** they request student Y of another family by id through the API, **then** RLS returns nothing and the attempt is logged — proved by a pgTAP negative test, not by UI hiding.
7. **Given** a subject teacher (not the class teacher), **when** they open a student profile, **then** the health tab renders a locked state and a direct sensitive-read call returns `FORBIDDEN_SENSITIVE`.
8. **Given** a student with 40 attendance records and 12 marks in Class 6 – A, **when** they are transferred to Class 6 – B on 1 March, **then** the old records remain attached to the old enrollment and visible on the timeline, and the 2 March roll-call for 6 – B includes them while 6 – A's does not.
9. **Given** a CSV with a quoted comma in an address, a Bengali name and a malformed date, **when** it is uploaded, **then** the first two import correctly and the third is reported with its line number and the `date_of_birth` cell highlighted; the report survives a page reload.
10. **Given** a validated import preview, **when** Import is tapped twice quickly, **then** exactly one batch commits (idempotency key) and no duplicate students are created.
11. **Given** an import of 298 students, **when** it completes, **then** **no** welcome emails have been sent automatically and the success screen offers "Invite 298 guardians" as a separate queued action.
12. **Given** an issued ID card, **when** its QR token is posted to the verify endpoint, **then** the student resolves; **when** the card is revoked and the same token is posted, **then** the endpoint returns `REVOKED`; **when** one byte of the token is changed, **then** it returns `INVALID_SIGNATURE`.
13. **Given** a closed academic year 2026 and a target year 2027, **when** promotion is committed for Class 6 – A with 3 repeats, **then** every promoted student has a `completed` 2026 enrollment and an `active` 2027 enrollment in Class 7 – A, repeats get a Class 6 enrollment in 2027, and one audit correlation id covers the section.
14. **Given** a soft-deleted student, **when** any roster, attendance or parent query runs, **then** they are absent; **when** an owner opens the "Removed" filter, **then** they are listed and can be restored.
15. **Given** a roster of 3,000 students, **when** the roster screen loads, **then** the network payload is one paginated page (≤ 30 rows), never the whole table.

## 11. Open questions

1. **Sibling linking.** The prototype stored siblings as a JSON string. Assumed: siblings are derived from shared guardians (same `phone` or same `guardian_users.user_id`) and shown as a "Siblings" chip; no explicit sibling table until fee discounts need one.
2. **Student photo retention after graduation.** Assumed: retained with the record; a future data-retention policy (SECURITY.md) may purge photos of graduated students after N years.
3. **National student identifiers.** Resolved by §3/§8 Part 9: `students.student_unique_id` carries the IEIMS/EMIS number, with an IEIMS/EMIS-ready export. A separate board registration number, if boards require one distinct from IEIMS, remains open — confirm the exact label with the owner.
4. **Re-admission of a `transferred_out` student.** Assumed: the same record is reactivated with a new enrollment and the original `student_code` is kept (history stays in one place). Alternative (new code) is one setting away.
5. **Who may edit a student's DOB after admission?** Assumed: owner/admin only, and every change writes an audit event with before/after, since DOB drives age-band checks and board registration.
6. **Import updating existing students.** v1 is insert-only. Assumed: an "update existing by `student_code`" mode is a later part; until then re-importing a known code is an error row, not a silent overwrite.
