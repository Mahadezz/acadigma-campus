## 1. Purpose

How a school gets its people in. Two complementary paths, one table (PRODUCT-DECISIONS §1.3): an admin **invites by email or SMS**, and the invitee accepts a signed link that makes them an active member; or the school shares a **rotating join code**, a teacher requests access with it, and an admin approves. The same machinery invites **guardians** so a parent account can be bound to their children (PRODUCT-DECISIONS §1.13). "Done" from the user's chair: a principal in Cumilla types twelve email addresses into her phone during a staff meeting, the teachers get a real email that afternoon, and by the next morning the roster shows twelve active members — and the one teacher who never got the email joins with a code she reads off the notice board.

The Base44 prototype had both halves and connected neither. The invitation entity (`SchoolWorkspaceInvitation`) was fully designed and **never created by any code path** — `grep` found zero `.create` calls (D9), so the beautifully built accept/decline inbox at `/personal/workspaces` was permanently empty. "Invite by Email" wrote a bare pending membership row, toasted _"Invitation sent"_, and sent nothing (B1); the underlying `base44.users.inviteUser` call sat inside a bare `try{}catch{}`. The join code was generated with `Math.random()` (security review), the lookup had no rate limit, `SchoolSettings.read` was `{}` so every school's code was enumerable anyway, and joining wrote a membership row directly from the client. Invitations had no RLS, no expiry enforcement, and the email binding was never checked on redeem — anyone with a link was anyone. The "Request Sent" screen's only button was **Sign Out**, and no notification reached the admin in either direction. The rebuild keeps both product paths and rebuilds every mechanism underneath them.

### RLS, in words

- `workspace_invitations` **select**: `app.has_role(workspace_id,'{owner,admin}')`; **plus** a self policy — a signed-in user sees rows where `lower(email) = lower(auth.jwt()->>'email')` or `phone = (select phone from profiles where id = auth.uid() and phone_verified_at is not null)` and `status='pending'`. Platform staff read all. `token_hash` is excluded from every client-facing view.
- `workspace_invitations` **insert**: `app.has_role(workspace_id,'{owner,admin}')` with a `with check` that `invited_by = app.current_user_id()` and `role <> 'owner'` unless `app.member_role(workspace_id) = 'owner'`.
- `workspace_invitations` **update**: owners/admins may set `status` to `revoked` only; the accept/decline transitions happen exclusively inside the SECURITY DEFINER function `app.redeem_invitation(raw_token, action)`, which is the only code that can write `accepted`/`declined`.
- **delete**: no grant. Expired and revoked rows stay as evidence.
- `workspace_join_codes` **select**: `app.has_role(workspace_id,'{owner,admin}')` and platform staff — **the code is never world-readable**, which is the direct fix for `SchoolSettings.read: {}`. Lookup by a joiner goes through `app.find_workspace_by_join_code(code)`, a SECURITY DEFINER function that returns only `{workspace_id, name, logo_url}` and nothing else.
- `workspace_join_codes` **insert/update**: `{owner,admin}`; **delete**: no grant.
- The self-insert path on `workspace_members` described in F-ID-03 §3 is satisfied only by `app.request_join_with_code(code)`, which verifies the code, the use count, the expiry, the absence of an existing active membership, and the seat limit, then inserts `status='pending', role=default_role`.

Private files: none.

## 4. Workflows

### 4.1 Invite by email or SMS

**Trigger:** Team & Access → **Invite** (the FAB in thumb reach at 360×800).

1. A bottom `Sheet`: a channel segmented control (Email / SMS), a multi-entry field that accepts pasted, comma- or newline-separated addresses (chips appear as you type), a role select, an optional custom label, an optional message, and a preview of exactly what the recipient will receive.
2. Client validates each entry; the server re-validates with `SendInvitationsInput` and rejects the whole batch only on structural errors — per-address problems come back as a per-row result so eleven good addresses are not blocked by one typo.
3. For each address: generate 32 bytes of CSPRNG entropy → base64url raw token (the link) → store `sha256(token)` → insert the invitation → enqueue a `jobs` row `invitation.send`.
4. The job renders the React Email template (school name, logo, inviter's name, role, message, the link, the expiry date, a "you didn't expect this?" line) and sends via Resend; SMS renders a 2-segment message with a short link. Every send writes `email_log` / `sms_log`.
5. The sheet closes to a result summary: "10 sent · 1 already a member · 1 invalid address", each with the address.

**Outcome:** `workspace_invitations` rows in `pending`.
**Notifications:** `invite.received` to the invitee **if they already have an Acadigma account** (in-app, so they see it on next open even if the email is lost). Nothing to the inviter beyond the UI result.
**Audit:** one `member.invited` row per invitation, with the workspace, role and masked address (`r***@gmail.com`) — never the raw token.
**Failure cases:** the address is already an active member → skipped with a per-row reason; a pending invitation already exists → offered as "Resend" instead; the plan's seat limit is reached → `SEAT_LIMIT_REACHED` for the whole batch with an upgrade link; email provider failure → the job retries with backoff (3 attempts), and the invitation row shows "Delivery failed — resend" in the list.

**Staff privacy notice at invitation [2027-05].** For `role ∈ {admin, teacher, staff}` invitations, the accept screen (§4.2) shows a **staff privacy notice** — what the school and platform hold on a staff member, what derived metrics exist (workload, punctuality, eligibility-adjacent signals), and the plain-language statement below — before the Accept button is enabled. Accepting records a `legal_acceptances` row with `document='staff_privacy_notice'` (a new value alongside `dpa`/`terms`/`privacy`/`seller_agreement` — the enum extension is DATA-MODEL.md's, out of scope here), `user_id`, `workspace_id`, `version`, `text_sha256`, `accepted_at`. Re-invitation after a version bump re-shows the notice and records a new row rather than reusing the old acceptance.

**Written statement (verbatim, shown in the notice and linked from Settings):** _"Workload, punctuality and eligibility-related metrics computed about you are advisory only. No automated system makes, or is used to make, an employment decision about you — hiring, discipline, non-renewal or termination — on the basis of these numbers alone."_ Staff also get visibility of their own derived metrics wherever they are computed (workload: F-TE-06 §5.3; punctuality/attendance-adjacent: owned by whichever operations feature computes them) — this spec only owns the notice-at-invitation and the acceptance record; it does not itself compute any metric.

### 4.2 Accept an invitation

**Trigger:** the link `/invite#{raw_token}` — the token travels in the **URL fragment**, never the path or a query string, so it is never sent to the server in a request line, never logged by a reverse proxy or CDN access log, and never leaked to a third-party origin via `Referer`. The route additionally serves `Referrer-Policy: no-referrer` on every response, so even an in-page link or asset load off `/invite` cannot leak the fragment-bearing URL upstream. [MUST]

1. The **client** reads the fragment, then calls a **POST** to redeem/look up the token (POST-from-landing pattern) rather than a GET carrying the token as a path segment — the token never appears in server access logs, browser history sync, or a `Referer` header. The handler hashes the token and looks up the row. Four terminal states are rendered as **full screens, not toasts**: not found, expired, revoked, already accepted (with a "Go to {school}" button when the accepter is the current user).
2. Valid and pending → a branded screen: the school logo and name, "You've been invited as **Teacher**", who invited them, the message, and two buttons: **Accept** / Decline.
3. If the visitor is **signed out**, Accept routes to `/register#invite={token}` or `/login#invite={token}` (fragment, not query string) with the email pre-filled and locked. After authentication the redemption resumes automatically from the fragment still held client-side.
4. If the visitor is **signed in as a different identity** than the invitation targets, the screen says so explicitly ("This invitation was sent to r***@gmail.com but you are signed in as n***@gmail.com") and offers "Sign in as that person" or "Accept with my current account" — the latter is **refused** for `kind='guardian'` and for `role='admin'/'owner'`, and allowed for `teacher`/`staff` only when the current account's email is verified, with the substitution recorded in the audit row. This is the email-binding check the prototype never performed.
5. Accept → `app.redeem_invitation(token,'accept')` in one transaction: invitation → `accepted`, `accepted_at`, `accepted_by`; `workspace_members` upsert to `status='active'`, `role`, `custom_label_id`, `joined_at`, `invited_by`, `invitation_id` (PRODUCT-DECISIONS §1.3 — email invites land `active`, skipping `pending`); for `kind='guardian'`, additionally a `guardian_users` link row.
6. Redirect to that workspace's landing route with a one-time welcome banner.

**Notifications:** `invite.accepted` to the inviter and all owners/admins. **Audit:** `member.invitation_accepted`, plus `member.approved` semantics on the membership row.
**Failure cases:** the token is valid but the workspace was archived/suspended → a dedicated screen; the seat limit was reached between send and accept → the invitation stays pending and the invitee sees "This school has reached its member limit — please contact the school"; concurrent double-click → the function is idempotent on `(token, accepted)`.

### 4.3 Decline, revoke, resend, expire

- **Decline:** the same screen's secondary action → `status='declined'`, `declined_at`. Notification `invite.declined` to the inviter. The invitee can be re-invited later.
- **Revoke:** Team & Access → Invitations tab → row action. `status='revoked'`; the link immediately shows the revoked screen. Audit `member.invitation_revoked`.
- **Resend:** row action; increments `sent_count`, updates `last_sent_at`, **and extends `expires_at` to now + 14 days**, but does **not** mint a new token (so the old link keeps working — the common support case is "I found the first email"). Rate-limited to 3 resends per invitation and a 10-minute cooldown between them. Audit `member.invitation_resent`.
  - **"New link" option [MUST]:** a distinct row action, separate from the plain resend above, that **re-mints `raw_token`/`token_hash`**, invalidates every previously issued link for that invitation, and sends the fresh link. Use this when the old link may have been exposed (forwarded, screenshotted, pasted into a group chat). Audit `member.invitation_relinked`.
- **Expire:** a pg_cron job at 03:00 Asia/Dhaka sets `status='expired'` for `pending` rows past `expires_at` and queues `invite.expired` notifications to the inviter. The redeem function also treats a past `expires_at` as expired regardless of the stored status, so the job is a cleanup, not the enforcement.

### 4.4 Join with a code

**Trigger:** `/onboarding` → "Join a school" (F-ID-05), or `/personal/workspaces` → "Join a school".

1. A single code field, formatted as `ACD-____-____` with auto-uppercasing, auto-hyphenation and paste support; the numeric-adjacent character set means no ambiguity between `0`/`O`.
2. `lookupJoinCode` (server) calls `app.find_workspace_by_join_code` → returns the school's name and logo → a confirmation card: "Join **Ideal School & College**?" with the role they will be requested as.
3. Confirm → `requestJoinWithCode` → `app.request_join_with_code` → membership `pending`.
4. The joiner sees a **status screen that is not a dead end** (the prototype's only button was Sign Out): "Waiting for approval from Ideal School & College — we'll notify you. In the meantime, continue in your personal workspace." with a primary button to `/personal` and a secondary "Cancel request".
5. Owners and admins get `join_request.received` (in-app, plus email if their digest settings allow) with an `action_url` straight to the Pending tab.
6. Approval/rejection is F-ID-03 §4.5. On approval the joiner gets `join_request.approved` with an `action_url` to the school's dashboard.

**Audit:** `member.join_requested`, then `member.approved` / `member.rejected`.
**Failure cases:** unknown or inactive code → a generic "That code isn't valid" (no distinction between "wrong" and "disabled", to make enumeration useless), with the attempt counted against a per-user and per-IP throttle; already an active member → "You're already in this school", with a switch button; already pending → the status screen; `max_uses` exhausted or `expires_at` passed → "This code is no longer accepting new members — ask the school for a new one"; seat limit reached → the same message, because the joiner should not learn the school's billing state.

### 4.5 Invite a guardian (parent linking)

**Trigger:** a student's record → Guardians → "Invite to the parent portal" (the student and guardian records belong to the academic area; this feature owns the invitation).

1. The guardian already exists as **data** (`guardians`: name, relation, phone, email — PRODUCT-DECISIONS §1.13). The sheet confirms the channel and shows exactly which children will become visible.
2. Sends an invitation with `kind='guardian'`, `role='parent'`, `guardian_id` set, expiry 30 days (longer than staff invites — parents are slower).
3. Redemption creates the account if needed, the `parent` membership, **and** the `guardian_users` link. A parent invited for a second child in the same school gets a second `guardian_users` link and no second membership.
4. The accept screen for guardians names the children explicitly and states what the parent will be able to see (attendance, marks, timetable, exam schedule, assignments, parent-visible behaviour notes, announcements) — informed consent, not a blank "accept".

**Notification:** `guardian.invited` (to the guardian if they already have an account), `guardian.linked` to the class teacher on acceptance.
**Audit:** `guardian.invited`, `guardian.linked` with the student id.
**Failure case:** identity substitution is **never** permitted for guardian invitations (§4.2 step 4) — a parent link must be bound to the invited address or phone.

### 4.6 Manage the join code

`/app/settings/workspace` → Access → Join code card: the code in a large monospace row, Copy, Share (Web Share API on phone, falling back to Copy), a QR code that encodes the join URL, `default_role`, `max_uses`, `expires_at`, an active/disabled switch, and **Rotate**.

- **Rotate** → destructive confirm ("Anyone holding the old code will no longer be able to join") → the old row is deactivated, a new one is generated. Audit `join_code.rotated`.
- **Disable** → `is_active=false`; the join path then behaves exactly like an unknown code. Audit `join_code.disabled`.
- The card also shows "Used 14 times · last on 3 Sep" from `use_count` and the audit trail, so an admin can notice abuse.

This replaces the prototype's copy-only affordance that silently copied an empty string for personal workspaces (B17) — personal workspaces have no join code and the card is not rendered.

### 4.7 My invitations (the invitee's inbox)

`/personal/workspaces` → an "Invitations" section listing pending invitations addressed to the signed-in user's verified email or phone: school name and logo, role offered, who invited them, expiry, Accept / Decline. This is the prototype's fully-built-but-unreachable inbox (D9), finally fed by real rows. Empty state: "No invitations right now — you can also join a school with a code."

## 5. Business rules and calculations

| Rule                                           | Value                                                                                                                                                                                                                                     | Where                                 |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| Invitation token                               | 32 bytes CSPRNG, base64url (43 chars), stored only as `sha256`, compared in constant time                                                                                                                                                 | `packages/domain/invite/token.ts`     |
| Invitation expiry                              | staff/member **14 days**; guardian **30 days**                                                                                                                                                                                            | `packages/domain/invite/policy.ts`    |
| Resend                                         | max 3 per invitation, 10-minute cooldown, extends expiry to now + 14 days, keeps the same token                                                                                                                                           | same                                  |
| Batch size                                     | ≤ 50 addresses per send                                                                                                                                                                                                                   | `SendInvitationsInput`                |
| Per-workspace send limits                      | 200 invitations / day, 1,000 / month                                                                                                                                                                                                      | `auth_throttle` keyed by workspace    |
| One live invitation per identity per workspace | partial unique index on pending rows                                                                                                                                                                                                      | migration                             |
| Join code format                               | `{workspace_short_code}-XXXX-XXXX`, **per-workspace prefixed** (not the fixed `ACD-` prefix table-wide), alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (Crockford, no I/L/O/U) for the random suffix, `gen_random_bytes`                    | `app.generate_join_code()`            |
| Join code entropy                              | 8 random characters × 32 symbols = 2^40 ≈ 1.1 × 10¹² combinations **per workspace prefix**; a guess against one school's code space no longer doubles as a guess against every other school's; with throttling, brute force is infeasible | same                                  |
| Join code lookup throttle                      | 10 attempts / hour per user, 30 / hour per IP, then a 1-hour block; every failed attempt audited                                                                                                                                          | `auth_throttle`                       |
| Global join-code failure budget                | A **platform-wide** hourly failed-lookup budget (independent of the per-user/per-IP throttles above) that raises a platform-console alert when exceeded — catches slow, distributed guessing that stays under each individual throttle    | `auth_throttle` + platform alert job  |
| Join code default role                         | `teacher`; approval may change it                                                                                                                                                                                                         | `workspace_join_codes.default_role`   |
| Approval requirement                           | always true in v1                                                                                                                                                                                                                         | `requires_approval`                   |
| Rotation                                       | one active code per workspace; old codes are retained as inactive rows                                                                                                                                                                    | partial unique index                  |
| Email-invite landing status                    | `active` (PRODUCT-DECISIONS §1.3a)                                                                                                                                                                                                        | `app.redeem_invitation`               |
| Code-join landing status                       | `pending` (PRODUCT-DECISIONS §1.3b)                                                                                                                                                                                                       | `app.request_join_with_code`          |
| Identity substitution                          | allowed only for `teacher`/`staff` with a verified email, recorded in audit; never for `admin`, `owner` or `guardian`                                                                                                                     | `app.redeem_invitation`               |
| Seat check                                     | evaluated at **send**, at **accept** and at **approve** — all three, because time passes                                                                                                                                                  | `packages/domain/workspace/limits.ts` |
| Notification pairing                           | every invitation event notifies **both sides** (PRODUCT-DECISIONS §1.3)                                                                                                                                                                   | F-ID-07                               |
| Masking in audit/logs                          | emails as `r***@gmail.com`, phones as `+8801*****678`; raw tokens never logged                                                                                                                                                            | `packages/domain/privacy/mask.ts`     |

## 9. Acceptance criteria

1. **Given** an admin on a 360×800 viewport, **when** they paste twelve email addresses into the invite sheet and send, **then** twelve `workspace_invitations` rows are created, twelve `email_log` rows are written, and the result summary names any address that was skipped and why.
2. **Given** an invitation to `r@example.com`, **when** anyone opens the link, **then** the raw token never appears in any log, audit row or error message, and the database stores only its sha256.
3. **Given** a valid pending invitation, **when** a signed-out visitor opens the link and completes registration, **then** on returning they are immediately an `active` member with the invited role and land on that school's dashboard — with no "pending approval" step.
4. **Given** an invitation addressed to `r@example.com`, **when** a user signed in as `n@example.com` opens it, **then** the mismatch is shown with both identities masked, and accepting with the current account is refused outright for `admin`, `owner` and guardian invitations.
5. **Given** an invitation whose `expires_at` has passed but whose `status` is still `pending`, **when** it is redeemed, **then** the function returns `TOKEN_EXPIRED` — expiry is enforced at redemption, not only by the nightly sweep.
6. **Given** a revoked invitation, **when** the invitee opens the link, **then** they see the revoked screen and no membership is created.
7. **Given** an invitation that has already been accepted, **when** the link is opened a second time (or double-tapped), **then** exactly one membership exists and the second call returns the same success result.
8. **Given** an admin of school B, **when** they query `workspace_invitations` or `workspace_join_codes` for school A through the browser client, **then** zero rows are returned.
9. **Given** a wrong join code, a disabled join code, and a code whose `max_uses` is exhausted, **when** each is submitted, **then** all three produce the identical `CODE_INVALID` message and none reveals whether the school exists.
10. **Given** eleven join-code attempts within an hour by one user, **when** the eleventh is submitted, **then** it is throttled with a countdown and the attempt is recorded in the audit trail.
11. **Given** a successful join request, **when** the joiner reaches the status screen, **then** the primary button takes them to their personal workspace — not to sign-out — and owners/admins have received `join_request.received` with an `action_url` to the Pending tab.
12. **Given** an owner rotating the join code, **when** rotation completes, **then** the previous code fails identically to a random code, exactly one `is_active` row exists for that workspace, and `join_code.rotated` is in the audit trail.
13. **Given** a guardian invitation for two children in the same school, **when** the guardian accepts both, **then** they have exactly one `parent` membership and two `guardian_users` rows, and the parent shell shows both children.
14. **Given** a school at its plan's teacher seat limit, **when** an admin tries to send an invitation, accept is attempted, or a pending member is approved, **then** all three are blocked with `SEAT_LIMIT_REACHED` and an upgrade link for the admin only.
15. **Given** an invitation resent three times, **when** a fourth resend is attempted, **then** `RESEND_LIMIT_REACHED` is returned and the original token still works.
16. **Given** any invitation event (sent, accepted, declined, revoked, expired), **when** the audit trail is read, **then** there is exactly one row per event with a masked recipient and no token material.

## 10. Tests

- **Unit:** token generation/hashing/constant-time comparison; join-code alphabet and formatting (round-trip, look-alike rejection); expiry and resend policy; `mask()` for emails and phones; seat-check helper.
- **DB (pgTAP):** cross-workspace isolation on both tables for select/insert/update/delete; the invitee self-select policy returns only rows matching the caller's **verified** identity; no client path can write `status='accepted'`; `app.redeem_invitation` under concurrent calls creates exactly one membership (advisory lock test); the one-active-join-code partial unique holds under concurrent rotation; `app.request_join_with_code` refuses when an active membership already exists.
- **Integration:** every action in §7 with every named error; idempotency-key replay for `sendInvitations`, `requestJoinWithCode` and `rotateJoinCode`; the expiry cron job run twice in a row.
- **E2E (360×800 and 1280×800):** `invite-email-accept-new-user`, `invite-accept-existing-user`, `invite-identity-mismatch`, `invite-revoked-screen`, `join-with-code-then-approve` (two contexts), `rotate-code-invalidates-old`, `guardian-invite-two-children`.
- **A11y:** axe on the invite sheet, the accept screen and the code input; the chips input announces added/removed recipients; the code input is one labelled field, not eight boxes (so screen-reader users can paste).
- **Performance budgets:** `sendInvitations` for 50 recipients completes in ≤ 2 s server-side (rows written synchronously, sends enqueued); `/invite/[token]` TTFB ≤ 400 ms; `lookupJoinCode` ≤ 80 ms.
- **Security:** a test that enumerating 1,000 random codes trips the throttle and yields no information; a Semgrep rule that no log statement includes a variable named `token` or `raw_token`; a test asserting the invitation list DTO has no `token_hash` key.

## 11. Open questions

- **OQ-1: SMS delivery.** Same dependency as F-ID-01 OQ-1 — SMS invitations need a provider that PRODUCT-DECISIONS §7 defers. **Default assumed:** the SMS channel is behind the `invites.sms` feature flag and is hidden until a provider is live; email invitations plus the join code cover launch.
- **OQ-2: invitation expiry lengths.** Not specified in PRODUCT-DECISIONS. **Default assumed:** 14 days for staff, 30 days for guardians.
- **OQ-3: identity substitution.** PRODUCT-DECISIONS does not address a teacher accepting an invitation sent to their old school address. **Default assumed:** allowed for `teacher`/`staff` with a verified email and recorded in the audit row; forbidden for `admin`, `owner` and guardians. Owner to confirm — the stricter alternative (never allow) is one flag away.
- **OQ-4: auto-admit join codes.** `requires_approval` exists but is forced true in v1 (PRODUCT-DECISIONS §1.3b describes approval as the flow). **Default assumed: always approval.**
- **OQ-5: bulk invitation via CSV.** Not in PRODUCT-DECISIONS for members (only for marketplace listings, §4.10). **Default assumed:** the 50-address paste box covers v1; a CSV importer is deferred to the academic area's bulk-admission work, which already needs one.
- **OQ-6: who may invite guardians.** **Default assumed:** owners, admins and the class teacher of the student's section. Academic area owns the "class teacher of" predicate; this spec depends on it existing as `app.is_class_teacher_of(student_id)`.
