## D-01 — Rebuild, do not patch the Base44 export · ACCEPTED (carried over from 2026-09-15) · 2026-09-17

**Why:** The security review shows the tenancy model is anchored to a client-writable field (`active_workspace_id`), 42/64 entities have no RLS, the marketplace has no payment processing, and the audit log is written from the browser. These are design-level, not bug-level. Patching RLS blocks one by one inside Base44 would leave the product dependent on a platform whose server behaviour we cannot see or test. The export stays untouched as the **product reference** (it tells us what was intended); the new app re-implements it.

## D-02 — Runtime stack · PROPOSED · 2026-09-17

**Context:** The 2026-09-15 spec chose a pnpm/Turbo monorepo with a Fastify API, Next.js web, Expo mobile, Tauri desktop, self-hosted Postgres + Redis + S3-compatible storage + SMTP, all via Docker. That skeleton was never run locally (pnpm was never installed, CI never placed, worktree never pushed).

**Recommendation:** **Next.js 15 (App Router) on Vercel + Supabase** (Postgres with RLS, Auth, Storage with signed URLs, Edge Functions for webhooks/jobs, Realtime for messaging/notifications, pg_cron for scheduled jobs). Server-side business rules live in Next.js route handlers / server actions using the Supabase **service role only on the server**, with RLS as the second wall.

**Why this over the Fastify design:**

1. The three non-negotiables of the spec (RLS + server policy + private files) are exactly what Supabase gives natively; the Fastify design would have us re-implement auth, storage signing, migrations tooling and job queues by hand.
2. Zero servers to run. The owner is one person shipping several products (Velora, Bengal Wireless, Nusrat Desire) on the same Vercel + Supabase pattern — operational consistency matters more than architectural purity.
3. Postgres is still Postgres: every RLS policy, trigger and audit function is plain SQL in versioned migrations; nothing locks us in.
4. Redis/queues: replaced by Postgres-backed job tables + pg_cron + Edge Functions, which is enough for print queues, credit renewal and notification fan-out at school scale (thousands, not millions, of rows per tenant).

**What we keep from the previous design:** the monorepo shape (`apps/web`, `packages/domain`, `packages/contracts`), Zod contracts, the role vocabulary, the three-layer authorization rule, the release ordering, tenant-isolation tests as a hard requirement.

**Cost of being wrong:** if the product later needs a long-running service (e.g. a real-time print agent broker), it can be added as a separate service talking to the same Postgres. Nothing in this choice prevents that.

## D-03 — Client scope for v1 · PROPOSED · 2026-09-17

**Recommendation:** Web (installable PWA, mobile-first layouts) only for v1. Expo mobile and the Tauri desktop print agent are deferred to after Release 3.

**Why:** Every feature in the Base44 app is a web feature. Mobile and desktop in the old spec are "boundary only" READMEs. Shipping three clients before one works is how projects die. The PWA covers attendance-on-phone for teachers and the parent portal; browser printing covers the print center until a local agent is justified.

## D-04 — Tenant context comes from the session, never from a client-writable field · ACCEPTED · 2026-09-17

**Why:** Root cause of the whole security review. Implementation: `workspace_members` is the only source of membership; the active workspace is selected per request (header/cookie) and **verified against membership** in a `SECURITY DEFINER` function that every RLS policy calls (`auth_workspace_id()` + `auth_role_in(workspace)`). Role is never read from the `users` row.

## D-05 — Audit events written by the database, not the client · ACCEPTED · 2026-09-17

**Why:** A client can skip a client-side call; it cannot skip a trigger. Every tenant table gets an `audit_events` trigger (actor from `auth.uid()`, before/after diff, correlation id from a request-scoped setting). Table is append-only (no UPDATE/DELETE grants).

## D-06 — Money is never computed in the browser · ACCEPTED · 2026-09-17

**Why:** The Base44 app lets the buyer write `MarketplaceTransaction` and `SellerEarnings` rows with self-chosen amounts and has two disagreeing commission rates. Prices, commission, earnings and entitlements are computed in one server function from a single `platform_settings` row; purchases only become entitlements after a verified payment webhook.

## Amendment to D-22 — Attendance no longer pre-fills present · AMENDED · 2026-09-17

**Amends:** D-22 point 1 (`defaulted_present = true`, pre-fill present + confirm).
**New rule:** Default `unmarked`. "সবাই উপস্থিত / Mark all present" ships as **one explicit header tap writing an audited bulk action** carrying the actor's user id, surfaced in the monthly register. `defaulted_present` is dropped; `bulk_marked_by` / `bulk_marked_at` are recorded instead. The undo toast is retained.
**Why:** A default that fabricates attendance records poisons every downstream number (%, risk score, health score, GPA denominators) and cannot be fixed retroactively once schools rely on the history. Read-back audits catch a bad _action_ fast; a bad _default_ is invisible until it is load-bearing (SYNTHESIS X-01). Priority: R1, before M2 2.4.

**Amends:** D-27 points (1), (2), (3), (8).

**Supersedes:** `ai_actions.min_plan_tier` gating (Free limited to haiku-backed actions).

## D-13 — Native Android + Windows via wrappers around one mobile-first web app · ACCEPTED (owner requirement) · 2026-09-17

**Owner's words:** "this will be a native android and windows app since it's for teachers, so the versions should also support the phone and make the app optimized for the mobile phones so it feels like it was made for a phone."

**Decision:** One codebase. The Next.js app is designed phone-first (bottom tab bar, thumb-reach actions, 44px targets, sheets instead of modals, pull-to-refresh, offline-tolerant attendance). It ships as: (1) installable PWA, (2) **Android via Capacitor** (native shell loading the app, with native plugins for push, camera/QR, file download, share), (3) **Windows via Tauri 2** (native shell + local printer access for the print center). Same screens, same API, same Supabase session.

**Why wrappers, not React Native:** every feature already exists as web UI; RN would mean a second implementation of ~70 screens. Capacitor/Tauri give store-distributable binaries, push notifications and device APIs with one UI codebase. The cost is that some very native gestures won't be present; for a teacher-productivity app that trade is right.

**Sequencing:** the wrappers are added after the web app's Release 1 is green, but every screen is built and tested at 360×800 first from day one.

## D-14 — Git workflow, CI, releases · ACCEPTED (owner requirement) · 2026-09-17

**Owner's words:** "whenever you are working on a major feature push the files and create branches so it doesn't break the app; I need test reports; packages, releases, everything tracked properly."

**Decision:**

- `main` is protected and always deployable. Every feature = branch `feat/<area>-<feature>` → PR → CI green → squash-merge.
- CI on every PR: typecheck, lint, unit tests (Vitest), DB tests against a disposable Postgres (RLS + policy tests), Playwright e2e on a preview build, security scans (dependency audit + secret scan + Semgrep). Test reports are uploaded as PR artifacts and summarized in the PR via a job summary; `docs/test-reports/` keeps a markdown report per feature.
- Releases: Conventional Commits → Changesets → tagged releases `v0.x.y` with generated CHANGELOG; Vercel deploys `main` to production, PRs to previews. Supabase migrations are applied by CI on merge to `main` (never by hand).
- Definition of done per feature (no moving on without all): spec in `docs/features/<feature>.md` ✔ · migrations + RLS tests ✔ · server logic unit-tested ✔ · UI at 360×800 and 1280 ✔ · Playwright journey ✔ · a11y check ✔ · test report ✔ · PR merged ✔.

## D-51 — Audit substrate: generic-trigger actions stay separate from the named catalogue, and correlation id rides a PostgREST pre-request hook · ACCEPTED · 2026-09-17

**Context:** F-ID-09 Part 1 (append-only substrate). Two things the spec left for the builder: (1) the generic trigger `app.tg_audit()` (D-05, shipped in 0003) has always written `<table>.<op>` actions (`workspace_members.update`), while F-ID-09 §5.1's catalogue names business actions (`member.role_changed`) — these do not line up, and acceptance criterion 17 requires every action actually written to exist in `app.audit_action_catalog`. (2) the trigger already read a transaction-local `app.correlation_id` setting, but nothing in the stack ever set it — `supabase-js` talks to PostgREST, which runs one transaction per HTTP request, so a `set_config(..., true)` made by one RPC call cannot be seen by a later `.from().insert()` call in the same server action.
**Decision:** (1) Seed **both** sets into `app.audit_action_catalog`: the curated business actions from §5.1 (for explicit `app.log_audit_event()` calls business logic makes going forward) and a generated `<table>.insert|update|delete` row for every table the trigger is attached to (`GENERIC_AUDIT_TABLES` in `packages/domain/src/audit/catalog.ts`, mirrored in the migration's `v_tables` array and diffed by `scripts/check-audit-catalog-parity.mjs`). `app.log_audit_event()` raises on an uncatalogued action; `app.tg_audit()` defaults a missing lookup to `info` rather than blocking a tenant write. (2) `app.pre_request()`, wired as PostgREST's `db-pre-request` function (`alter role authenticator set pgrst.db_pre_request = 'app.pre_request'`, guarded exactly like the 0001 `pg_cron` block), copies `x-correlation-id` into `app.correlation_id` inside the request's own transaction before RLS runs. `app.set_correlation_id(uuid)` is the explicit fallback for callers outside that path (jobs, webhooks).
**Why:** rejecting every non-catalogued action outright (matching the trigger's real output to the letter) would mean re-deriving ~50 business-meaning actions from raw CRUD before Part 1 could ship at all; separating "what the trigger writes today" from "what business logic will name tomorrow" ships the append-only guarantee now without inventing fake specificity. The pre-request hook is the standard, Supabase-documented mechanism for exactly this per-request-GUC problem — the alternative (thread correlation id as an explicit parameter through every future repository write) would touch every area's migrations, not just this one.
**Consequences:** a future migration that calls `app.attach_audit()` on a new table must also seed that table's three generic rows (`packages/domain/src/audit/catalog.ts` + the migration's `v_tables`) or the CI parity check fails; this is the intended forcing function. CI's disposable Postgres has no `authenticator`-role restrictions matching a locked-down hosted project, so the pre-request wiring is exercised in CI but its _hosted_ behaviour is verified only once against the Supabase dev branch — tracked as a Part 2 follow-up, not blocking Part 1.

## D-52 — F-ID-03 review follow-ups: a removed/pending member is not a forger; the tenant-freeze trigger has exactly one cascade exception · ACCEPTED · 2026-09-24

> Numbering note: D-51 exists on a not-yet-merged PR at the time this entry was written. If D-51 lands first with a different subject, this entry keeps the number D-52 (`DECISION-LOG.md`'s own rule: "numbers are never reused") — the PR that introduced it flags the collision risk for the merge reviewer to confirm before merge.

**Context:** an Opus review of the merged F-ID-03 Parts 1-3 PR (#7) found two related tenancy gaps.

1. `resolveWorkspaceContext`'s header path (`packages/db/src/workspace-context.ts`) treated "no ACTIVE membership row for the candidate workspace" as a single case: fire the `tenancy.context_rejected` forgery tripwire and fail `not_a_member`. But a **removed** member (F-ID-03 §9 AC6) or a **pending** join-by-code applicant replaying a stale `x-workspace-id`/`acadigma_workspace` cookie — most concretely, a second person signing in on a shared phone after the first person's session expired without signing out — hits the exact same code path as a genuine forged-header attack, and gets logged as one: a false audit row lands in the FIRST person's school, naming the second person as a would-be attacker.
2. `public.data_requests.workspace_id` is `on delete set null` (a DSAR must outlive the school it names), but F-ID-03 Part 1's tenant-freeze audit attached `app.tg_freeze_workspace` to that table (closing a real re-parenting gap, D-36's degenerate-role-predicate warning). `ON DELETE SET NULL` is itself an internal UPDATE, so the freeze trigger — an unconditional "`workspace_id` never changes" — fired on that cascade and aborted any hard delete of a workspace with a `data_requests` row.

**Decision:**

- `resolveWorkspaceContext` now runs a second, narrower query — "does the caller have ANY `workspace_members` row for this workspace, in any status" (RLS already lets a user see their own row in every status, F-ID-03 §3) — only when the active-membership check comes back empty on the header path. A row found (removed/pending) fails a new, distinct reason, `membership_inactive`; no row at all fails `not_a_member`. **Both fire the tripwire** (amended after the PR #12 Opus review, see below). `public.log_tenancy_context_rejected` (`20260924020000_tenancy_tripwire_membership_status.sql`) looks up the caller's own membership status server-side and writes it into the row as `membership_status` (`none`/`pending`/`removed`) plus `severity` (`forgery` when `none`, otherwise `inactive`), so alerting can rank them without the row ever being skipped.
- **Amendment (PR #12 review):** the first draft skipped the tripwire for removed/pending callers. Rejected: a `pending` row is one invite code away for anyone (`join_workspace_by_code`), so skipping it would let an outsider probe a school silently, and a removed ex-employee's probes would go unrecorded. The shared-phone false positive that motivated skipping is already fixed at its source by clearing the cookie on sign-in, so the skip bought nothing and weakened AC1. `requireWorkspace()` (`apps/web/lib/workspace.ts`) needed no change — it already renders the same `forbidden()` screen for any reason other than `unauthenticated`, so AC6 ("the removed member sees the no-longer-have-access screen") still holds exactly as before.
- `app.tg_freeze_workspace()` (`20260924010000_tenancy_freeze_cascade_exception.sql`) allows exactly one transition: `old.workspace_id is not null and new.workspace_id is null`, on `public.data_requests` only, and only when `pg_trigger_depth() > 1` — the signature of being invoked from inside another trigger (the FK action's own internal UPDATE), which a direct client statement (`pg_trigger_depth() = 1`) can never produce. Every other re-parent attempt, on every frozen table including `data_requests` itself, still raises `42501`.
- Separately (not a schema/behaviour change, but the same review): the `acadigma_workspace` cookie is now cleared on every path that mints a session for a possibly-different user (`signInWithPassword`, `resetPassword`'s `verifyOtp`, and `/api/auth/callback`'s `verifyOtp`), and `resolveLandingRoute` resolves workspace context with an empty header bag rather than the request's real headers, since middleware has already mirrored a possibly-stale cookie into it before that function runs.

**Why:** a security tripwire that fires on ordinary account lifecycle events (being removed, or replaying a shared device's leftover cookie) trains whoever reads `audit_events` to ignore it — the opposite of what a tripwire is for. A blanket immutability trigger that cannot tell "an attacker re-parenting a tenant row" from "the one FK action the schema itself declares as legitimate" is the same class of bug D-36 already named: correct in the common case, wrong at the one boundary that matters. Distinguishing both narrowly, rather than loosening the general rule, keeps the tenant-freeze invariant intact everywhere except the one place it was never meant to apply.

**Consequences:** `WorkspaceContextFailureReason` gains `membership_inactive`; any future caller that branches on `.reason` (none does today outside `workspace-context.ts` itself) must treat it the same as `not_a_member` unless it specifically wants to show different copy. The freeze-trigger exception is narrow by construction (table name + exact transition + nesting depth) and pgTAP (`supabase/tests/10_tenancy_cascade.sql`) proves both the allowed cascade and that a direct client re-parent is still blocked. `docs/features/01-identity/F-ID-03-workspaces-and-membership.md` §11 records both as deviations from the Part 1-3 build.

## D-54 — Deny function EXECUTE by default in `public`; CI mirrors Supabase's default privileges · ACCEPTED · 2026-09-24

**Context:** Live verification against the production Supabase project `kekfmibwjejdhxjkmezo` (all main migrations applied at the time) showed `has_function_privilege('anon', 'public.switch_workspace(uuid)', 'execute')` returning `true`, despite `20260917020300_tenancy_hardening.sql` §5 granting that function to `authenticated` only. The cause: Supabase provisions every project with `ALTER DEFAULT PRIVILEGES FOR ROLE postgres, supabase_admin IN SCHEMA public GRANT EXECUTE ON FUNCTIONS TO anon, authenticated, service_role`. Every migration's `revoke all on function ... from public` revokes the PUBLIC pseudo-role's grant, not the explicit per-role grant the default already handed to anon/authenticated at `CREATE FUNCTION` time — so the "revoke, then grant back the intended roles" pattern used throughout `identity_auth.sql` and `tenancy_hardening.sql` left the unintended roles granted anyway. Affected: `public.log_auth_event_service` (intended service_role-only — anon/authenticated could forge `account.registered` audit rows with an arbitrary user id, ip and user agent), `public.switch_workspace`, `public.list_my_workspaces`, `public.log_tenancy_context_rejected` (all intended authenticated-only). `log_tenancy_context_rejected` additionally has no `auth.uid() is null` guard, so this was live-exploitable: anon could write a `tenancy.context_rejected` audit row into any workspace with an attacker-chosen `attempted_workspace_id`. CI never caught this because its Postgres 17 service container has no such default, so `has_function_privilege('anon', ...)` pgTAP assertions passed for the wrong reason.

**Opus review of this PR found the first cut was still not deny-by-default for anon:** per-schema default privileges (`... IN SCHEMA public ...`) only _add to_ the role-wide default; Postgres's built-in role-wide default already grants EXECUTE on functions to `PUBLIC`. A future `public` function that skips its own `revoke ... from public` is still anon-callable through that global default even after the schema-scoped fix below, because `PUBLIC` membership is implicit for every role including `anon`.

**Decision:** (1) `supabase/ci/bootstrap.sql` now runs the same `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT EXECUTE ON FUNCTIONS TO anon, authenticated, service_role` Supabase runs on project creation, so CI's grant assertions are false exactly when they would be false live. (2) `20260924030000_revoke_default_function_grants.sql` revokes the mis-granted EXECUTE from the four functions above and, going forward, flips the default itself at **both** levels: the schema-scoped `alter default privileges for role postgres in schema public revoke execute on functions from anon, authenticated` (service_role keeps it), **and** the role-wide `alter default privileges for role postgres revoke execute on functions from public` — closing the gap the review found, since a schema-scoped revoke alone cannot undo a grant to the implicit `PUBLIC` role that every future function still inherits. Every new `public` function is now genuinely deny-by-default and must grant EXECUTE explicitly, or it is uncallable rather than silently open. (3) `supabase/tests/12_function_grants_invariant.sql` asserts the allowlists, the default-ACL shape, **and** (new, from the review) a live probe: it creates a throwaway ungranted function inside the test transaction and asserts anon/authenticated cannot execute it while service_role can — a probe that would have failed before the role-wide revoke, so it actually tests the fix rather than just re-describing it. `log_tenancy_context_rejected`'s missing null-check is NOT fixed in this PR — its body was already being replaced by PR #12 (`fix/tenancy-review-followups`, `20260924020000_tenancy_tripwire_membership_status.sql`, merged as D-52); adding the check here would have conflicted. The grant fix alone closes the PostgREST path; the null-check follow-up belongs to a small PR after both merge.

**Knock-on to test infrastructure:** revoking EXECUTE from `PUBLIC` role-wide also affects pgTAP's own `tests.*` helper functions (`tests.login()`, `tests.logout()`, `tests.mkuser()` — created by `postgres` in each spec, called after `SET ROLE authenticated`), which previously worked only because of the same implicit `PUBLIC` grant this fix removes. `supabase/ci/bootstrap.sql` adds `create schema if not exists tests; alter default privileges for role postgres in schema tests grant execute on functions to public;` (plus `grant usage on schema tests to public`) — test infrastructure only, never shipped to the real project, and safe because per-schema default-privilege entries are additive on top of (never replaced by) the role-wide default, so scoping the grant back to `public` for the `tests` schema alone does not reopen anything in `public`/`app`.

**Two further, lower-priority review findings, same PR:** (a) `12_function_grants_invariant.sql`'s allowlist checks originally filtered to `prosecdef` (SECURITY DEFINER) functions only; dropped, so a future plain SECURITY INVOKER function in `public`/`app` is covered by the same allowlist — every function in both schemas today is already either DEFINER or an already-excluded `app` utility, so this cost nothing to extend. Merging `main` (D-51, D-52) into this PR while making that change surfaced one genuine addition the allowlist needed regardless: `app.pre_request()` (D-51, `20260924000100_audit_substrate.sql` §9), PostgREST's `db-pre-request` hook, must be anon-executable because it runs on every request — including anonymous ones — before RLS; it is now on the A1 allowlist with its rationale inline. (b) `supabase/ci/bootstrap.sql` also mirrors Supabase's default table/sequence privilege (`ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES/SEQUENCES TO anon, authenticated, service_role`) for the same reason as the function one — a table-grant pgTAP assertion in a plain container could otherwise be passing because nothing was ever granted, not because it was explicitly revoked. This PR's test report records whether that surfaced a real table/sequence-grant gap (in which case it is a separate finding, not papered over here) or stayed green.

**Why:** a security boundary that depends on the platform's default privileges silently agreeing with the repo's intent, with nothing testing that they do, is not actually enforced — CLAUDE.md rule 1 ("the database and the server are the security boundary") requires the database layer to be verified, not assumed. A schema-scoped revoke that leaves the role-wide `PUBLIC` grant standing is not deny-by-default, it is a default that still works by accident for exactly the schema this repo audits — the review caught that the fix needed to be provably complete, not merely plausible.
**Consequences:** every future migration that adds a `public` function MUST grant EXECUTE explicitly to whichever of anon/authenticated it intends, or the function is uncallable from the client entirely (service_role is unaffected, and so is anything created inside `supabase/ci/bootstrap.sql`'s `tests` schema). `supabase/tests/README.md` documents the new test file and its probe.

**Why:** two independently-tested, independently-shipped systems claiming to be "the nav" is the exact drift ARCHITECTURE and CLAUDE.md rule 1 exist to prevent — a route guard and a rendered nav item disagreeing about visibility is precisely prototype finding D6 (`module_*` toggles no navigation code read) reappearing at the shell level. Any future caller resolving a workspace's plan for anything beyond its id (billing pages, display) still has `getWorkspacePlan`'s original RLS caveat and must decide for itself whether it needs the full row (and therefore inherits the same non-public-plan `not_found`) or just the id.

## D-59 — `app.tg_workspace_billing_bootstrap()` stops doing a second `UPDATE`, instead of teaching the guard to tolerate one · ACCEPTED · 2026-09-25

**Context:** Confirmed pre-existing bug, found by PR #19's reviews and recorded as Known issue #3 in `docs/test-reports/2026-09-24-F-ID-05-p1.md` and `15_personal_workspace_registration.sql` test 7's comment. `app.tg_workspace_billing_bootstrap()` (`20260917010300_plans_and_notifications.sql`, AFTER INSERT, `SECURITY DEFINER`) set `workspaces.plan_id`/`.trial_ends_at` with a nested `UPDATE public.workspaces ... WHERE id = new.id` against the row it had just inserted. That UPDATE fires `app.tg_workspaces_guard()` (BEFORE UPDATE, latest definition in `20260925000100_personal_workspace_uniqueness.sql`, unchanged from `20260917010100_identity.sql:606-644`), which since `20260917020100_plans_limits_engine.sql` §5b reads the `role` GUC via `app.is_privileged_context()` rather than `current_user` — a deliberate, correct fix for a DIFFERENT false positive (a `SECURITY DEFINER` function's `current_user` becomes its owner, not the real caller, at every nesting depth, which previously disarmed every caller check built on `is_privileged_context()`). PostgREST issues `SET ROLE authenticated` once per request; entering a `SECURITY DEFINER` function does not re-issue that `SET`, so `role` correctly reports `'authenticated'` for the nested UPDATE too. `is_privileged_context()` therefore cannot distinguish "the platform's own bootstrap trigger, running inside the same INSERT statement that just created this row" from "an ordinary authenticated client UPDATE" — both report `role = 'authenticated'` — and the guard's plan/trial check (added for the latter) raised `42501` for both. Consequence: any workspace INSERT made as `authenticated` failed in the bootstrap chain; a school created from the app would fail outright, and F-ID-05 Part 4's planned `app.create_school_workspace()` would hit this on day one.

**Decision:** split `app.tg_workspace_billing_bootstrap()` into two functions rather than teach the guard a `pg_trigger_depth()` exception (D-52's `data_requests` cascade pattern, the alternative option): a new `app.tg_workspace_billing_defaults()`, BEFORE INSERT, sets `NEW.plan_id` (and, for schools, `NEW.trial_ends_at`) directly — no `UPDATE` statement at all. `app.tg_workspaces_guard()` is `before update` only (it reads `OLD`, which does not exist for an INSERT), so a BEFORE INSERT trigger never reaches it — there is nothing left for the guard to see or misclassify. `app.tg_workspace_billing_bootstrap()` itself is narrowed (`create or replace` on the same signature, forward-only per HANDBOOK §1 rule 5) to only what genuinely needs the row to already exist — the school's `subscriptions`/`subscription_events` rows, which reference `new.id` as a foreign key checked immediately at the end of their own INSERT statement, before the outer `workspaces` INSERT has necessarily completed if done any earlier. Migration: `20260925000200_billing_bootstrap_vs_workspace_guard.sql`. Proof: `supabase/tests/16_billing_bootstrap_guard.sql`.

**Why not the guard exception (option a):** would have worked (mirroring D-52 exactly: `pg_trigger_depth() > 1` plus the specific `plan_id`/`trial_ends_at` NULL → bootstrap-value transition a client can never manufacture, since the guard already blocks any client `UPDATE` that would put a row's `plan_id` back into `NULL`), but it is strictly wider than necessary — it teaches a security trigger a new case to reason about, forever, for a problem that has a zero-new-surface fix. Removing the second statement is narrower: nothing is added to the guard's job, and a client's direct `UPDATE` of `plan_id`/`trial_ends_at`/`access_mode` is refused exactly as before — same code path, same message, same errcode (`16_billing_bootstrap_guard.sql` test 2). **Why not a transaction-local flag (option c):** PostgREST lets `authenticated` reach `app.*` only through the `SECURITY DEFINER` surface D-50 already defines, not arbitrary SQL, so a client-forged `set_config('app.bootstrap', 'on', true)` is likely not reachable today — but "likely unreachable" is not a security boundary on its own, and it would still need something to distinguish caller from callee, which is precisely what removing the second statement makes unnecessary.

**Consequences:** the personal-workspace bootstrap now also goes through `app.tg_workspace_billing_defaults()` (previously reached only via `app.handle_new_user()`'s privileged execution context, so it never actually tripped the guard in practice — but it is fixed on the same path regardless, not left as a coincidence). **Not fixed here, same class of bug, flagged for follow-up:** `app.transfer_ownership()` (`20260917010100_identity.sql:785-819`) has the identical shape — a `SECURITY DEFINER` function, callable by a plain `owner` (checked explicitly via `app.member_role`), does a nested `UPDATE public.workspaces SET owner_id = ...`, which would trip the guard's `owner_id` immutability check for the same `role`-GUC reason the moment anything calls it as `authenticated` rather than a privileged role. No `public` wrapper exists for it yet (D-50) and no test exercises it as `authenticated`, so this is untested and latent, not confirmed-broken-in-production — recorded here so whoever wires up ownership transfer checks this decision first instead of rediscovering D-59 from scratch.

**Hardening added on Opus review (same PR, before merge):** `workspaces_insert`'s `WITH CHECK` (`20260925000100_personal_workspace_uniqueness.sql`) constrains `owner_id`/`created_by`/`type` only — it says nothing about `plan_id`/`trial_ends_at`, so a client's own INSERT statement could set either to anything (a paid plan, a decade-long trial). The BEFORE INSERT trigger already overwrote both on every success path, but the failure path — the expected `plans` row missing — did not: `if found then ... end if` around each catalogue lookup meant a missing row silently left `NEW.plan_id`/`NEW.trial_ends_at` exactly as the client supplied them, and for a school that value would then flow straight into the AFTER trigger's `subscriptions` insert as a real trialing subscription on the client's chosen plan. Fixed two ways in `app.tg_workspace_billing_defaults()`: (1) `new.plan_id := null; new.trial_ends_at := null;` unconditionally, as the first statement in the function body, before any lookup — so there is no code path where a client-supplied value can survive; (2) `if not found then raise exception ... using errcode = '22023'` in place of the old silent `if found`, for both the `personal_free` and `pro` lookups — a missing catalogue row is a bootstrap misconfiguration, not a client input problem, and per this repo's own precedent (`app.log_audit_event()`'s uncatalogued-action check, `20260924000100_audit_substrate.sql`) that must abort the transaction loudly rather than produce a row nobody asked for. Both fixes are kept together: clearing alone would still leave a signup silently under-entitled (a workspace with `plan_id is null`); raising alone would still, in principle, depend on no future edit reordering the function ahead of the clear. Proof: `16_billing_bootstrap_guard.sql` — a caller-supplied paid `plan_id` and a decade-long `trial_ends_at` are both overwritten by the bootstrap regardless; and, under a savepoint as the privileged `postgres` role with the `pro` plan row temporarily renamed, the INSERT raises `22023` rather than creating a workspace with client-controlled billing.

**Audit-trail note (Opus review):** moving `plan_id`/`trial_ends_at` from an AFTER INSERT `UPDATE` onto the BEFORE INSERT `NEW` changes what `app.tg_audit()`'s generic trigger records, not just how the guard sees it. Before this PR, the second `UPDATE` statement meant the audit trail carried two rows per workspace creation — a `workspaces.insert` row (without a plan yet) immediately followed by a `workspaces.update` row (recording the plan/trial being set, and bumping `updated_at`). After this PR there is exactly one `workspaces.insert` row, and it already carries the final `plan_id`/`trial_ends_at` in `after` — `updated_at` is never bumped at creation at all, because no UPDATE against `public.workspaces` happens during bootstrap any more. This is a strictly more accurate trail (a workspace was created once, already priced, not created-then-immediately-amended) and is consistent with D-58's existing position that `workspaces.insert` is the row of record for workspace creation; no `app.audit_action_catalog` or `packages/domain/src/audit/catalog.ts` change is needed, since both `workspaces.insert` and `workspaces.update` already exist in the generic-audit catalogue and this only changes which one fires for billing fields, not the catalogue's shape.

## D-60 — `onboarding_progress`'s repository is keyed on `userId`, not `WorkspaceContext` · ACCEPTED · 2026-09-25

**Context:** CLAUDE.md's non-negotiable rule 6 reads "every repository method takes `WorkspaceContext` first." F-ID-05 Part 2's `packages/db/src/repositories/onboarding.ts` (`getOnboardingProgress`, `saveOnboardingDraft`, `markOnboardingComplete`) instead takes `(supabase, userId: string, ...)` — no `WorkspaceContext` argument anywhere in the file. Flagged for a decision entry during PR #24's Opus review rather than left as an undiscussed deviation, the same standard D-58 set for F-ID-05 Part 1.

**Decision:** `onboarding_progress` repository methods are keyed on the caller's own `userId` (the id `auth.getUser()` returned for this request — never client-supplied), not a `WorkspaceContext`. `WorkspaceContext` is not merely omitted; it is unavailable in the paths this table is written from — `resolveWorkspaceContext` requires an existing `workspace_members` row to resolve, and onboarding's whole job (F-ID-05 §2: "Onboarding runs before a role exists") is bridging the gap between "has an account" and "has a workspace worth resolving a context for." The same shape already exists precedent-free in this codebase: `packages/db/src/repositories` has no `user_preferences` or `device_registrations` repository today, but both of those `public` tables (`20260917010100_identity.sql`) are user-scoped exactly this way, and F-ID-03's own `switchWorkspace`/`listMyWorkspaces` actions (`apps/web/app/(shared)/workspace/actions.ts`) are the documented precedent for "there is no `WorkspaceContext` yet — that is the point of these two actions," resolving `userId` from `auth.getUser()` directly instead.

**Why:** the security boundary rule 6 protects is real regardless of the parameter name — every write must be provably scoped to the right tenant/user, never trusting a client-supplied id. `onboarding_progress`'s RLS (`user_id = app.current_user_id()`, class U1 with two deviations, `20260925000300_onboarding_progress.sql`) is that boundary here, exactly as `WorkspaceContext` plus RLS is the boundary for tenant tables; `userId` flows into every repository call from the same trusted source (`supabase.auth.getUser()` in the calling server action, `apps/web/app/(onboarding)/actions.ts`) that `WorkspaceContext` itself is built from downstream of. Inventing a `WorkspaceContext`-shaped wrapper around a user id that has no `workspaceId` to carry would not add a boundary — RLS already provides it — it would only add a type that lies about having tenant scope it does not have.

**Consequences:** a future reviewer scanning `packages/db/src/repositories/*.ts` for "does every exported function's first parameter say `WorkspaceContext`" will find one legitimate exception here (and, if either is ever extracted into `packages/db`, two more precedent-consistent ones in `user_preferences`/`device_registrations`). Rule 6 in CLAUDE.md is not reworded by this entry — it still correctly describes the default and near-universal case; this decision is the recorded exception for the one class of table (§0.3's **user**-scoped group in DATA-MODEL.md) where a `WorkspaceContext` cannot exist by construction, not a precedent for skipping it anywhere a workspace genuinely is resolvable.

## D-63 — F-OP-06 Part 1: staff schema shape, `app.staff_hourly_rate`'s signature, and the `staff_directory` view pattern · ACCEPTED · 2026-09-25

**Context:** F-OP-06 §11 OQ-1 flags "compensation table vs column" as "the single most important call in this feature" and explicitly defers to `DATA-MODEL.md`. `DATA-MODEL.md` §6 already carried a short, pre-spec sketch of `staff_records`/`staff_compensation` (Base44-mirroring columns: `contract_signed`/`id_issued`/`orientation_done`/`system_access`, no `staff_status` lifecycle) and, in §11's illustrative policy-template block, a 3-argument `app.staff_hourly_rate(p_workspace_id, p_user_id, p_on)`. **Decisions:**

1. **`staff_compensation` is a separate table**, confirming OQ-1's own recommendation and `DATA-MODEL.md`'s independent prior lean — RLS is row-level, not column-level, so a `staff_records`-column rate would either be readable by everyone with record access or would force `staff_records` itself to `{owner,admin}`-only, breaking "a teacher sees their own joining date." Exclusion constraint: `exclude using gist (staff_record_id with =, daterange(effective_from, effective_to, '[]') with &&)`, `effective_to` **inclusive** (spec §3.2's own example: a period "ending 30 Sep" and the next "starting 1 Oct" do not overlap only if 30 Sep is included in the first). A `before insert` trigger (`app.tg_close_prior_compensation_period`) closes the previous still-open row to `new.effective_from - 1` for the common forward-dated case; a genuinely overlapping or back-dated insert is left for the exclusion constraint itself to refuse.
2. **`app.staff_hourly_rate(p_workspace_id uuid, p_user_id uuid, p_on date)` — three arguments, matching `DATA-MODEL.md` §11's original sketch, not the 2-argument self-checking signature this entry originally described.** A first draft dropped `p_workspace_id`, resolving the staff record's workspace implicitly from `staff_records.user_id` alone and checking the CALLER'S own standing inline. That is wrong for a person staffed at more than one school (PRODUCT-DECISIONS §7 accepts this as normal): with no workspace filter, the query's `order by effective_from desc limit 1` can pick whichever school's compensation row happens to sort first, silently returning the WRONG school's rate. Restored on lead review (item 9 below) with `p_workspace_id` filtering both the join and the authorization check (`p_user_id = app.current_user_id() or app.has_role(p_workspace_id, '{owner,admin}')` — see item 7 for how that second clause was separately corrected).
3. **`staff_records`' overlapping columns with `workspace_members` are NOT reconciled in this Part.** `staff_records.designation_label_id/department/subject_ids/work_phone` are new, independent columns — this migration does not read, migrate or deprecate `workspace_members.label_id/department/subjects/phone`. Flagged in `F-OP-06-staff-directory-and-records.md` §11 for whichever Part next touches the directory (Part 2) or the record editor (Part 3) to settle.
4. **`staff_directory` is a view with default (definer) privileges, not `security_invoker`.** Every other manually-secured view in this codebase so far (`audit_events_view`) uses `security_invoker = true`, because its job is read-time column redaction UNDER THE SAME row visibility the base table's RLS already grants. `staff_directory`'s job is the opposite — WIDEN visibility beyond `staff_records_select` (owner/admin-or-self) to "every active non-parent member" — so it deliberately omits `security_invoker`, runs with the view owner's (postgres, RLS-exempt-by-ownership) privileges, and re-implements the intended row check itself in its own `WHERE app.has_role(sr.workspace_id, '{owner,admin,teacher,staff}')`, with `security_barrier = true` as insurance against a future added column creating an evaluation-order side channel. This is the first instance of this pattern in the codebase and is recorded here as the template for it, alongside the existing `security_invoker` template for redaction-only views.
5. **`check-audit-catalog-parity.mjs` now scans every file in `supabase/migrations/`, not only `20260924000100_audit_substrate.sql`.** The script hard-coded that one path; `staff_records`/`staff_compensation`/`staff_documents` need `<table>.insert|update|delete` rows in `audit_action_catalog` the same way every other generic-audit table gets them, and the already-applied audit-substrate migration can never be edited to add them (HANDBOOK: forward-only). The script now aggregates every migration's `v_tables text[] := array[...]` block and every `insert into audit_action_catalog ... values ... on conflict` block, and `packages/domain/src/audit/catalog.ts`'s `GENERIC_AUDIT_TABLES` gained the three new table names to match.

CI's `db` job caught this before merge: `custom_labels_base_role_not_parent` (`20260917010100_identity.sql`, pre-existing — `check (base_role <> 'parent')`) rejected the insert, and because the seeding runs inside `app.tg_workspace_bootstrap()` (every workspace's own creation trigger), the failure was not confined to one test — it aborted the fixture setup of every pgTAP file that creates a school workspace, roughly a dozen files across the whole suite, all reported as collateral "Bad plan" failures with zero relation to their own logic. Fixed by dropping the Guardian row rather than touching the pre-existing constraint (out of scope for this Part, and the constraint is arguably correct — permissions come from `base_role`, and a `parent` custom label is not currently a concept this schema supports anywhere else). Caught by CI, not local testing — this laptop has no local Postgres this session (`HANDOFF-2026-09-24.md`), so this trigger body had never actually executed before its first `db` job run.
7. **`app.staff_hourly_rate`'s first draft let any active member of the row's workspace — including a teacher or staff colleague — read the rate, not just owner/admin or the row's own person. A real, confirmed leak, not a false alarm.** The `or app.has_role(sr.workspace_id, '{owner,admin,teacher,staff}')` clause (mirroring `staff_directory`'s intentionally-wide visibility, item 4) was wrong here: `staff_compensation_select`, the RLS policy this function exists specifically to provide a narrower alternative to, never grants a teacher visibility into a colleague's compensation row at all — copying the wider role list onto the function opened exactly the side door the table's own RLS refuses. Caught by CI: `20_staff_schema.sql`'s own `app.staff_hourly_rate never returns a colleague's rate to a teacher` assertion failed against a live Postgres, `have: 45000, want: NULL` (Teacher A querying Teacher A2's real rate and getting it). Fixed to `'{owner,admin}'`, matching `staff_compensation_select` exactly. This is the reason the Part 1 demo's central claim — "a teacher cannot read a colleague's rate by any query" — did not hold before this fix; it holds now, and is the whole reason this function's own pgTAP coverage exists rather than trusting the design read alone.
8. **The three new tables were missing their explicit `revoke all ... from anon, authenticated` — the table-grant equivalent of D-54.** `supabase/ci/bootstrap.sql` mirrors a real Supabase per-project default privilege — `alter default privileges for role postgres in schema public grant all on tables to anon, authenticated, service_role` — so every new table starts with a raw GRANT to `anon` unless a migration explicitly revokes it, the same gap D-54 closed for functions. Every other table in this schema does this (`onboarding_progress`, `platform_settings`, ...); this migration's first draft copied the `grant select, insert, update ... to authenticated` lines without the preceding revoke. Caught by CI: `20_staff_schema.sql`'s `anon has no privileges on staff_records/staff_compensation at all` assertions failed. **Not a data leak** — RLS was already enabled with every policy scoped `to authenticated`, so `anon` (no applicable policy, no `BYPASSRLS`) saw zero rows regardless of the table grant — but it is a real violation of this codebase's grant-hygiene invariant, worth fixing on its own terms rather than arguing RLS alone was sufficient. Fixed: `revoke all on public.staff_records/staff_compensation/staff_documents from anon, authenticated;` added before each table's `grant` line.
9. **`app.staff_hourly_rate` regained its third argument, `p_workspace_id`, on lead review — see item 2's rewrite above.** New pgTAP directly proves AC-30 (a person staffed at two schools, with two different overlapping-date rates, gets back exactly the rate for the workspace they asked about) rather than treating AC-30 as merely "implied" by the general tenant-isolation proof, which is what the Part 1 test report originally — incorrectly — claimed.
10. **`staff_compensation` and `staff_documents` gained a COMPOSITE `(workspace_id, staff_record_id)` foreign key against `staff_records (workspace_id, id)`, replacing a plain single-column FK on `staff_record_id` alone. A real, confirmed cross-tenant write, not a false alarm — BLOCKING lead review.** A plain FK only proves the referenced `staff_records` row exists somewhere, never that it belongs to THIS row's own `workspace_id`. Concretely: an owner/admin of workspace B (anyone can become one — school creation is self-serve) could `insert into staff_compensation (workspace_id, staff_record_id, ...) values (B, <a staff_record_id that actually belongs to workspace A>, ...)` — `staff_compensation_insert`'s RLS only checks `has_role(workspace_id, {owner,admin})` against the INSERTED row's own `workspace_id` (B, which they legitimately own), never that it agrees with the referenced record's real workspace. The row would then insert successfully, `app.tg_close_prior_compensation_period()` would close the REAL School A period sharing that `staff_record_id` (the closing trigger only filters by `staff_record_id`, not `workspace_id`), and `app.staff_hourly_rate` called with `p_workspace_id = B` would return the forged rate for a person who has never worked at School B. `staff_records` gained `constraint staff_records_workspace_id_key unique (workspace_id, id)` (redundant with the PK alone but required as an explicit constraint object for the two tables to reference) as the FK target. Fixed on both tables; proven by pgTAP (`23503` on the forged insert, both tables).
11. **`app.tg_staff_records_self_update_guard()` was rewritten from a deny-list to an allow-list of self-editable columns.** The first draft enumerated admin-only columns (`v_admin_only_cols`) and let anything NOT in that list through — which fails OPEN: a column this migration forgot to list, or a column a FUTURE migration adds to `staff_records` without also touching this trigger, defaults to self-editable. Rewritten to enumerate `v_self_editable_cols` (the genuinely personal fields) and reject every OTHER column (except a small `v_system_cols` set — `id`, `workspace_id`, `created_at`, `created_by`, `updated_at` — that are either immutable or managed by a different trigger; `updated_at` specifically is touched by `app.tg_set_updated_at()` on every update, including a legitimate self-update, and must never be mistaken for an admin-only column). New pgTAP proves the allow-list rejects `designation_label_id` and `joined_on` individually, not only the three columns the original test happened to name.
12. **`staff_documents_insert`'s self-insert branch was missing checks on `verified_by`/`verified_at`/`uploaded_by` — a real security gap, not a false alarm.** A self-inserting teacher could set `verified_by`/`verified_at` to anything (faking their own document as admin-verified) or set `uploaded_by` to someone else's id entirely. Fixed: the self-insert branch of the `with check` now additionally requires `verified_by is null and verified_at is null and uploaded_by = (select app.current_user_id())`; the owner/admin branch is unaffected (they ARE the verifier). Proven by two new pgTAP throws_ok cases.
13. **Bare `app.current_user_id()` calls inside RLS `USING`/`WITH CHECK` clauses wrapped as `(select app.current_user_id())`**, matching this repo's existing convention (a scalar-subquery wrapper lets Postgres cache a `STABLE` function's result once per statement as an initplan, instead of re-evaluating it per row scanned) — six call sites across `staff_records_select`, `staff_records_update_self`, `staff_compensation_select`, `staff_documents_select` and the new `staff_documents_insert` self-insert branch. Left bare inside the two plain-SQL functions (`app.staff_hourly_rate`, `app.can_open_staff_document`), which are single-row lookups, not per-row policy predicates evaluated over a scan.
14. **New indexes from lead review:** `staff_compensation (workspace_id)`, `staff_documents (workspace_id)` (a full index alongside the existing `(workspace_id, expires_on) where expires_on is not null` partial one), `staff_records (user_id, workspace_id)` (the reverse column order of `staff_records_workspace_user_key`, for "which of my records, in which school" when a person holds more than one).
15. **The allow-list guard's own `v_system_cols` skip-list still let `created_by`/`created_at` through unchecked — a real gap in item 11's fix, found on a security re-check of the fix itself.** Rewriting the guard from a deny-list to an allow-list (item 11) is only as safe as the small "never checked either way" system-column list sitting outside both lists — and that list originally named `created_by`/`created_at` alongside `id`/`workspace_id`/`updated_at`, on the reasoning that all three are "system-managed." `id` and `workspace_id` genuinely are (immutable, and separately frozen); `updated_at` genuinely is (touched by `app.tg_set_updated_at()` on every legitimate update, so it must stay skipped or every harmless self-update would false-trip the guard). `created_by`/`created_at` are NOT system-managed after insert — nothing else protects them from a client `UPDATE`, so skipping them meant a self-updating member could rewrite their own record's provenance (who created it, when) in the same statement that legitimately touched their phone number. Fixed: removed from `v_system_cols`, so both now fall through to the ordinary allow-list check like any other column (neither is in `v_self_editable_cols`, so any change by a non-admin is rejected). Proven by two new pgTAP cases using the 4-arg `throws_ok` form with the exact pinned exception message, not just the errcode.
16. **`app.staff_hourly_rate`'s third parameter is named `p_on`, not `p_on_date` — a forced rename, not a style choice.** An M0 stub of this exact function already exists — `20260917010000_extensions_and_app_schema.sql` §6, applied to `main` long before F-OP-06 Part 1, signature `app.staff_hourly_rate(p_workspace_id uuid, p_user_id uuid, p_on date)`, with a body written against a `staff_compensation` shape (`user_id`/`valid_from`/`valid_to`) that never actually shipped that way. This migration's own `create or replace function app.staff_hourly_rate(...)` is what gives the stub its real, working body — Postgres refuses a `CREATE OR REPLACE FUNCTION` that renames an EXISTING parameter (`cannot change name of input parameter "p_on"`), caught by CI (`db` job, run 36061148429) on `p_on_date`. The alternative — `DROP FUNCTION` then `CREATE FUNCTION` under the preferred name — was explicitly rejected: a drop discards the function's existing grants and would break any (even latent, not-yet-built) dependent that already resolves it by OID. Fixed by reverting the parameter name to `p_on` throughout (signature, body, comment) — everywhere else in this migration and its docs, callers already used purely positional arguments, so no test or TS call site needed a matching rename.

**Why:** all four schema/function calls in items 1-4 are the direct, narrow answers OQ-1 and DATA-MODEL.md's own sketch left open; none is speculative — each is required for the Part 1 demo ("a teacher can read their own record and their own rate, cannot read a colleague's rate by any query, and `app.staff_hourly_rate` returns the rate in force on a past date") to be true. Item 3 is a deliberate non-decision, recorded so the duplication is visible rather than silently repeated. Items 6-16 are all fixes found by CI (and, for 9-16, one or more subsequent lead/security reviews) rather than by local testing — this laptop had no local Postgres available this session (`HANDOFF-2026-09-24.md`), so this migration's trigger and function bodies ran against a real Postgres for the first time only inside CI, and each review read the actual shipped SQL rather than re-trusting the design narrative — including, in item 15's case, re-checking the PREVIOUS review's own fix rather than assuming it was complete, and in item 16's case, CI catching a collision with a pre-existing M0 stub this Part's author did not know existed until the error named it.

**Consequences:** `DATA-MODEL.md` §6 is rewritten to match the shipped schema (columns, RLS, indexes, the corrected function signature) in this PR. `workspace_members.label_id/department/subjects/phone` remain live, unused by this feature, until a future Part reconciles them — a directory screen built carelessly against `workspace_members` instead of `staff_directory`/`staff_records` would show stale or duplicate data; Part 2 must read from `staff_directory`. `check-audit-catalog-parity.mjs`'s new multi-file scan is a superset of its old behaviour (unchanged result for every migration before this one) and is itself exercised by this PR passing. ## D-66 — EIIN availability is a partial unique index plus a boolean-only SECURITY DEFINER probe, checked ahead of the school-creation transaction · ACCEPTED · 2026-09-25

**Context:** F-ID-05 §4.3 step 1 must tell the user, before they ever reach the final "Create school" button, whether an EIIN they typed already belongs to another school (AC6: "an inline error names the collision ... the wizard does not advance"). §5 separately states "EIIN ... unique across the platform." Part 3 (this PR) builds only steps 1-2 of the wizard — the actual `app.create_school_workspace()` transaction that would otherwise raise `EIIN_TAKEN` is Part 4's, not yet built — so step 1's own Continue button had no enforcement to check against at all. `school_profiles`' RLS (DATA-MODEL.md §1.3, class T2) only lets an active member of a school read its row; a caller filling in the wizard is a member of nothing yet, so there is no RLS path to "does another school already have this EIIN" for any school, including the one that collides.

**Decision:** `20260925000700_school_eiin_availability.sql` adds two things, both scoped narrowly to the read-only availability question this Part actually needs:

1. `school_profiles_eiin_unique`, a partial unique index (`where eiin is not null`) — the real enforcement, and the same constraint Part 4's `app.create_school_workspace()` will eventually catch (`23505`) and translate to `EIIN_TAKEN`. A client-side probe alone cannot prevent a race between two concurrent submissions; only a database constraint can.
2. `public.check_eiin_available(eiin text) returns boolean`, a `SECURITY DEFINER` function (with an `app.eiin_is_available()` inner helper, matching this codebase's `public` = PostgREST-reachable / `app` = server-internal split, D-50) that answers the one boolean question without exposing which school holds the EIIN or any other column. Granted to `authenticated` only — unlike `public.throttle_status` and its siblings (§1.8a), this surface is reachable only after sign-in and email verification (F-ID-05 §2), so there is no pre-session case for `anon` to reach it.

**Why not defer this to Part 4:** the alternative was building an EIIN-collision check nobody could see until the whole five-step wizard existed, silently violating AC6 and §4.3's "step 1 ... does not advance" for the length of an entire Part. The index and the probe are both narrowly scoped to the read-only question Part 3 owns; neither creates a workspace, seeds any row, or reaches into territory Part 4's brief reserves (`app.create_school_workspace`, grade levels, academic years, the trial). Building the index now, rather than when Part 4 lands, also means Part 4 never has to choose between "does the uniqueness constraint already exist" and "am I the one who adds it" — it exists once, here, and Part 4's transaction only has to handle the `23505` it can already produce.

**Why a SECURITY DEFINER boolean probe, not a widened RLS policy:** widening `school_profiles_select` to let any authenticated caller read `eiin` (or any other column) across every school would leak far more than this one field asks for, permanently, for every future caller of that policy — not just the wizard's one pre-submit check. A function that answers exactly one boolean question, and nothing else, is the narrower and more reversible surface; it is also the pattern this codebase already uses for the same shape of problem (`public.throttle_status`, `public.list_my_workspaces`).

**Consequences:** `packages/db/src/repositories/school.ts` (`checkEiinAvailability`) and `apps/web/app/(onboarding)/actions.ts`'s `checkEiinAvailability` action are the only callers today. `supabase/tests/12_function_grants_invariant.sql`'s `authenticated` allowlist and `22_school_eiin_availability.sql` (new) both assert the grant shape. If a future Part needs to answer a richer "why is this EIIN taken" question (e.g. "is it yours"), that is a new, separately-considered surface — this one stays boolean-only on purpose.

## D-69 — Four parallel lanes with per-lane number ranges; only the lead merges · ACCEPTED · 2026-09-25

**Context:** Two builders working at once had already collided twice: both picked the same next decision number, and one PR's migration was written against a timestamp another PR's (already-merged) migration had since made stale — `supabase db push` refuses a migration dated before the newest one already applied. With more than one builder running concurrently, an unordered shared decision-number sequence and an unordered shared migration timestamp are both races with no lock.

**Decision (owner decision, 2026-09-25):** the build runs as four parallel lanes plus the lead, each with its own reserved decision-number range and pgTAP file-number range, so two lanes can never collide on those by construction. Migration timestamps are **not** lane-scoped — a lane digit fixed at write time would make a lane-1 migration always sort before a lane-3 one on the same day regardless of which PR actually merged first, forcing a re-date on almost every merge. Instead every migration is timestamped with the real UTC time it is written (`date -u +%Y%m%d%H%M%S`), which sorts correctly in the overwhelmingly common case on its own; `scripts/check-migrations-order.mjs` (D-70) is the mechanical backstop for the rare case where a lane's migration still falls behind another lane's between being written and being merged.

- **Identity and onboarding** (lane 1) — `(auth)`, `(onboarding)`, identity packages, F-ID-\* specs.
- **Operations** (lane 2) — `(school)/app/{staff,settings,...}`, F-OP-06/F-OP-07, F-ID-07 notifications.
- **Billing** (lane 3) — billing, plans/limits, access mode, F-CM-\* specs; `requireWritable` on every write path is first, due before mid-October.
- **Design** (lane 4) — tokens and theme in `packages/ui`, brand components, `DESIGN-SYSTEM.md`, icons/OG assets; D-68 visual refinement and product logos first.
- **Lead** (lane 0) — CI, releases, migration order, docs index, reviews, merges; process and infrastructure changes only.

The exact ranges, queue order and merge rules are recorded once, in `docs/plan/LANES.md`, not duplicated here — this entry is the decision to run lanes at all and why. Only the lead merges, one PR at a time, and confirms the live deploy and smoke test before merging the next PR when a merge carries a migration.

**Why:** the two collisions already happened, on real PRs, in the same week lanes were introduced — this is a fix for an observed failure mode, not a speculative one. A per-lane reserved range is the cheapest fix that removes the race by construction rather than by discipline: no lane has to check what another lane is doing before picking a number, because the ranges never overlap. `docs/plan/LANES.md` is the single place the ranges live so they are never redefined inconsistently in two documents.

**Consequences:** lanes still merge in whatever order they finish, so a lane's real-time migration timestamp can still fall behind another lane's between when it was written and when it merges — `scripts/check-migrations-order.mjs` (D-70) catches that and the lane renames the file with `git mv`. `docs/plan/BUILDER-BRIEF.md` is the brief every lane builder reads before starting a Part, and links to `LANES.md` for the ranges. A lane that needs a number outside its own range (a genuine cross-lane decision) takes it from the lead's range (D-69 to D-99) instead, recorded as a lead decision. The lead also now keeps `docs/plan/BUILD-LOG.md`, a dated running log of every merged PR (what shipped, decisions, migrations applied to production, deploy/smoke-test result, review findings), appended after each merge — with four lanes merging independently, this is the one place that stays a single, ordered account of what actually happened, rather than four lanes' worth of PR descriptions someone has to reassemble later.

## D-70 — Cut CI and Vercel usage with free options · ACCEPTED · 2026-09-25

**Context (owner request, 2026-09-25):** with four lanes running builders concurrently, CI and Vercel usage rises with them. The owner asked for CI and Vercel usage to be cut using free options only, no new paid tier.

**Decision:** three changes, all free-tier:

1. **`scripts/check-migrations-order.mjs`** (new): fails CI when any migration added in a PR (compared to the merge-base with `origin/main`) has a filename timestamp at or before the newest migration timestamp already on `main`, printing a `::error` naming the offending file and a suggested new name that sorts after it — the current UTC time, or one second past main's newest if that isn't later (D-69: migration timestamps are real UTC time, not lane-scoped, so there is no lane digit or sequence number to reason about here). Wired into `ci.yml`'s `db` job, next to `check-migrations-append-only.mjs`, same job so it shares that step's `fetch-depth: 0` checkout. This is the mechanical backstop for D-69's real-time migration timestamps — real time sorts correctly on its own in the common case, this catches the rare case where a lane's PR falls behind because another lane merged a later migration first.
2. **`ci.yml` job skipping via a new `changes` job, fail-closed by construction:** computes `db` (`true` only when `supabase/**` or `.github/**` — workflows, actions, dependabot, everything — changed: the narrow, expensive-job case) and `app` (`false` only when _every_ changed file matches a narrow docs/prose/dotfile allowlist: the broad, default-on case) from `git diff --no-renames --name-only <base>...HEAD` — no third-party action, `--no-renames` so a code file renamed into `docs/` still shows its old path and isn't misread as docs-only. On `push` to `main` and on `merge_group` both are forced true (a full run — `merge_group` is never partial). `db` runs unless its output is the literal string `'false'`; `lint`/`typecheck`/`unit`/`contracts`/`build`/`security` run unless _both_ outputs are `'false'`; `e2e`/`lighthouse` run on `pull_request` (not draft) and on `merge_group`, never on `push` to `main`, under the same not-`'false'` rule. Every one of those `if` conditions is prefixed with `!cancelled()`: GitHub silently ANDs an implicit `success()` across every job in `needs` unless the expression contains a status-check function, so without it a `db` job that is legitimately `'skipped'` would still take `e2e` down with it regardless of what the rest of the condition said (actions/runner#491) — `!cancelled()` removes that implicit gate so the written condition, not GitHub's default, decides. A skipped job reports as passing to GitHub, so required checks stay green; `CI / changes` is itself added to the required-checks list (CI.md §3) specifically so a broken `changes` job blocks the merge instead of silently costing everyone a full, unskippable run. `changeset`, `docs-sync`, `report` and `guard` are unchanged in intent; `report` (`if: always()`) still resolves correctly against a mix of skipped and run `needs`.
3. **Vercel builds only `main`:** `apps/web/vercel.json` gets `"ignoreCommand": "[ \"$VERCEL_GIT_COMMIT_REF\" != \"main\" ]"` (exit 0 skips the build), so PR previews are dropped entirely. `CI / build` already proves the app builds on every PR; the Vercel PR check now shows as skipped/canceled and was never a required check.

**Rejected options, with reasons:**

- **A self-hosted runner on the owner's PC**, to move CI compute off GitHub's shared runners: rejected. The repo is public (D-64), so a self-hosted runner would let a fork PR's workflow run arbitrary code on the owner's own machine — GitHub's own documented warning against self-hosted runners on public repos. It would also need Docker, and Docker's default data root is on `C:`, which is already full (the same constraint every builder already works around with `TMP`/`TEMP`/`TMPDIR` on `F:`).
- **Local pgTAP**, to move the `db` job's Postgres service container off Actions minutes entirely: rejected for the same reason CI.md §6 already gives for not having per-PR Supabase branches — it needs Docker or the Supabase local stack, and the dev machine has no Docker (§6: "The dev machine also has no Docker, so there is no per-PR local database either").
- **Note, not a change:** GitHub Actions minutes are already free and unlimited on this public repo (D-64 item 1) — the real limit `changes`-job skipping addresses is the shared ~20 concurrent-job queue across four lanes' PRs running at once, not minutes. `cancel-in-progress` was already present in both `ci.yml` and `db.yml` before this PR (`true` on `pull_request`, `false` on `main`/pushed migrations) — not added by this decision, carried over unchanged.

**Why:** all three changes reduce actual usage (concurrent job count, Vercel build count) rather than working around a quota after the fact. Honestly: the skip logic does not weaken a merge gate _by design_, but that design is only as good as the `changes` job's own correctness — a bug in its diff logic that wrongly reports `app=false`/`db=false` would skip real gates and still show green. The mitigations are the fail-closed defaults themselves (§2: `app` defaults true, `db`'s skip requires a specific narrow pattern, and any unset/errored output reads as "run" downstream because every comparison is `!= 'false'`, never `== 'true'`) plus making `CI / changes` a required check (§3), so a `changes` job that errors outright is a red, blocking check rather than a silent full-permissive run. A docs-only PR skipping `e2e`/`lighthouse`/`build` is exactly what those jobs would have reported anyway (no app code changed to break), and the migration-order check is a net new gate, not a relaxed one.

**An honest gap this PR does not close:** `main` currently has **no branch protection at all** (verified via `gh api repos/Mahadezz/acadigma-campus/branches/main/protection`, 2026-09-25 → `404 Branch not protected`). CI.md §3's required-checks list, including the new `CI / changes` entry above, is therefore the _documented contract_ CI implements, not an _enforced_ one yet — nothing today stops a force-push or branch deletion, and nothing requires any of these checks to pass before a merge. Turning on branch protection (required status checks, no force-push, no deletion, the settings already itemised in CI.md §3) is an owner action, not something this PR does unilaterally to the shared repository's protection settings. Required-status-checks enforcement is deferred specifically until `release.yml`'s changesets "version packages" PR (D-64 item 3: Actions can open/approve PRs) itself has a passing `CI` run to point at — turning on enforcement before that PR-flow is proven green would risk locking the release process out of its own repository.

**Consequences:** this PR itself touches `.github/workflows/**`, so its own `changes` job reports `db=true` and every job runs — expected, not a bug. A future PR that touches only `docs/**` will show `lint`/`typecheck`/`unit`/`contracts`/`build`/`security`/`e2e`/`lighthouse` as skipped and still merge, since GitHub treats a skipped required check as passing. Vercel PR previews no longer exist; a lane builder makes screenshots locally with Playwright instead (`docs/plan/LANES.md`, `docs/plan/BUILDER-BRIEF.md`). `docs/engineering/CI.md` §2.3, §3 and its generated-types section are updated in this PR to document the skip rules, the migration-order check and the re-date procedure.

## D-300 — Read-only mode refuses every tenant write, in the server action and in the database · ACCEPTED · 2026-09-25

**Context:** D-29 put read-only mode in `workspaces.access_mode`, checked by server actions (`PLAN_READ_ONLY`), and DATA-MODEL §1.2 kept it out of RLS. D-62 made trial expiry set it. But no server action called `requireWritable`, a member's direct PostgREST write skipped the check entirely, and D-62/the shell banner described the mode as "only creates are blocked" while D-29 and DATA-MODEL say "any write". The lead's lane brief (LANES, billing queue item 1) asks for enforcement on every write path before mid-October.

**Decision:** (1) `read_only` refuses every tenant write — create, update and delete. Reads, exports, billing/upgrade, sign-out, workspace switching and the individual's own records stay available. (2) Every tenant write server action calls `requireWritable` after the policy check (parse → context → policy → **writable** → repo) and returns `err(planReadOnlyApiError(...))`: `payment_required` (402), the reason plus "Upgrade to make changes — you can still view and export everything, and nothing has been deleted." The shell banner shows the same sentence. (3) Defence in depth is one shared `security definer` BEFORE INSERT/UPDATE/DELETE row trigger, `app.tg_require_writable()`, on every tenant table — not an RLS predicate. It exempts `app.is_privileged_context()` and `app.is_platform_admin()`, so the billing tick and `app.set_access_mode(..., 'normal')` always work. (4) CI: `scripts/check-require-writable.mjs` (contracts job) fails a write server action or `POST/PUT/PATCH/DELETE` route that resolves a workspace context without calling `requireWritable`; a name starting with a read verb counts as a read. `supabase/tests/50_require_writable.sql` fails any `workspace_id` table without the trigger that is not on its exempt list.

**Why:** A trigger touches only writes, so DATA-MODEL's objections to RLS (per-row cost on every read, a billing bug hiding in a hundred policies) do not apply. It also covers SECURITY DEFINER RPCs, because `is_privileged_context()` reads the caller's `role` GUC at any nesting depth. A catalog invariant and a source scan are the two places a future table or action cannot quietly skip. Reusing `payment_required` avoids widening the shared `ApiError` enum that every lane's actions return.

**Consequences:** D-62's "allow everything else" and the banner's "edits and deletes still work" are superseded (F-CM-06 §11 updated). Every lane's new write action and every new tenant table must add the guard (CLAUDE.md rule). Exempt tables and their reasons are listed in DATA-MODEL §1.2 and `50_require_writable.sql`. **Review follow-ups (PR #35):** removing access stays possible in read_only — a membership set to `removed`, a capability deleted/revoked, an invitation revoked or declined — while their siblings (role change, grant, invitation edit) are refused. The trigger raises only for an active member (and, generically, for a non-member's membership INSERT), so a stranger never learns the workspace's `access_mode_reason`. Triggers are attached through `app.attach_require_writable()`; the three F-OP-06 staff tables are guarded. The action check is file-level and fail-closed: an action guarded through a same-file helper passes, one that skips it fails.

**Owner's answers (2026-09-25):** leaving a read-only school — **allowed**; the leave RPC does not exist yet, and when it lands the trigger gains its exception (self status → `removed`). Accepting an invitation to a read-only school — **refused**, "ask the owner to upgrade". §5.6 delete-to-get-under-a-limit — **not** for read_only; that is the `LIMIT_EXCEEDED` path only.
