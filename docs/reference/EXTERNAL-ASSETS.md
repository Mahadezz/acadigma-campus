## 3. Security checklist from the login/security docs

Source: "5 Security Holes in Your Vibe-Coded App's Login Screen." Mapped to Acadigma's actual surfaces — Supabase Auth (multi-tenant: school owner / teacher / parent / student roles), SSLCommerz payments, and file uploads (marketplace digital resources, resource library). Feed this raw list to the handbook agent writing `docs/engineering/SECURITY.md`; it complements (does not replace) the offensive-* skill checklists already covered in TOOLING-AND-REFERENCES.md.

1. **Session token storage.** Confirm the Next.js app uses `@supabase/ssr` so the session lives in an `httpOnly`, `Secure`, `SameSite=Lax` cookie — never `window.localStorage`. Any custom client-side auth code (e.g. a mobile/Capacitor bridge later) must not read/write the token to storage accessible from JS. Verify in DevTools → Application → no auth token under Local Storage.
2. **Server-side authorization, every time.** Every API route / server action that changes data (enroll student, approve marketplace listing, issue AI credits, post job listing, approve payout) must re-check the caller's role from the server session — never trust a client-supplied role/tenant flag. Pair every such check with a matching Supabase RLS policy so the DB enforces it even if a route is missed. This is the same root issue the already-installed `offensive-idor`/`offensive-business-logic` skills test for — use this as the _prevention_ checklist, those as the _verification_ checklist.
3. **Email verification (and 2FA for high-privilege roles).** Block unverified users from write/sensitive actions — check `email_confirmed_at` server-side, not just at signup. Given Acadigma handles school finances (marketplace payouts, SSLCommerz) and student data, require verified email before a school-owner or finance-role account can approve payouts or change payment settings; consider mandatory 2FA for school-owner/admin roles specifically (not necessarily teacher/parent/student).
4. **Rate limiting on auth AND on money/spam surfaces.** Apply Supabase Auth's built-in rate limits (or Upstash Ratelimit middleware) to login/signup/password-reset (e.g. 5 attempts/15 min per IP+email). Extend the same pattern to: marketplace checkout attempts, SSLCommerz webhook retries/replay, hiring job-application submissions, and AI lesson-plan generation requests (credit-abuse vector) — brute force and abuse risk isn't limited to login.
5. **Password policy + breach check.** Enforce minimum length 12 and HaveIBeenPwned/leaked-password rejection via Supabase Auth settings, with a clear strength error in the sign-up UI. Applies to every role that self-registers (teachers, parents signing up independently, marketplace sellers).
6. **File upload surface (cross-referenced, not from this doc but flagged while mapping the checklist to our stack).** Marketplace digital-resource uploads and the resource library are exactly the surface the already-installed `offensive-file-upload` skill targets (MIME/extension bypass, SVG/HTML stored XSS, path traversal) — make sure the SECURITY.md handbook explicitly cross-links prevention controls (Supabase Storage signed URLs, content-type allowlist, virus/format validation before publish) to that checklist rather than treating upload security as covered by login-hardening alone.

## 4. Performance prompt pack / collaboration / secret-codes takeaways

**Performance (App Performance Prompt Pack — apply where relevant, test after each one individually, don't stack untested changes):**

- Enable gzip/brotli on API responses above a small size threshold (Vercel edge / Next.js route handlers) — check `Accept-Encoding` negotiation, watch for double-compressing already-compressed payloads (e.g. images, already-gzipped SSLCommerz webhook bodies).
- Batch inserts/updates: audit any loop that does per-row Supabase writes (bulk enrollment import, bulk marketplace listing seed, bulk grade entry) and replace with multi-row inserts/batched updates inside a transaction, chunked to avoid oversized statements.
- Circuit breaker for slow external dependencies: SSLCommerz payment calls, courier/notification webhooks, and the AI lesson-planning LLM call are exactly the "external dependency that could cascade" case — add timeouts + limited concurrency + fast-fail/fallback so a slow SSLCommerz or LLM response doesn't exhaust the app's connection pool.
- Optimistic UI updates for low-risk, high-frequency actions (marking attendance, liking/saving a resource, toggling a lesson-plan draft) — instant UI update, reconcile with server, roll back with visible error on failure. Do **not** apply this to payment or credit-spend actions where the server must be the source of truth before the UI commits.
- Cache rendered pages/fragments that are identical across tenants or change rarely (marketplace category listings, public school directory pages, lesson-plan templates) while keeping tenant-specific regions dynamic; cache keys must account for tenant/locale.

**AI collaboration field guide (apply as lightweight process, not new tooling):**

- Keep `docs/decisions` capturing _why_, not just _what_ — it already exists in this repo; keep using it per-feature.
- Before implementing anything non-trivial, state the plan/assumptions first (catches bad reasoning at paragraph stage, not after 200 lines) — reinforced by the newly installed `karpathy-guidelines` skill.
- One logical change per request/session; read every diff; end sessions with a short handoff note (what's done, what's left, what to watch out for) — cheap habit, highest leverage per the guide.
- Own the mental model: if the change can't be explained in your own words, it isn't ready to accept regardless of how much documentation surrounds it.

**Claude Secret Codes:** no adoption — see IGNORE entry above. The underlying prompting techniques it repackages (pre-mortem, red-team a plan, ELI5, layered depth) are already achievable in plain language and several are already served by real installed skills (`security-review`, `brainstorming`, `/code-review`).
