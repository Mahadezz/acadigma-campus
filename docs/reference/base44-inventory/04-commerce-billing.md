## 1. Area summary — what the owner was trying to build

### The marketplace concept

A **teacher-to-teacher marketplace for downloadable academic files** (a Teachers-Pay-Teachers clone localised to Bangladesh).

- **Who sells:** individual teachers ("Academic Publishers"), gated on identity verification. `canSell()` at `src/pages/marketplace/MarketplaceConstants.jsx:44-46` restricts selling to role `teacher`. `PERMISSIONS.marketplace_sell = ['teacher']` (`src/lib/permissions.js:61`). A parallel, newer path exists: `user.account_type === 'seller'` / `user.has_seller_profile` (`src/pages/seller/Dashboard.jsx:13`, `src/pages/seller/Listings.jsx:12`) with its own `workspace_type: 'seller'` workspace (`SchoolSettings.workspace_type` enum) and its own sidebar/layout (`SellerSidebar.jsx`, `SellerLayout.jsx`).
- **What they sell:** digital files only. 15 resource types (`MarketplaceConstants.jsx:3-7`): worksheet, exam_paper, quiz, class_test, homework, notes, presentation, lab_sheet, project_work, resource_pack, book, thesis, question_bank, assignment, handout. Upload is a single "main file" (PDF/DOC/DOCX/PPT/PPTX/ZIP/XLSX — `ListingForm.jsx:145`) + cover image + up to 3 preview pages. Nothing is print-ready/POD; there is no physical fulfilment anywhere.
- **Who buys:** any logged-in user (`/marketplace` route is unguarded — `src/App.jsx:136`). `PERMISSIONS.marketplace_buy = ['superadmin','admin','teacher']` (`permissions.js:60`) is defined but **never enforced**.
- **Delivery on purchase:** the listing's `main_file_url` is copied into an `AcademicResource` row in the buyer's workspace with `source: 'marketplace_purchase'` (`ListingDetail.jsx:97-113`), and a "Download Resource" button opens the raw URL (`ListingDetail.jsx:249`, `:258`).
- **Two funding modes:** _Personal_ (teacher pays themselves) vs _School Funded_ (request → school admin approval). Toggle at `ListingDetail.jsx:268-274`.

### Subscription / plan model

Two **incompatible** models coexist:

| Model                        | Where                                      | Shape                                                                                                                                                                                                                                     |
| ---------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per-teacher seat pricing     | `base44/entities/SchoolSubscription.jsonc` | `plan_name` free-text (schema example: `"6-10 Teachers"`), `teacher_count_min/max`, `monthly_cost_per_teacher` (BDT), `total_monthly_cost` (BDT), billing cycle dates, status `active\|overdue\|cancelled\|trial`, `auto_billing_enabled` |
| Named tiers on the workspace | `base44/entities/SchoolSettings.jsonc`     | `subscription_plan` enum `free\|starter\|pro\|enterprise`, `subscription_status` enum `trial\|active\|expired\|cancelled`                                                                                                                 |

**No prices exist anywhere in the code for either model.** No pricing page, no plan picker, no upgrade flow. Every signup path hardcodes `subscription_status: 'trial'`, `subscription_plan: 'free'` (`src/pages/Welcome.jsx:142-143, 183-184, 213-214`; `src/components/auth/TeacherRegister.jsx:99-100`; `src/components/auth/SellerRegister.jsx:77-78`; `src/components/personal/BecomeSellerModal.jsx:78-79`). Nothing ever moves a workspace off `trial`/`free`. No trial length, no expiry check, no gate keyed to plan.

### Currency

**BDT (৳) throughout.** `MarketplaceTransaction.currency` defaults to `"BDT"`; `MarketplaceListing.price` documented as "BDT — 0 = free"; every money field in `SchoolSubscription`, `BillingRecord`, `ManualExpense`, `AIUsageLog.cost_generated`, `PayrollImpactLog` is annotated BDT; every UI amount is rendered `৳ {n.toLocaleString()}`. The only USD leak is the CSV bulk-upload template sample price `"5.00"` (`BulkListingUpload.jsx:13`) and Lucide `DollarSign` icons.

### Payment providers named in UI

- **SSLCommerz** and **Stripe** — the only two, as a `PaymentMethod.provider` enum and a dropdown (`PaymentMethodsPanel.jsx:14-17`). UI copy: _"Secure payment via SSLCommerz / Stripe"_ (`ListingDetail.jsx:264`).
- **bKash / Nagad / bank transfer** — offered as seller **payout** rails in the Become-a-Seller wizard (`BecomeSellerModal.jsx:207-233`). Collected then thrown away (see §7).
- No SDK, no API key, no redirect, no webhook, no edge function anywhere in the repo. `base44.integrations.Core.*` is only ever used for `UploadFile` and `ExtractDataFromUploadedFile`.

## 2. Data model as implemented

All entities live in `base44/entities/*.jsonc`. **Tenancy note:** this area is split between two tenancy conventions — marketplace/seller entities are keyed on `user_id`/`seller_id` (global, cross-tenant by design), while billing entities are keyed on `school_id`. `useSchool()` exposes `activeWorkspaceId`, but **only `ListingDetail.jsx:98` uses it**; every billing writer instead uses `user?.school_id || 'default'` — and `school_id` is **not a field on the User entity** (`base44/entities/User.jsonc`), so every such write lands on the literal string `'default'`.

### Marketplace

**MarketplaceListing** — a sellable file.
`seller_id` (FK User, required), `title` (req), `description`, `subject`, `grade_level`, `curriculum`, `language` (default `English`), `resource_type` (req, enum of 15), `price` (number, **BDT, default 0 = free**), `cover_image_url`, `main_file_url`, `preview_page_urls` (**string** holding a JSON array of ≤3 URLs), `status` (enum `draft|pending_review|approved|published|rejected|revision_requested`, default `draft`), `rejection_reason`, `revision_notes`, `view_count`, `total_sales`, `total_revenue_gross` (money, BDT), `rating_average`, `review_count`, `published_at`.
**Tenant field: none** — listings are global, correct for a cross-school marketplace.
**RLS: present.** read = `status == 'published'` OR own; create/update/delete = `seller_id == user.id`. _This RLS breaks the buyer-side sales counter — see §7._

**MarketplaceTransaction** — one purchase.
`listing_id` (req), `seller_id` (req), `buyer_id` (req), `amount` (req, money), `currency` (default `BDT`), `status` (enum `pending|completed|refunded|disputed`, default `pending`), `payment_method` (free string — actually used to store `'personal'|'school_funded'`, _not_ a provider), `payout_processed` (bool, default false).
**No `school_id`.** **RLS: present** — read/update/delete for buyer or seller; create is wide open (`{}`), so any authenticated user can mint a transaction row for any listing.
Missing vs. what other code expects: `EnterpriseAnalytics.jsx:96-98` reads `t.purchased_at` and `t.amount_paid` — **neither field exists**.

**SellerEarnings** — the commission ledger line.
`transaction_id`, `seller_id` (req), `listing_id`, `gross_amount` (req, money), `platform_fee` (money), `seller_amount` (req, money), `commission_rate` (**number with no declared unit — written as 0.30 in one place and 15 in another**), `status` (enum `pending_payout|paid|on_hold`, default `pending_payout`), `processed_at`.
**RLS: present** — read/update/delete = own `seller_id`; create open.

**MarketplaceReview**
`listing_id` (req), `transaction_id` (req — "verified buyers only"), `buyer_id` (req), `rating` (number, doc says integer 1-5, **no enum/min/max enforced**), `review_text`.
**RLS: present** — read open `{}`, write = own `buyer_id`.

**SellerPublicProfile** — the buyer-facing seller identity.
`user_id` (req, "unique"), `display_name` (req), `bio`, `subjects` (string holding JSON array), `profile_image_url`, `verified_educator` (bool, default false, _"Set by SchoolTroop team ONLY — never by school"_), `total_listings`, `total_sales`, `rating_average`, `joined_at`.
**RLS: ABSENT.** **Never written by any code** — see §7.

**IdentityVerification** — KYC.
`user_id` (req, unique), `document_type` (req, enum `nid|passport|drivers_license`), `document_upload_url` (_"INTERNAL ONLY — never expose to public, schools, or buyers"_), `selfie_url` (same warning), `status` (enum `pending|verified|rejected`, default `pending`), `verified_by`, `verified_at`, `rejection_reason`.
**RLS: ABSENT.** This is the single most serious data-exposure gap in the area (§7).

## 3. Money flows — reconstructed precisely

### 3.1 Listing price → buyer pays

1. Seller sets `price` in BDT on the listing form (`ListingForm.jsx:134`), `0` = free.
2. Buyer opens `ListingDetail`. Price card shows `৳ {price}` and, if paid, the literal string **"Secure payment via SSLCommerz / Stripe"** (`ListingDetail.jsx:264`).
3. Buyer clicks **Buy Now**. `purchaseMutation` (`ListingDetail.jsx:67-128`) runs. **No payment is taken.** No provider SDK is loaded, no redirect, no charge, no order id. It writes rows:
   - `MarketplaceTransaction.create({... status: isSchoolFunded ? 'pending' : 'completed', payment_method: payMode, payout_processed:false })` (`:70-79`) — note `payment_method` stores `'personal'`/`'school_funded'`, **not** a provider.
   - If **not** school-funded: `SellerEarnings.create` (`:85-94`), `AcademicResource.create` (`:97-113`), `MarketplaceListing.update({total_sales+1, total_revenue_gross+price})` (`:115-118`).
4. UI then shows "Purchase Complete!" and a **Download Resource** button opening `listing.main_file_url` directly (`:249`).

**Status:** the personal-purchase path is a **STUB that self-declares success**. Marking `status:'completed'` with no payment means anyone can acquire any paid file for free by clicking Buy.

### 3.4 Seller earnings → payout

- **Path A (buy-time):** `ListingDetail.jsx:85-94` creates `SellerEarnings` at 30%, `status: 'pending_payout'`, `processed_at` omitted.
- **Path B (admin batch):** `CommissionEngine.runPayouts()` (`:64-88`) scans `MarketplaceTransaction` where `status==='completed'` and no `SellerEarnings` row carries that `transaction_id` (`:44-45`), then creates earnings at the admin's chosen rate with `processed_at = now`. Because Path A already stamps `transaction_id`, personal purchases are correctly skipped — but this means **the two paths use different rates depending on which one fired.**
- **The actual payout:** there is **none**. `runPayouts()` only inserts `SellerEarnings` rows with `status: 'pending_payout'`. Nothing ever sets `status: 'paid'`, nothing ever sets `MarketplaceTransaction.payout_processed = true`, no bank/bKash API is called. The button says _"Process N Payouts"_ and the success line says _"N payouts processed successfully"_ (`:138`). **This is a pure stub that mislabels row insertion as money movement.**
- **Seller payout destination:** collected in `BecomeSellerModal` step 3 (bank name / account name / account number, **or** bKash/Nagad number — `:207-233`) and **never persisted**. `handleSubmit` (`:38-100`) writes IdentityVerification, `auth.updateMe`, SchoolSettings and WorkspaceMember — the four payout state variables are simply dropped. There is no entity field anywhere to hold them.

### 3.5 School-funded vs personal

- **Personal:** transaction `status:'completed'` immediately; earnings + AcademicResource + counters written; buyer gets the file.
- **School-funded:** transaction `status:'pending'`; **no** earnings, **no** AcademicResource, **no** counters (`ListingDetail.jsx:81`). UI says _"Your school admin will review and approve the purchase"_ (`:245`).
  **The approval never arrives.** `Billing → Marketplace` tab renders `MarketplaceApprovals.jsx`, which queries **`BillingRecord` filtered to `record_type:'marketplace_purchase'`** — not `MarketplaceTransaction`. Its own comment admits it: _"In a real implementation, MarketplaceTransaction entity would be queried here / For now, use BillingRecord to show marketplace-type records"_ (`:15-16`). Approve sets `BillingRecord.status='paid'`, Reject sets `'overdue'` (`:27,34`). Since **nothing in the codebase ever creates a BillingRecord**, this table is permanently empty and the pending school-funded transaction is orphaned forever. **DEAD END.**
- Footnote at `MarketplaceApprovals.jsx:137`: _"Direct purchases made personally by teachers are marked 'Personal Purchase — not billed to school.'"_ — that string appears nowhere else; no such marking exists.

### 3.6 Subscription billing

- Plan is displayed from `SchoolSubscription` (`BillingOverview.jsx:68` `plan_name`, `:95` `total_monthly_cost`, `:134` `next_billing_date`, `:135` auto-billing state).
- **Nothing creates a SchoolSubscription row**, so for every real workspace `subscription` is `null` and the overview reads "No Active Plan" / "—".
- The only write is the **auto-billing toggle** (`Billing.jsx:49-54` → `SchoolSubscription.update({auto_billing_enabled})`), rendered per-card in `PaymentMethodsPanel.jsx:78-81`. It flips a boolean; no scheduler, no charge, no invoice generation exists.
- No proration, no seat-count recalculation (`monthly_cost_per_teacher × teacher_count` is never computed anywhere), no plan change, no cancel, no dunning for `status:'overdue'`.
- **Trial logic:** none beyond hardcoding `'trial'` at signup. No trial end date, no countdown, no expiry enforcement, no conversion path.

### 3.7 Credits / AI billing model & top-ups

- Intended model: `AIBillingModel.model_type` = `shared_pool` (one school-wide daily pool, unused credits expire at midnight) or `individual_allocation` (per-teacher daily credits), set at onboarding and changeable only by support (`permissions.js:27` `ai_billing_model_change: []`). `DailyAILimit` holds `daily_credits_per_teacher` / `daily_credits_pool` per plan.
- **Implemented:** `StaffAIPanel.jsx` lists all users with their `CreditAllocation` for the day, shows a status chip (`statusInfo` `:22-28`: `remaining<=0` → "Daily Limit Reached", `<20%` → "Low Credits"), and offers Approve/Reject on a pending `CreditRequest` plus a free-form **Top Up** grant.
  - Approve (`:199-219`): sets request `approved`, then `CreditAllocation.update({extra_credits_granted += requested, remaining_today += requested})`, then a Notification.
  - Top-up (`:236-247`): same allocation update, **no request record, no audit, no cap, no cost** — credits are conjured for free. _Admin top-up is not a purchase; no money is involved anywhere in the credit system._
- **Fake data:** the teacher drawer's three charts — 30-day bar, 6-month line, tool-usage donut — are `Math.random()` (`StaffAIPanel.jsx:33-43`, literally commented `// Mock chart data`). **Every AI usage chart an admin sees is fabricated and re-randomises on each open.**
- **Dead ends:** `AIBillingModel` and `DailyAILimit` are never read or written. `AIUsageLog` is never written (so `EnterpriseAnalytics` AI charts are empty). `CreditAllocation` is never _created_ and never reset at midnight despite `last_reset_at` existing. `CreditRequest` is never _created_ — there is no teacher-facing "ask for more credits" UI, so the whole approve/reject queue (and the pending-count badge on `Billing.jsx:92-94`) can never fire.
- `BillingOverview.jsx:100-103` hardcodes **"AI Usage Cost This Cycle: ৳ 0"**.

### 3.8 Manual expenses

The one genuinely working money feature. `ManualExpensesPanel.jsx`: create (`:73-76`), edit (`:78-81`), soft-delete via `deleted_at` (`:83-86`), recover (`:88-91`), total (`:95`). Caveat: `school_id: user?.school_id || 'default'` (`:74`) — `User` has no `school_id`, so **every expense is written to the literal tenant `'default'`** and, with no RLS on ManualExpense, becomes visible to every workspace. The "recoverable within 30 days" label (`:168`) is decorative — nothing purges.

### 3.9 Invoices / receipts

None. `PaymentMethodsPanel.jsx:124-126` renders a per-row **Download** icon button with **no `onClick`** — a dead button. No PDF/HTML invoice generator, no receipt on marketplace purchase, no email. `base44.integrations.Core.SendEmail` is never called anywhere in this area. `Billing → Import/Export → "Billing History"` / `"Marketplace Transactions"` exports a hardcoded placeholder blob: `[{ note: 'Export functionality — connects to entity data in production' }]` (`ImportExportModal.jsx:72`), saved with the chosen extension regardless of the JSON content.

## 4. Seller verification flow

**Two separate, divergent implementations.**

### Flow A — `VerificationWall.jsx` (used by `/marketplace` sell tab, `/seller-portal`, `/seller/verification`)

1. **Step 1** — pick `document_type`: NID / Passport / Driver's License (`:99-106`).
2. **Step 2** — upload ID document (`.pdf,.jpg,.jpeg,.png`) (`:110-117`).
3. **Step 3** — upload selfie (`.jpg,.jpeg,.png`) (`:120-127`).
4. Submit → two `Core.UploadFile` calls, then `IdentityVerification.create({status:'pending'})` (`:29-37`).
5. States rendered: `pending` → _"under review by the SchoolTroop team … usually within 1–2 business days"_ (`:57`); `rejected` → shows `rejection_reason` + a "Resubmit Documents" button that **only invalidates the query cache and resets local step state** (`:74`) — it does not clear or re-open the form, so the rejected screen re-renders unchanged; `verified` → `return null` (`:46`) and the parent shows the dashboard.
6. All three fields are required to enable Submit (`:131`).
7. **Resubmission always `create`s a new row** (never updates), so a user who submits twice produces duplicate `IdentityVerification` rows despite `user_id` being documented "unique"; all readers take `r[0]`.

### Flow B — `BecomeSellerModal.jsx` (personal-workspace "Become a Seller" CTA)

Three steps: **Seller Profile** (display name, ≤200-char bio, individual|institution, professional link) → **Identity Verification** (doc type, ID upload **required**, selfie _"optional, speeds up review"_ — but `canProceed1` at `:35` requires both, contradicting the label) → **Payout Details** (bank triple **or** bKash/Nagad number).
On submit (`:38-100`): uploads both files, **update-or-create** `IdentityVerification` (`:45-61`), `auth.updateMe({has_seller_profile:true, display_name, bio, seller_type, professional_link})`, then creates a `SchoolSettings` workspace `{workspace_type:'seller', subscription_status:'trial', subscription_plan:'free'}` + an owner `WorkspaceMember`. Toast: _"We'll review within 24–48 hours."_ (`:92`) — a **third** SLA, vs "1–2 business days" in Flow A.
**Payout fields are discarded.**

### Who approves

**Nobody.** There is **no admin/staff UI anywhere in the repo** that lists, reads, or updates `IdentityVerification`. The only writes are the two submit paths above. `verified_by` / `verified_at` / `rejection_reason` can only ever be set by direct DB edit. So in the shipped app, **`status` is permanently `'pending'` and no seller can ever be verified.**

### What verification gates

| Gate                                 | File:line                                                   | Effect                                                                                                                                      |
| ------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Marketplace "Academic Publisher" tab | `Marketplace.jsx:222-226`                                   | `verified` → `<SellerDashboard/>`, else `<VerificationWall/>`                                                                               |
| Seller Portal dashboard              | `SellerPortal.jsx:74-106`                                   | `verified` → KPIs + 5 tabs, else banner + wall                                                                                              |
| `/seller` dashboard                  | `seller/Dashboard.jsx:26-36`                                | banner only — **KPIs and OverviewTab render regardless**                                                                                    |
| `/seller/listings`                   | `seller/Listings.jsx:23-29`                                 | banner _"You can create draft listings but cannot publish until verified"_ — **ListingsManager renders and is fully functional regardless** |
| Sidebar badges                       | `SellerSidebar.jsx:56-60`, `PersonalSidebar.jsx:38,120-131` | "Verified" / "Pending Verification" chip; Seller Space link only for verified                                                               |

**The "cannot publish until verified" promise is not enforced.** Publishing is `status:'pending_review'` on the listing (`ListingForm.jsx:59`) and nothing checks verification at write time; RLS on MarketplaceListing checks only `seller_id`. An unverified user reaching `/seller/listings` (route has **no RoleGuard** — `App.jsx:181-188`) can create listings freely.

### Separately: listing moderation

`MarketplaceListing.status` implies a review queue (`pending_review → approved → published`, with `rejected` / `revision_requested` + `rejection_reason` + `revision_notes`). **No moderation UI exists.** `ListingForm` writes `pending_review`; `Marketplace.jsx:25` only shows `published`. Nothing ever transitions a listing to `approved`/`published`/`rejected`, and `published_at` is never set. **Consequence: no listing created through the app can ever appear in the marketplace.** The seller-side UI already renders all six statuses (`MarketplaceConstants.jsx:26-33`, `ListingsManager.jsx:59,73-75`) in anticipation.

### What "Connect" actually does

`ConnectWizard.jsx` — 3 labelled steps (`Authorize`, `Configure`, `Done`) but **only 2 are ever reachable**: `handleNext` (`:17-22`) calls `onConfirm` once `step === STEPS.length - 2` (i.e. step 1), so the "Done" panel at `:94-102` is unreachable dead UI.

- **Step 0 "Authorize"** — renders `item.scopes` as a checklist with green ticks, plus _"By connecting, you agree that this integration will act on behalf of your school's account."_ (`:73`). **No OAuth. No redirect. No consent screen. No token.** (Note: a separate `src/pages/OAuthConsent.jsx` exists but is not wired to this flow.)
- **Step 1 "Configure"** — one free-text field, "Connected Account Email", labelled _"This is the account identifier for audit purposes."_ (`:88`). Not validated, not verified, can be any string.
- **Finish** → `saveMutation` (`Integrations.jsx:233-257`) upserts an `IntegrationConfig`:
  `{ integration_id, name, status:'connected', connected_account: accountEmail || 'admin@school', last_sync_at: new Date().toISOString(), connected_by, connected_by_name, sync_enabled:true }`.
  Note the fallback **`'admin@school'`** (`:240`) when the field is left blank.

### What config is stored / not stored

Stored: the 7 fields above. **Never stored:** `settings` (the field explicitly documented _"JSON stringified settings/token metadata"_) and `last_error`. There is **no credential, token, refresh token, API key, webhook secret, or tenant id** stored anywhere — and no `school_id` on the entity, so one workspace's "connections" are visible to all.

## 8. Open questions for the owner

1. **Payment provider for buyer-side charges** — SSLCommerz, Stripe, or both? The `PaymentMethod.provider` enum and the `ListingDetail` copy name both, but SSLCommerz (BDT) and Stripe (card) imply very different flows. Is Stripe for international/school subscriptions and SSLCommerz for local marketplace purchases, or is one a fallback?
2. **Seller payout rail** — the onboarding wizard offers bank transfer **or** bKash/Nagad. Which do you actually intend to support, and do you plan to pay out manually at first? Nothing is currently stored; a `SellerPayoutMethod` entity (or fields on `SellerPublicProfile`) has to be designed.
3. **Payout cadence and minimum** — on what schedule do sellers get paid (per sale, weekly, monthly, on-request)? Is there a minimum balance? Is there a hold period before earnings become payable (`status: 'on_hold'` exists but is never used)?
4. **Commission rate — 30 % or 15 %?** Nine UI strings promise sellers 70 %, `COMMISSION_RATE` says 30 %, `CommissionEngine` defaults to 15 % and lets an admin type anything 0–50, and `permissions.js:28` says nobody may change it. Which is the real rate, and is it global, per-seller, per-category, or negotiable?
5. **Commission-rate storage unit** — should `SellerEarnings.commission_rate` be a fraction (0.30) or a percent (15)? Both are written today.
6. **Who moderates listings?** The `pending_review → approved → published → rejected → revision_requested` workflow implies a human editorial queue. Is that you/your staff, school admins, or should listings auto-publish on submission? Today nothing can ever publish.
7. **Who approves identity verification, and what are the criteria?** There is no reviewer UI at all. Is this a platform-staff (SchoolTroop/Acadigma) function, and what's the real SLA — "1–2 business days" or "24–48 hours"?
8. **What does `verified_educator` mean** as distinct from `IdentityVerification.status === 'verified'`? Is the blue badge earned by KYC, by employment proof, or by sales volume?
9. **Subscription pricing** — what are the actual plan names and BDT prices? Two conflicting models exist (`SchoolSubscription` per-teacher seat bands like "6-10 Teachers" vs `SchoolSettings.subscription_plan` = free/starter/pro/enterprise). Which one wins?
10. **What does each plan gate?** Nothing in the code is plan-conditional today. Candidates from the schema: AI daily credits (`DailyAILimit.plan_name`), storage quota (the "34 GB of 100 GB" / "Upgrade to Enterprise for 250 GB" strings), and the `module_*` feature flags.
11. **Trial terms** — how long, what happens at expiry (read-only? lockout? downgrade to free?), and does a card need to be on file to start?
12. **AI billing model choice** — is `shared_pool` vs `individual_allocation` a plan-level property, a sales-time decision, or customer-configurable? Today it's "onboarding only, support-changeable" but no onboarding writes it.
13. **Do AI credits cost money?** `AIUsageLog.cost_generated` is BDT and `BillingRecord.record_type` includes `ai_usage`, implying metered overage billing — but admin top-ups are currently free and uncapped. Are extra credits sold, or included in the plan?
14. **School-funded purchases** — is the school charged at approval time (invoice line on the school's next bill) or immediately? Who is the buyer of record for the licence — the teacher or the school? Does the resource stay with the teacher if they leave (`AcademicResource.status: 'orphaned'` suggests you've thought about this)?
15. **Digital-rights model** — should a purchased file be re-hosted per buyer (watermarked with the buyer's name?) or is a shared URL acceptable? Today the paid file URL is readable by anyone who can see the listing.
16. **Refund policy and tooling** — `refunded`/`disputed` exist in the schema. Who can issue a refund, does it claw back seller earnings, and within what window?
17. **Invoices/receipts** — do you need PDF invoices for schools (VAT/BIN for Bangladesh?), and receipts for marketplace buyers? Nothing is generated today.
18. **Tenancy for billing** — should `SchoolSubscription`/`BillingRecord`/`PaymentMethod`/`ManualExpense`/`CreditAllocation` be scoped by `workspace_id` like the rest of the app? All currently write to the literal `'default'` and read cross-tenant.
19. **Integrations** — which of the 12 "connectable" integrations do you actually intend to build first, and is a real OAuth flow (`OAuthConsent.jsx` exists unused) the plan? Also: should `IntegrationConfig` be per-workspace rather than global?
20. **Seller identity vs user identity** — should the public storefront live on `SellerPublicProfile` (as the buyer UI reads) or on the `User` record (as `/seller/profile` writes)? Right now they're two disconnected stores.
21. **Who may sell?** `canSell` says teacher-role only, but the newer `account_type: 'seller'` / seller-workspace path implies standalone sellers who aren't in a school at all. Which is the product?
22. **Bulk upload** — is CSV import a real seller need (it currently uses an LLM extraction call per file), and should bulk-created listings bypass moderation?
