# 02 — Academic Core: Product-Intent Inventory

**Scope:** Classes, Students, Admission, Attendance (student + teacher), Marks, Exams, Assignments, Schedule, Master Calendar, Handouts, Parent Portal, Behavior Tracking, Student Analytics, Risk Scoring, and the components they pull in.
**Codebase:** `F:\Acadigma Campus\Acadigma Campus Base44 Source Code` (read-only)
**Date:** 2026-09-17

---

## 1. Area summary

The owner is building a **single-campus K-12 school operations system aimed at Bangladeshi private/English-medium schools** (defaults: `nationality: "Bangladeshi"`, `country: "Bangladesh"`, Bengali/Madrasa curriculum boards, Saturday-start work week, `Asia/Dhaka` timezone, subject list includes Bengali and Islamic-context religions). Target size looks like **a few hundred to ~2,000 students** — every list screen loads the whole table client-side with no pagination, so it breaks above that.

The **grading model** is percentage-based with a 7-band letter scale (A+ / A / B+ / B / C / D / F at 90/80/70/60/50/40). There is **no GPA, no weighting, no subject credit, no pass mark configuration, and no ranking** anywhere in the code. Terms are a fixed enum (`Term 1 / Mid Term / Term 2 / Term 3 / Annual`), and marks are entered per _assessment component_ (Quiz, Class Test, Homework, Oral, Midterm, Final Exam, Project, Classwork).

The **timetable model** is a permanent repeating weekly routine: one `ScheduleSlot` per (class, day-of-week, period number), with start/end time and a session type. There is no dated timetable, no teacher-slot ownership, no room booking, and no conflict detection.

The **attendance model is the single biggest problem in this area — it is modelled twice and the two halves are not connected.** The intended model appears to be daily per-class roll-call (`Attendance`: student + class + date + present/absent/late). The _implemented_ UI is a gate/scanner check-in/check-out event log (`AttendanceLog`: student + timestamp + checked_in/checked_out). **Nothing in the app writes `Attendance`, and six screens read it.** So attendance percentages, parent-visible attendance, attendance analytics, attendance alerts and the attendance section of the PDF report are all permanently zero/empty.

A "Class" in this data model is **a class-subject pair**, not a homeroom (`Class.subject` is required), but the Add Class form never sets `subject` — so the data model and the only creation UI disagree.

### Class — `base44/entities/Class.jsonc`

A class-subject offering, not a homeroom. Fields: `name` (required), `subject` (**required**, 15-value enum `Class.jsonc:36-52`), `grade_label`, `grade_number`, `section`, `level_group` (Early/Primary/Secondary — **never set or read anywhere**), `teacher_name` (**a free-text string, not an FK to User**), `room`, `total_students` (**never written or recalculated**), `notes`.
Relationships: pointed at by `Student.class_id`, `Attendance.class_id`, `Mark.class_id`, `Exam.class_id`, `Assignment.class_id`, `ScheduleSlot.class_id`, `Handout.class_id`, `BehaviorLog.class_id`.

### Student — `base44/entities/Student.jsonc` (100+ fields)

By far the largest entity. Blocks: identity, ID document, addresses, class placement (`class_id`, `grade_number`, `section`, `roll_number`), admission (`admission_date/year/number`, `class_sought`), siblings (JSON string), previous school + TC, health (7 fields), interests, **full father block (18 fields) and full mother block (18 fields)** incl. WhatsApp/Facebook/Twitter/Instagram/WeChat, `heard_from`, `photo_consent`, legacy `parent_name/contact/email`, `status` enum (active/inactive/transferred/draft), `needs_attention` + `attention_reason`, `average_score` (**declared but never written — the UI recomputes from Marks every time**), `admission_form_complete`.
**There is no `grade` field** — `Attendance.jsx:44,62` reads `s.grade` (see §6). There is no `student_code` field either — `Attendance.jsx:60,243` reads it.

### Attendance vs AttendanceLog — the duplicate model

- **`Attendance`** (`Attendance.jsonc`): daily roll-call. `student_id`, `class_id`, `date` (date), `status` ∈ present/absent/late, `notes`. Tenant + RLS. **Zero write sites in the whole app** (verified by grep: only `.filter`/`.list` calls exist).
- **`AttendanceLog`** (`AttendanceLog.jsonc`): event log. `student_id`, `teacher_id`, `timestamp` (date-time), `status` ∈ checked_in/checked_out/late/absent, `room_id`, `scan_type` ∈ hardware/manual/qr, `notes`. **No `class_id`, no `date`, no `workspace_id`, no RLS.** Written only by `Attendance.jsx:82`.
- Consequence: the roll-call screen produces event rows that no report, portal or analytic can read, and the reports read a table nobody fills.

### Mark vs Grade — the second duplicate model

- **`Mark`** (`Mark.jsonc`): `student_id`, `class_id`, `subject`, `component` (8-value enum), `assessment_title`, `marks_obtained`, `max_marks`, `term` (5-value enum), `date`, `remarks`. Tenant + RLS. This is the live one.
- **`Grade`** (`Grade.jsonc`): `student_id`, `class_id`, `assessment_type` (exam/assignment/quiz/classwork/project), `assessment_title`, `marks_obtained`, `total_marks`, `date`, `remarks`. No tenant, no RLS. **Completely unreferenced in `src/` — dead entity, earlier draft of `Mark`.**

### TeacherAttendance — `TeacherAttendance.jsonc`

`teacher_id` (User id), `teacher_name`, `department` (**never written**), `role`, `date`, `check_in_time`, `check_out_time`, `status` ∈ Present/Absent/Late/On Leave/Half Day, `leave_type` ∈ Sick/Annual/Emergency/Official Duty/Unpaid, `notes`. **No `workspace_id`, no RLS.**

### Exam / Assignment / ScheduleSlot / Handout / BehaviorLog

- **Exam**: `title`, `class_id`, `exam_date`, `exam_type` (7-value enum), `total_marks`, `duration_minutes`, `syllabus`, `status` ∈ upcoming/paper_ready/conducted/graded, `paper_file_url` (**no UI to set it**), `google_doc_link`.
- **Assignment**: `title`, `class_id`, `description` (**no UI field**), `assigned_date`, `due_date`, `status` ∈ assigned/collecting/collected/graded, `type` (6-value enum), `total_marks`, `file_url` (**no UI**), `google_doc_link` (**no UI**). No per-student submission or grade link — "graded" is a status flag on the whole assignment.
- **ScheduleSlot**: `class_id`, `day_of_week` ∈ **Monday…Saturday (no Sunday)**, `period_number`, `start_time`, `end_time`, `session_type` (7-value enum), `topic`, `notes`.
- **Handout**: `title`, `class_id`, `type` (6-value enum), `file_url`, `google_doc_link`, `distribution_date`, `distributed` (bool), `topic`, `notes`. **No tenant field, no RLS.**
- **BehaviorLog**: `student_id`, `student_name` (denormalized), `class_id` (**never written by the UI**), `logged_by`, `logged_by_name`, `type` ∈ positive/negative, `category` (7-value enum), `description`, `points` (default 1), `date`. Tenant + RLS.

### Cross-cutting: nothing stamps `workspace_id`

Grep across all 17 files in this area: **not one `.create()` call sets `workspace_id`.** The app relies entirely on Base44 auto-applying the RLS `create` rule. For the four entities with no `workspace_id` property at all (AttendanceLog, TeacherAttendance, Handout, Grade), there is nothing to apply — those tables are **global across every school on the platform**.

## 4. Workflows

### 4.1 Admit a student → assign to class → take attendance → enter marks → parent sees report

**As intended:**
Admission form → student gets a class → daily roll call → marks per assessment → parent logs in and sees attendance + grades + report card.

**As it actually exists:**

1. **Admit.** Admin opens `/students/admission` (`App.jsx:109`, admin+superadmin only). 9 steps (`StudentAdmission.jsx:15-25`). Class is chosen in step 1 (`:317`), which also copies `grade_number`, `section` and `class_sought` off the Class record. Photo and documents go through `Core.UploadFile` (`:200-214`, `:38-43`, `:71-76`). Submit builds `name` by joining first/middle/last (`:226`), generates `student_id` as `STU-<year>-<random 5 digits>` (`:227`) and `admission_number` as `ADM-<year>-<random 3 digits>` (`:146`) — **both random, both collision-prone, neither sequential**. Siblings are `JSON.stringify`'d into a string column (`:232`).
2. **Welcome email.** On the _create_ path only, `Core.SendEmail` fires (`:181-186`) — this one is a genuine integration call, but errors are swallowed and there is no delivery record. On the _draft → submit_ path (`:238-244`) no email is sent at all.
3. **Redirect.** `navigate('/students/<id>?admitted=true')` (`:187`) — `StudentDetail.jsx` never reads `admitted`, so there is no success confirmation.
4. **Assign to class.** Either at admission (step 1) or later in bulk via Students → select → Move to Class (`Students.jsx:110-124`), which also copies `grade_number`/`section` from the target class.
5. **Take attendance.** `/attendance`. The teacher must apply a filter first (`Attendance.jsx:187-197` — empty state until then). The **grade dropdown is permanently empty** because it maps `students.map(s => s.grade)` and `Student` has no `grade` field (`:44`). So in practice only the free-text ID/name search works. Pressing Check In / Absent / Late writes an **`AttendanceLog`** row (`:80-84`).
6. **Marks.** `/marks`: pick class → term → component → title → max marks → type a number per student → Save. Students are matched to the class by `class_id`, falling back to `grade_number + section` (`Marks.jsx:48-58`). Save loops one API call per student (`:102-122`).
7. **Parent sees.** Parent logs in, lands on `/parent-portal`. **Attendance tab is empty forever** (`ParentPortal.jsx:54-58` reads `Attendance`; step 5 wrote `AttendanceLog`). Marks tab works. There is no report card, no behaviour, no timetable for parents.
8. **Report card.** The real report card lives in `components/reports/StudentReportCard.jsx`, reachable from `/reports` (outside this area). It aggregates Marks by subject, offers per-subject AI comments (`:68-81`, real `InvokeLLM`) — **but the generated comments are held in React state only and are never persisted** (`:79`), and the header is hardcoded to `"TeachFlow Academy"` (`:123`) instead of `SchoolSettings.name`.

### 4.2 Create a timetable

`/schedule` → pick a day tab → "Add Class Slot" → choose Class, period #, start/end, session type, topic → `ScheduleSlot.create` (`Schedule.jsx:70-76`). Days come from `getWorkDays(school.first_day_of_week)` (`:23-34`), always exactly 5 days. **Sunday-start schools will attempt to write `day_of_week: "Sunday"`, which is not in the enum.** No teacher ownership (the slot only points at a Class, whose teacher is a free-text `teacher_name`), no room field on the slot (it shows `cls.room`), no clash detection, no bulk/copy-week, and the timetable never appears on the Master Calendar.

### 4.3 Assign homework

`/assignments` → New Assignment → title, class, type, assigned/due date, marks, status → `Assignment.create`. **The type dropdown is wired to the wrong list** (`Assignments.jsx:200` uses `MATERIAL_TYPES`, 16 values, vs the 6-value schema enum). There is no description field, no file attach, no notification to students or parents. Parents can see the assignment via `/parent-portal` "Upcoming Work" (`ParentPortal.jsx:66-70`). Grading is a status flag on the assignment; there is no per-student submission record and no path from a graded assignment into `Mark`.

### 4.4 Exam scheduling

`/exams` → New Exam → title, class, type, date, marks, duration, syllabus, optional Google Doc → `Exam.create`. Lifecycle is driven by one "Advance Status" button that cycles `upcoming → paper_ready → conducted → graded → upcoming` (`Exams.jsx:66-70`) — **it wraps, so a graded exam reverts to upcoming on one extra click.** Exams appear on the Master Calendar by `exam_date` (`MasterCalendar.jsx:31-34`). There is no seating plan, no invigilator assignment, no paper upload, no roll of which students sat it, and no link from `Exam` to `Mark` (Marks is organised by component/term, not by exam id).

### 4.5 Behaviour incident

`/behavior` → "Log Behavior" → student, positive/negative, category, points (1–10), date, description → `BehaviorLog.create` with `student_name`, `logged_by`, `logged_by_name` denormalised in (`BehaviorTracking.jsx:76-85`). `class_id` is never set. The log appears in a feed and contributes to a running conduct score and a top-5 leaderboard. **Nobody is notified**; the incident is invisible on StudentDetail, on the report card and to parents. Its only downstream effect is as a penalty term in Risk Scoring.

### 4.6 Risk scoring — inputs and outputs

**Inputs:** the last 1,000 `Mark` rows and last 1,000 `BehaviorLog` rows, plus all Students (`RiskScoring.jsx:43-45`). Students with **fewer than 2 marks are excluded entirely** (`:14`). Attendance is not an input.
**Outputs:** three on-screen buckets (At-Risk / Declining / On Track) and, when "Run Risk Scan" is pressed, a write-back of `needs_attention: true` + a human-readable `attention_reason` onto the Student row (`:83-90`). That flag is then surfaced on Students (`Students.jsx:254`), StudentDetail (`StudentDetail.jsx:193,245-247`), Parent Portal (`ParentPortal.jsx:140-144`) and Student Analytics ("Needs Attention" card, `StudentAnalytics.jsx:125`). The scan also **auto-clears** flags a human may have set, using substring matching on the reason text (`:91`).

### 4.7 ID card / barcode / QR

Not implemented in this area. `AttendanceLog.scan_type` permits `hardware` / `qr` and `AttendanceLog.room_id` exists, and the Attendance page dresses itself as a live scanner (fake feed, "Live" pill, room filter) — but there is no QR/barcode generation, no scanner input handler, no device integration, and no barcode/RFID field on `Student`. The display IDs shown on the cards are computed on the fly as `S-<first 4 chars of the row id>` (`Attendance.jsx:59,243`).

## 5. Calculations (every formula in this area, verbatim)

**Grade letter — four independent, mutually inconsistent implementations:**

1. `StudentDetail.jsx:26-34` — `≥90 A+`, `≥80 A`, `≥70 B+`, `≥60 B`, `≥50 C`, `≥40 D`, else `F`.
2. `Marks.jsx:17-25` — identical bands, plus colours.
3. `components/reports/StudentReportCard.jsx:11-19` — identical bands, plus colours + background.
4. `ParentPortal.jsx:12-19` — **different scale**: `≥90 A+`, `≥80 A`, `≥70 B`, `≥60 C`, `≥50 D`, else `F` (no B+, and C/D shifted a full band). **A child can be shown a "C" on the parent portal and a "B+" on the teacher's screen for the same 72%.**

**Per-assessment percentage** — `StudentDetail.jsx:128,318`, `Marks.jsx:211`, `ParentPortal.jsx:198`, `StudentReportCard.jsx:195`, `RiskScoring.jsx:16`:
`pct = round((marks_obtained / max_marks) * 100)`

**Student average score (StudentDetail)** — `StudentDetail.jsx:132-134`:
`avg = round( Σ over all marks of (max_marks ? (obtained/max)*100 : 0) / count(marks where max_marks truthy) )`
Unweighted mean of percentages. Note the numerator sums over _all_ marks (contributing 0 for rows with no max_marks) while the denominator counts only rows _with_ max_marks — so a bad row drags the average down rather than being excluded.

**Student average score (Parent Portal)** — `ParentPortal.jsx:77-79`:
`avg = round( Σ (obtained/max)*100 / marks.length )` — no guard on `max_marks`; a zero/undefined `max_marks` yields `NaN` or `Infinity` for the whole average.

**Student attendance % (StudentDetail)** — `StudentDetail.jsx:136-138`, over the last 60 `Attendance` rows:
`pct = round(present / total * 100)` — **late counts against the student.**

**Student attendance % (Parent Portal)** — `ParentPortal.jsx:75`, over the last 30 rows:
`pct = round((present + late) / total * 100)` — **late counts as present.** The same child's attendance is computed two different ways on two screens.

**Overall attendance rate (Analytics)** — `StudentAnalytics.jsx:119-123`:
`rate = round(present / attendance.length * 100)` over the last 1,000 rows, labelled "all-time average".

**Daily attendance rate (Analytics, last 7 days)** — `StudentAnalytics.jsx:73-78`:
`rate_day = round(present / (present + absent + late) * 100)`, 0 when the day has no rows (so a holiday plots as 0%, not as a gap).

**Attendance rate by class (Analytics)** — `StudentAnalytics.jsx:82-96`:
`rate_class = round(present / total * 100)`, top 8 classes by rate.

**Low-attendance alert threshold** — `components/notifications/AttendanceAlerts.jsx:33-40`, last 30 days:
`absentRate = round(absent / (present + absent + late) * 100)`; a class is flagged when `absentRate > 15`.

**Overdue-assignment alert** — `AttendanceAlerts.jsx:46-50`: a student is flagged when their class has **more than 3** assignments in the last 30 days still in `assigned` or `collecting`. (This is a _class_-level count attributed to every student in the class — it is not per-student.)

**Assignment completion rate** — `StudentAnalytics.jsx:105-109`:
`completion = round( count(status ∈ {graded, collected}) / count(all assignments) * 100 )`

**Teacher attendance rate** — `TeacherAttendance.jsx:24-28`:
`rate = round( count(status ∈ {Present, Half Day, Late}) / count(all records) * 100 )` — Half Day counts as a full day.

**Conduct score (Behaviour)** — `BehaviorTracking.jsx:54-61`:
`score(student) = Σ over logs of ( type === 'positive' ? +points : −points )`, `points` defaulting to 1. Bands (`:20-22`): `≥20 Excellent`, `≥0 Satisfactory`, `<0 Needs Improvement`.

**Risk — academic** — `RiskScoring.jsx:13-26`:

```
sorted   = marks sorted ascending by date
pcts     = sorted.map(m => (m.marks_obtained / m.max_marks) * 100)
avg      = round(mean(pcts))
recent   = last 3 of pcts
trend    = round(recent[last] - recent[0])      // 0 if fewer than 2
```

Returns `null` (student excluded) when `marks.length < 2`.

**Risk — behaviour** — `RiskScoring.jsx:28-37`:
`behaviorPoints = Σ positive points − Σ negative points`

**Risk — combined score** — `RiskScoring.jsx:59-60`:

```
behaviorPenalty = behaviorPoints < 0 ? |behaviorPoints| * 2 : 0
combinedRisk    = (100 − (avg ?? 100)) + (trend < 0 ? |trend| : 0) + behaviorPenalty
```

`combinedRisk` is used **only to sort the list** (`:64`) — it is never displayed and never stored.

**Risk — bucketing and flagging** — `RiskScoring.jsx:10-11,67-77`:

```
RISK_THRESHOLD  = 50      // avg below 50% ⇒ At-Risk
TREND_THRESHOLD = -10     // trend below −10 ⇒ Declining
atRisk    = avg < 50
declining = avg ≥ 50 and trend < −10
healthy   = avg ≥ 50 and trend ≥ −10
shouldFlag = (avg < 50) or (trend < −10) or (behaviorPoints < −2)
```

**Report-card subject aggregation** — `StudentReportCard.jsx:46-66`:
`subject_pct = round(Σ obtained / Σ max * 100)` per subject; `overall_pct = round(Σ all obtained / Σ all max * 100)`. This is **mark-weighted** — unlike StudentDetail's unweighted mean of percentages, so the same student's "average" differs between the profile page and the report card.

**Not implemented anywhere:** GPA, credit/subject weighting, class rank or position, pass/fail mark, term-to-term progress delta, promotion/retention rule, attendance requirement for exam eligibility.

## 7. Open questions for the owner

1. **Which attendance model do you actually want?** Daily per-class roll-call (`Attendance`), a gate/scanner event log (`AttendanceLog`), or both (period-level attendance rolled up from gate scans)? Everything downstream — parent portal, analytics, alerts, report cards — assumes the first; the only working UI implements the second.
2. **Does "late" count as present?** StudentDetail says no (`StudentDetail.jsx:136`), Parent Portal says yes (`ParentPortal.jsx:75`), teacher attendance counts Half Day as full (`TeacherAttendance.jsx:26`). Which is the school's rule, and is there a minimum attendance % for exam eligibility?
3. **Is a `Class` a homeroom or a class-subject pair?** The schema requires `subject` (class-subject), the Add Class form treats it as a homeroom, and `Student.class_id` is singular — so a student can only belong to one Class, which is incompatible with one Class per subject. This is the single most load-bearing modelling decision in the area.
4. **What is the real grade scale?** Four scales exist in code, one of which (Parent Portal) contradicts the other three. Bangladeshi GPA (A+ = 5.00, A = 4.00 … F = 0.00) is the obvious candidate but appears nowhere. Do you need GPA, subject weights, a pass mark, and class ranking?
5. **What is the work week?** `first_day_of_week` supports Sat/Sun/Mon, `work_week_days` defaults to 6 days (Sat–Thu), the Schedule page hardcodes 5 days, and `ScheduleSlot.day_of_week` has no Sunday. Which is authoritative?
6. **Should student IDs and admission numbers be sequential?** Both are currently random (`STU-2026-<5 random digits>`, `ADM-2026-<3 random digits>`) with no uniqueness check — three-digit random admission numbers will collide within one intake.
7. **Should Exams and Marks be linked?** Today `Exam.status = graded` and the `Mark` rows for that exam are completely unconnected; there is no `Mark.exam_id`. Same question for Assignment → Mark.
8. **What does "distribute a handout" mean operationally** — send to a print queue, email parents, publish to a student portal, or just tick a box for the teacher's own tracking?
9. **Who may take staff attendance?** Route says teachers can; nav and the permission matrix say admin only.
10. **Should Risk Scoring actually use AI,** or is the deterministic formula the intent and the "AI" label just branding? And should attendance and assignment-submission be inputs alongside marks and behaviour?
11. **Should the risk scan be allowed to clear a flag a human set?** It currently does, using substring matching on the reason text.
12. **Is the barcode/QR/ID-card gate scanning a real roadmap item** (the Attendance page is dressed as one, `AttendanceLog.scan_type` anticipates it), or should the fake live-feed UI be dropped?
13. **How much of the 100-field Student record is mandatory in practice?** The 9-step admission wizard has no validation at all — should submission be blocked on missing required fields, and which are they?
14. **Should parents see report cards, behaviour logs, timetables and exam schedules?** Today they see attendance (empty), marks, and upcoming assignments only.
15. **Is `Grade` safe to drop,** and is there production data in it from an earlier version?
16. **Are behaviour points meant to be term-scoped or all-time?** The leaderboard is currently all-time over the most recent 200 logs.

## 8. Cross-area dependencies

**Auth & tenancy** (`src/lib/AuthContext.jsx`, `src/lib/SchoolContext.jsx`, `src/lib/permissions.js`, `src/lib/RoleGuard.jsx`)

- Every screen here depends on Base44 RLS resolving `{{user.data.active_workspace_id}}`, which is set by a best-effort `auth.updateMe` at boot (`SchoolContext.jsx:55-57`) that fails silently. If that sync loses a race, every list in this area comes back empty with no error shown.
- This area needs: a server-side workspace-scoped student/staff directory (replacing `User.list()`), `workspace_id` on AttendanceLog / TeacherAttendance / Handout, a parent↔student link that is not an email-string match, route guards on `/schedule` and `/calendar`, and one source of truth for nav-vs-route-vs-permission-matrix roles.

**Printing** (`/print`, `PrintQueue` / `Printer` entities, `permissions.js:49-50`)

- The Recovery Protocol modal's "Confirm & Print" and the Handouts "distribute" action both need a real print-job submission. Neither touches `PrintQueue` today. Report cards use raw `window.print()` (`StudentReportCard.jsx:91-93`).

**Reports** (`/reports`, `src/components/reports/*`, `src/lib/pdfReports.js`)

- `StudentDetail` and `StudentAnalytics` call `pdfReports.js` directly; the richer report card and progress report live under `/reports`. Both report generators read `Attendance` and therefore inherit the empty-attendance bug. The report card needs `SchoolSettings.name` and a place to persist AI comments.

**Messaging / notifications** (`/messaging`, `/communication`, `Message` / `Notification` entities, `Core.SendEmail`)

- Absence notification, behaviour-incident notification, low-attendance escalation, report-card delivery, assignment reminders and handout distribution are all implied by this area's UI and none are wired. The only two live `SendEmail` calls are the admission welcome and the bulk-import welcome, both fire-and-forget.

**AI** (`Core.InvokeLLM`, `AIUsageLog` / `DailyAILimit` / `CreditAllocation`)

- The only genuine LLM use touching this area is report-card comment generation (`StudentReportCard.jsx:68-81`), and it does **not** log usage or check credits, unlike the AI features in other areas. "AI Risk Scoring" uses no AI at all.

**Settings / onboarding** (`/settings`, `/welcome`, `SchoolSettings`)

- `first_day_of_week` is honoured by `/schedule` only; `work_week_days`, `attendance_cutoff`, `date_format` and `timezone` are collected and never consumed by this area.

**Other areas that read this area's data:** Dashboard (Attendance, Students), Communication (DiaryEntry), CurriculumEngine (DiaryEntry), Workload/WorkloadBalancer, Cover Teacher (Class/ScheduleSlot), Report Generator.
