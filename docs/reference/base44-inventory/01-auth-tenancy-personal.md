## 1. Area summary

The owner is building **Acadigma Campus** — a multi-tenant school-operations SaaS for Bangladesh/South-Asia (BDT, bKash/Nagad, Saturday-first work week, Class 1–10 / O-Level / HSC, National Curriculum BD + Cambridge).

The product intent in this area is a **three-front identity**: a teacher can be (a) a member of a **school workspace** with an admin-controlled role, (b) the owner of a **personal workspace** — a solo/tuition teacher's private space with their own students, attendance, file vault and CV, and (c) a **seller** on the marketplace. One login, multiple workspaces, a switcher in the top bar, and hard tenant isolation ("Every school gets a fully private, isolated workspace. No data mixing. Ever." — `Welcome.jsx:50`).

Onboarding is meant to be the funnel: register as Teacher or Academic Publisher (seller) → verify email by OTP → land on a Welcome/onboarding screen → choose "Create School Workspace" (3-step branding wizard), "Join a School" (invite code → admin approval), or "Personal Workspace" (instant). Admins then manage the roster on a Team & Access page with roles, per-member staff metadata, invite code, and email invites.

**What actually exists:** the entity model and the happy-path CRUD are real and mostly work. What is _not_ built: any binding between workspace type and which app shell a user sees, any real email delivery, any invitation record creation, user preference persistence, account deletion, password change inside the app, and per-workspace role enforcement on the server (permissions are cosmetic client-side filters).

## 2. Workspace model as implemented

### 2.1 Workspace types

`SchoolSettings` **is** the workspace table — one entity serving three purposes (`SchoolSettings.jsonc:9-18`):

| `workspace_type` | Created by                                                                       | Name convention                            | Lands on                                            |
| ---------------- | -------------------------------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------- |
| `school`         | `Welcome.jsx:126-172` (3-step wizard)                                            | user-entered                               | `/`                                                 |
| `personal`       | `TeacherRegister.jsx:95-112`, `Welcome.jsx:175-203`                              | `"{name} Workspace"`                       | `/` (register) or `/` (welcome) — never `/personal` |
| `seller`         | `SellerRegister.jsx:73-90`, `Welcome.jsx:205-232`, `BecomeSellerModal.jsx:74-90` | `"{name} Store"` / `"{name} Seller Store"` | `/seller-portal`                                    |

Only `school` workspaces get an `invite_code` (`Welcome.jsx:131-141`). Personal and seller workspaces get `owner_id`, `subscription_status: 'trial'`, `subscription_plan: 'free'` and nothing else — no timezone, no country, no logo.

### 2.2 How a user gets into a workspace

Membership is `WorkspaceMember` (`WorkspaceMember.jsonc`), keyed by `workspace_id` + `user_email`. Four paths:

1. **Auto-provision at registration.** `TeacherRegister.handleVerify` creates a personal workspace + `role: 'owner', status: 'active'` (`TeacherRegister.jsx:95-112`). `SellerRegister.handleVerify` does the same for a seller workspace (`SellerRegister.jsx:73-90`).
2. **Create a school** in onboarding — creator becomes `owner/active` (`Welcome.jsx:156-165`).
3. **Request access by invite code** — user types `ACD-XXXX-XXXX`, the app `filter`s `SchoolSettings` by `invite_code`, and self-creates a `WorkspaceMember` with `role: 'teacher', status: 'pending'` (`Welcome.jsx:254-273`; duplicated at `personal/Workspaces.jsx:55-79`). An admin then flips it to `active` on Team & Access.
4. **Admin invites by email** — `TeamManagement.handleInvite` creates the member row directly as `status: 'pending'` (`TeamManagement.jsx:53-79`).

### 2.3 Role vocabulary — three overlapping systems

| System                                 | Values                                                      | Where                                   |
| -------------------------------------- | ----------------------------------------------------------- | --------------------------------------- |
| Base44 platform role                   | `admin` \| `user`                                           | `User.jsonc:5-13`                       |
| Workspace member role                  | `owner` \| `admin` \| `teacher` \| `parent` \| `staff`      | `WorkspaceMember.jsonc:41-52`           |
| Permission role ("School Troop roles") | `superadmin` \| `admin` \| `teacher` \| `staff` \| `parent` | `permissions.js:7-16`                   |
| Invitation role offered                | `teacher` \| `staff` \| `principal`                         | `SchoolWorkspaceInvitation.jsonc:29-37` |
| CustomLabel base role                  | `superadmin` \| `admin` \| `teacher` \| `staff`             | `CustomLabel.jsonc:9-18`                |

The bridge is `useEffectiveRole()` (`RoleGuard.jsx:25-34`): take `currentRole` from `SchoolContext` (the member row's role), map **`owner` → `superadmin`**, else pass through; fall back to `getUserRole(user)` which returns `user.role` if it is one of the five, else `'teacher'` (`permissions.js:77-83`).

Consequences:

- There is **no `owner` in `PERMISSIONS`** and no `superadmin` in `WorkspaceMember.role` — the mapping is the only link.
- `SchoolContext` defaults `currentRole` to `'teacher'` whenever there is no member row (`SchoolContext.jsx:109`), so `useEffectiveRole` **never** returns `null` and the `getUserRole(user)` fallback branch is unreachable.
- `principal` exists only on the invitation entity; nothing consumes it, and `TeamManagement`/`WorkspaceMembers` role dropdowns don't offer it.
- `staff` is assignable but appears in almost no `PERMISSIONS` list — a staff user sees Dashboard, Calendar, Schedule, Messaging, Marketplace, Profile only.

### 2.4 Switching & storage

`SchoolContext` (`SchoolContext.jsx:11-68`) on mount: `auth.me()` → `WorkspaceMember.filter({user_email})` → keep `status === 'active'` → `SchoolSettings.get()` each → pick from `localStorage.activeWorkspaceId` or first → `localStorage.setItem` → `auth.updateMe({ active_workspace_id })`.

| State               | Stored where                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Active workspace id | `localStorage['activeWorkspaceId']` **and** mirrored to the User record as `active_workspace_id` (`SchoolContext.jsx:56`, `:78`) |
| Theme mode          | `localStorage['tf-mode']` (`ThemeContext.jsx:78`)                                                                                |
| Palette             | `localStorage['tf-palette']` (`ThemeContext.jsx:86`)                                                                             |
| Effective role      | derived at render from the member row — never stored                                                                             |
| Everything else     | Base44 entities                                                                                                                  |

**`active_workspace_id` is not declared on the `User` schema** (`User.jsonc` has no such field) yet four entities' RLS blocks key off `{{user.data.active_workspace_id}}` — `WorkspaceMember` (`:82,88,91`), `SchoolSettings` (`:168,171`), `DiaryEntry` (`:66-75`). Whether this works depends on whether Base44 allows undeclared user data keys; the code itself hedges: _"non-blocking — RLS may return empty until next sync"_ (`SchoolContext.jsx:57`).

The switcher UI is `WorkspaceSwitcher.jsx` in `TopBar` — a dropdown of all active workspaces with role sub-label plus a "Create or Join Workspace" link to `/welcome`. **`switchWorkspace` only sets state + localStorage + `updateMe`; it does not navigate.** Switching from a school to a personal workspace leaves you on the school Dashboard rendering personal-workspace data (which is empty).

### 2.5 The three app shells

| Shell    | Route group                                           | Sidebar                                     | Guard                                                                                   |
| -------- | ----------------------------------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------- |
| School   | `AppLayout` — `/`, `/students`, … (`App.jsx:102-167`) | `Sidebar.jsx` (truncated) + `MobileNav.jsx` | auth only; redirects to `/welcome` if `workspaces.length === 0` (`AppLayout.jsx:19-21`) |
| Personal | `PersonalLayout` — `/personal/*` (`App.jsx:169-178`)  | `PersonalSidebar.jsx`                       | **auth only — no role, no workspace-type check**                                        |
| Seller   | `SellerLayout` — `/seller/*` (`App.jsx:180-189`)      | `SellerSidebar.jsx`                         | **auth only — no role, no verification check**                                          |

Nothing routes a user to the shell matching their active workspace. `AppLayout` renders the full school UI for a user whose only workspace is `personal`.

## 4. Workflows

### 4.1 Register (teacher) → personal workspace — AS BUILT

1. `/register` → "Teacher / School Staff" → `/register?type=teacher`.
2. **Step 0** name, email, password ×2, optional photo (client-validated: image, <5 MB). Photo is held in memory only (`TeacherRegister.jsx:39-47`).
3. **Step 1 "Professional Profile"** — subjects (multi), grade levels (multi), years of experience, current status (radio), curriculum focus (multi). All but curriculum are required (`:36-37`). Clicking **"Create Account"** here is what calls `auth.register({email,password})` (`:55`).
4. **Step 2 OTP** — 6 digits → `verifyOtp` → `setToken`.
5. Then, in three independent swallowed `try/catch` blocks: upload photo → `updateMe({full_name, account_type:'teacher', role:'user', photo_url, subjects, grade_levels, curriculum_focus, years_experience, current_status})` → create `SchoolSettings{workspace_type:'personal'}` + `WorkspaceMember{role:'owner',status:'active'}` → `localStorage.activeWorkspaceId`.
6. `window.location.href = '/'` → school `AppLayout` → school Dashboard, which is empty.

**Clearly intended:** land on `/personal`. Login already does exactly that (`Login.jsx:37`), and `Welcome`'s personal branch also lands on `/` (`Welcome.jsx:196`) — so all three entry points disagree with the shell the user is supposed to see.

### 4.2 Register (seller) — AS BUILT

Same shape; step 1 is Seller Identity (display name, 200-char bio, professional link) and step 0 additionally collects seller type + professional type. After OTP: `updateMe({account_type:'seller', display_name, bio, seller_type, professional_type, professional_link})`, create seller workspace, `→ /seller-portal`.

**Gaps vs. intent:** `has_seller_profile` stays `false`, so the personal sidebar keeps offering "Become a Seller" to a user who registered _as_ a seller. No `IdentityVerification` row is created, so `SellerSidebar` shows "Pending Verification" forever with no submission path in the seller shell (`SellerSidebar.jsx:56-60`) — the only submission UI is `BecomeSellerModal`, reachable **only** from `PersonalLayout`.

### 4.3 Create a school → invite a teacher → teacher joins

**As built (invite-code path — the one that works):**

1. Owner: `/welcome` → Create School Workspace → 3-step wizard → `SchoolSettings{workspace_type:'school', invite_code:'ACD-XXXX-XXXX', owner_id}` + own `WorkspaceMember{owner/active}` → `/`.
2. Owner copies the code from Team & Access (`WorkspaceMembers.jsx:266`) or the sidebar info card (`WorkspaceInfoCard.jsx:39`) and sends it **out of band** (WhatsApp, in person). The app has no sharing mechanism.
3. Teacher: `/welcome` → Join a School → paste code → `SchoolSettings.filter({invite_code})` → "Request Access" → `WorkspaceMember{teacher/pending}` → a "Request Sent" screen whose only button is Sign Out.
4. Owner: `/workspace-members` → Pending tab → optionally change the offered role → **Approve** → `status:'active', joined_at`.
5. Teacher reloads; `SchoolContext` now picks up the workspace.

**No notification reaches the owner in step 3 and none reaches the teacher in step 4.** Approval is discovered by polling manually.

**As built (email-invite path — the broken one):**
Owner: `/settings` → Team & Access → type email + role → **Invite**. A `WorkspaceMember{pending}` row appears with `user_name = email.split('@')[0]`. Toast claims an invitation was sent. Nothing is sent. The invitee will only join if they independently sign up with the same email and the owner then approves them — the pending row already exists, so the flow "works" by coincidence.

**Clearly intended:** the `SchoolWorkspaceInvitation` entity — `teacher_id`, `teacher_email`, `school_id`, `school_name`, `invited_by`, `invited_by_name`, `role_offered ∈ {teacher,staff,principal}`, `status`, `responded_at` — plus the fully built inbox at `/personal/workspaces` (`personal/Workspaces.jsx:120-141`) with Accept (creates the member row as `active` with `role_offered`) and Decline. The **create** half was never written. `grep` confirms zero `SchoolWorkspaceInvitation.create` in the codebase.

### 4.4 Workspace switching — AS BUILT

TopBar dropdown (desktop only; `MobileNav` has no switcher) → `switchWorkspace(id)` → state + `localStorage` + `updateMe({active_workspace_id})`. No navigation, no query invalidation — React Query keys are `[..., activeWorkspaceId]` on Dashboard so those refetch, but `Settings`, `WorkspaceMembers` and `TeamManagement` refetch via their own `useEffect([activeWorkspaceId])`. Pages using bare `.list()` (Printers, AttendanceAlerts, NotificationCenter) do not rescope at all.

### 4.5 Parent linking

**Does not exist.** `parent` is an assignable `WorkspaceMember.role` and `/parent-portal` is `RoleGuard`-ed to `['parent']` (`App.jsx:164`), but there is no flow anywhere in this area to link a parent to a `Student`, no guardian invite, no child-selection. Assigning someone the parent role via the Team dropdown is the entire mechanism.

### 4.6 Leaving / offboarding

- Teacher self-leave: `/personal/workspaces` → Leave School → `WorkspaceMember.delete(member.id)` + `window.location.reload()` (`personal/Workspaces.jsx:81-89`). Only removes the **first** school workspace found.
- Admin removes a member: `WorkspaceMember.delete` — hard delete. The schema has `status: 'removed'` (`WorkspaceMember.jsonc:59`) which is **never written**; soft-remove was clearly intended.
- Owners cannot be removed or role-changed (`member.role !== 'owner'` guards at `WorkspaceMembers.jsx:161,198`). There is **no ownership-transfer flow**, so an owner who leaves the company strands the workspace.
- Account deletion: stub (#50).

## 8. Open questions for the owner

1. **Which shell should a user land in?** Login sends teachers to `/personal`, registration sends them to `/`, and the onboarding "Personal Workspace" button also sends them to `/`. Should the active workspace's `workspace_type` decide the shell (`school`→`/`, `personal`→`/personal`, `seller`→`/seller`)?
2. **Should every teacher get an auto-created personal workspace at registration?** Right now they do (`TeacherRegister.jsx:95`), _and_ the onboarding screen still offers "Personal Workspace" as a choice — so a teacher who picks it gets two.
3. **Is `SchoolWorkspaceInvitation` the intended invite mechanism, or was invite-code + admin approval the final answer?** The inbox UI is fully built and the create side was never written. Should the email-invite path in Team & Access write invitation rows and actually send mail via `Core.SendEmail`?
4. **`principal` as a role** — should it be a first-class permission role, or is it a _label_ (the `CustomLabel` entity with `base_role: 'admin'`) ? `CustomLabel` + `UserLabel` look designed for exactly this, and `UserLabel` is entirely unused.
5. **`superadmin` vs `owner`** — is `owner→superadmin` a permanent mapping, or should `WorkspaceMember.role` gain `superadmin` and drop `owner`? Can there be more than one owner? There is currently no ownership-transfer flow.
6. **Tenant key naming.** Some entities use `workspace_id` (WorkspaceMember, DiaryEntry, Class/Student/Assignment per Dashboard), others `school_id` (Notification, AuditLog, ActivityFeedItem, UserLabel, CustomLabel, DocumentRequest), and the personal entities use `teacher_id`. Should everything standardise on `workspace_id`?
7. **Is `SchoolSettings` meant to stay the workspace table** for all three types, or should `Workspace` be split out from school-specific settings? Personal/seller rows currently carry ~20 irrelevant school columns.
8. **Seller identity: `account_type: 'seller'` vs `has_seller_profile: true`** — are these two different products (a pure publisher account vs a teacher who also sells)? The code treats them inconsistently: `SellerRegister` sets the first and not the second; `BecomeSellerModal` sets the second and not the first.
9. **Where do seller payout details live?** `BecomeSellerModal` collects bank/bKash/Nagad and throws them away. `PaymentMethod` and `SellerEarnings` entities exist — is one of them the destination?
10. **Should the user's theme/palette/notification preferences sync across devices?** `UserPreferences` exists for it and is unused; today everything is `localStorage`.
11. **What is the intended `Notification` taxonomy?** The schema enum is business-category (`marketplace`, `recruitment`, `billing`) while the UI expects event-type (`print_ready`, `exam_reminder`). Which is right, and should `action_url` make notifications clickable?
12. **Module toggles** — should `module_*` actually hide nav items, or are they billing entitlements?
13. **Parent linking** — what is the intended flow? There is no Student↔parent link anywhere. Is the parent invited by the school, or do they self-register with a student code?
14. **Does "Leave School" mean delete the member row (current behaviour) or set `status: 'removed'`?** Same question for admin removal — the enum value exists and is never used.
15. **`DocumentRequest`** — a superadmin asks a candidate for documents, the candidate approves/declines. The candidate-facing response UI does not exist anywhere in this area. Should it live in `/personal/cv-jobs`?
16. **Was the MCP/OAuth consent page (`OAuthConsent.jsx`) meant to ship?** It implies the app exposes an MCP server for AI clients — a significant product surface with no other trace in the export.
17. **`useScopedEntity`** — was this the intended isolation layer that never got adopted, or is server-side RLS the plan? Nothing in the app currently injects `workspace_id` automatically.
18. **Does "Personal Workspace" need a `SchoolSettings` row at all?** Personal data is keyed on `teacher_id`, not `workspace_id`, so the personal workspace row exists only to make the switcher and `AppLayout`'s `workspaces.length` check work.
19. **Brand:** confirm **Acadigma Campus** is final, so the School Troop / TeachFlow strings in PDFs, watermarks and the Integrations page can be purged.
20. **Is the Print Box a real hardware product?** `Integrations.jsx:176` markets "TeachFlow Print Box" — relevant to naming and to the print area.
21. **Sidebar.jsx is truncated in the export** — can you re-export or supply the original so the desktop school nav (groups, order, collapse behaviour, whether `WorkspaceInfoCard` is rendered) can be captured exactly? The MobileNav reconstruction is an inference.
22. **Subscription/plan source of truth** — `SchoolSettings.subscription_plan` (free/starter/pro/enterprise) vs the profile page's hardcoded Free/Pro/School/Enterprise vs the `SchoolSubscription` entity. Which wins?
