# Migrating from the Base44 prototype

What happens to each of the 64 prototype entities, and how untrusted rows are reconciled before anything is imported.

Sources: `docs/reference/base44-inventory/` (§2 of each file, "Data model as implemented") · `base44/entities/*.jsonc` in `F:\Acadigma Campus\Acadigma Campus Base44 Source Code` · `docs/reference/base44-security-review.md` · `docs/product/PRODUCT-DECISIONS.md` (binding).
Target: `docs/architecture/DATA-MODEL.md`.

---

## 1. The headline

| Outcome                                              | Entities |
| ---------------------------------------------------- | -------: |
| **Kept** — becomes one table, largely 1:1            |       21 |
| **Split** — becomes two or more tables               |        6 |
| **Merged** — folded into a table that already exists |       20 |
| **Dropped** — not migrated                           |       17 |
| **Total**                                            |   **64** |

Nothing in the prototype is lost unless PRODUCT-DECISIONS drops it. Where an entity is dropped, the row below says which decision dropped it and where its behaviour went.

## 2. The one rule that governs the whole migration

> Migration needs a reconciliation step that treats existing `WorkspaceMember`, `MarketplaceTransaction` and `SellerEarnings` rows as **untrusted**, not as ground truth to be copied forward.
> — `base44-security-review.md`

Two prototype defects make ownership itself unreliable:

- **`WorkspaceMember.create` was `{}`** — any authenticated user could mint a membership in any workspace, with any role, at `status: 'active'` (finding 2). Every membership row is therefore a _claim_, not a fact.
- **`MarketplaceTransaction.create` and `SellerEarnings.create` were `{}`, and no payment processor was ever called** (finding 4). Every paid listing was free through the normal UI, and anyone could mint an earning payable to themselves at an amount of their choosing.

A third defect means we cannot use the audit trail to sort it out: `AuditLog` had no RLS, was written from the browser on a best-effort basis, was updated in place by `DossierScorecard.jsx:66`, and both real call sites passed arguments in the wrong order. There is no reliable record of who did what.

§7 sets out the reconciliation rules that follow from this. Read it before running any import.

| `User.role`                                     | Never the role source; `workspace_members.role` is                   |
| `User.active_workspace_id`                      | The security root cause; context is server-derived now               |

Also dropped as _fields_, not entities: `Student.average_score`, `Class.level_group`, `Class.total_students`, `JobPosting.applicant_count`, `LessonPlan.{content, materials_needed, homework_legacy}`, `ResourceFolder.shared_with`, `TeacherAttendance.department`, the 10 parent social-media columns on `Student`, and `Exam.google_doc_link` — every one of them declared and never written, or written and never read.

## 7. Reconciliation: what must not be trusted

Run all of §7 **before** any import, on a staging copy. The output of each step is a CSV the owner signs off on.

### 7.1 Memberships

Every `WorkspaceMember` row is a claim. `create` was unconstrained, `update` never checked the caller's role, and removal deleted rows rather than setting `status` — so the table cannot even tell you who _used_ to be a member.

1. **Trust exactly one row per workspace without review:** the `owner` whose `user_id` matches `SchoolSettings.owner_id`. That value was set once, by the creation wizard, before anyone else could reach the workspace.
2. Import every other membership as **`status = 'pending'`, role floored at `teacher`**, regardless of what the row claims. `admin` and `owner` claims are recorded in a `migration_notes` column and granted only by explicit owner action after import.
3. Produce a per-school CSV — name, email, claimed role, claimed status, first-seen date — and require the owner to approve each line in the new Team & Access screen. A membership that nobody approves stays `pending` and grants nothing.
4. **Do not import** membership rows whose `user_email` matches no `auth.users` row. They were unredeemed invitations at best.
5. Rows in workspaces where the claimed member has no other trace — no `Mark`, no `LessonPlan`, no `Message`, no `PrintQueue` row — are flagged in the CSV as _no activity_, because a self-appointed membership is what that looks like.

### 7.2 Transactions

No payment processor was ever called. There is no external record to reconcile against, which means **no `MarketplaceTransaction` row can be proven to represent money that moved.**

1. Import every transaction into `orders` with `status = 'unverified_legacy'`, `payments` empty, and `total_paisa` recomputed from the listing's price at the time — never from the row's own `amount`.
2. **Grant entitlements anyway**, once, for every imported order. The buyer downloaded the file already: the prototype made every paid listing free through the normal UI, so revoking access now punishes users for our defect. `entitlements.granted_at` carries `source = 'legacy_grant'`.
3. **Do not** count legacy orders in revenue, MRR, seller sales counts or listing `sales_count`. They are access grants, not sales. Analytics filter on `status <> 'unverified_legacy'`.
4. Flag for the owner any transaction whose `amount` differs from the listing price at purchase time — that is the signature of a minted row.

### 7.3 Earnings and payouts

`SellerEarnings.create` was open, `commission_rate` had no unit and disagreed with itself across code paths, and `CommissionEngine.jsx` held the rate in React state behind an editable input.

1. **Import no `SellerEarnings` rows at all.** Recompute from scratch: for each imported order line, `commission_bp = 3000` (PRODUCT-DECISIONS 4.3), `net_paisa = gross − platform_fee`.
2. Every recomputed earning lands as `status = 'reversed'` with reason `legacy_unverified`, so nothing legacy is payable. Balance for payout starts at zero on migration day.
3. Produce a per-seller statement of what the prototype _claimed_ they were owed, as a support artefact. Any goodwill payment is an owner decision made outside the system, recorded as a manual adjustment with a reason.
4. Any earning whose `seller_amount` exceeds the listing price, or whose `seller_id` differs from the listing's seller, goes on a separate abuse list.

### 7.4 The audit trail

Do not import `AuditLog`. Rows carry `user_id: 'system'` and `school_id: 'unknown'` from the two call sites that passed arguments in the wrong order; the table had no RLS, so any row could have been written or edited by anyone; and it was updated in place as a scorecard store. Preserve the raw export as a cold file for forensics if it is ever needed, and start `audit_events` empty. Write one `migration.completed` event per workspace via `app.log_audit_event()` recording the counts imported.

### 7.5 Things a machine cannot resolve

These need a human and are collected into one post-import checklist per school:

| Problem                                                                                                   | Why                                        | Resolution                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Class.teacher_name` is free text                                                                         | There was never a teacher FK               | Owner maps each name to a member; unmapped sections get no subject teacher                                                                                            |
| `CoverTeacherConfig.primary_teacher_id` holds a display name                                              | Same root cause                            | Recomputed from `section_subjects` after the mapping above                                                                                                            |
| Four entities have no tenant field at all (`AttendanceLog`, `TeacherAttendance`, `Handout`, `SchoolBook`) | Global across every school on the platform | Assign by the creating user's single active membership. Where a user had several, the rows go to a quarantine table for owner review — they cannot be assigned safely |
| `user.school_id` wrote the literal string `'default'`                                                     | The field never existed on `User`          | Every `'default'` row is quarantined, not guessed                                                                                                                     |
| Personal vs. seller workspace                                                                             | `workspace_type: 'seller'` is gone         | Fold into the user's single personal workspace; create `seller_profiles` from `has_seller_profile`                                                                    |
| `Student` duplicates                                                                                      | No uniqueness anywhere                     | Match on (name, DOB, guardian phone); near-matches go to a review list                                                                                                |

## 8. Import order

Foreign keys and the bootstrap triggers dictate the sequence. Every step is idempotent on a natural key and records its source id in `migration_source_id`.

1. `auth.users` → `profiles`, `user_preferences` (the auth trigger creates the personal workspace)
2. `workspaces` (school) → `school_profiles` — the triggers create the owner membership, invite code and trial
3. `custom_labels`, then `workspace_members` **as `pending`** (§7.1)
4. `files` (from every `*_url` column), then everything that references a file
5. `grade_levels` → `subjects` → `sections` → `section_subjects`
6. `students` → `guardians` → `enrollments`
7. `periods` → `timetable_slots`
8. `exams` → `exam_subjects` → `marks`; `assignments` → `assignment_submissions`
9. `attendance_sessions` → `attendance_records`; `staff_attendance`
10. `resource_folders` → `resources` → `resource_shares`; `lesson_plans`, `lesson_logs`
11. `job_postings` → `applications` → `interviews`; `staff_records`
12. `channels` → `channel_members` → `messages`
13. `listings` → `listing_files`; `orders` → `order_lines` → `entitlements` (§7.2); earnings recomputed (§7.3)
14. `print_jobs`, `manual_expenses`, `diary_entries`, `personal_students`, `personal_attendance`
15. Reconciliation CSVs generated; quarantine tables reviewed; `migration.completed` audit event written

Steps 1–14 run with the service role, which bypasses RLS — deliberately, because the importer is the one caller that legitimately writes across every tenant. The guard triggers still fire (they detect the privileged context and skip only the _authorization_ checks, never the invariants), so the last-owner rule and the tenant-freeze rule hold throughout the import.

## 9. What "done" looks like

- Every import script is idempotent and re-runnable.
- Row counts per entity, before and after, in a single report.
- Zero rows carrying `school_id = 'default'` or any other sentinel.
- Zero memberships at `active` that an owner did not approve.
- Zero payable legacy earnings.
- `supabase test db` passes against the migrated staging database — the same tenant-isolation and escalation suite that runs in CI.
