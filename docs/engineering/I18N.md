# Acadigma Campus — Internationalisation (i18n)

How the app ships English and Bengali UI. Binding on `apps/web`; implements `ARCHITECTURE.md` §6 (client architecture) and the localisation row of PRD §6 (Non-functional requirements: "English and Bengali UI strings; Bengali-capable fonts in UI and PDFs; Asia/Dhaka timezone; BDT formatting"). Vocabulary source of truth: `docs/product/GLOSSARY-EN-BN.md`.

Library: **[`next-intl`](https://next-intl.dev) `4.14.5`** (verified via `npm view next-intl version` on 2026-09-17 — pin `^4.14.5` in `apps/web/package.json` when the scaffold agent adds dependencies). Next.js 15 App Router, per `ARCHITECTURE.md` §1/§5.

---

## 1. Routing strategy — cookie-based, no URL prefix

Campus does **not** use next-intl's path-prefix i18n routing (`/en/...`, `/bn/...`). Reasons:

- Route groups are already meaningful (`(school)/app`, `(personal)/personal`, `(parent)/family`, …) — adding a locale segment in front of every one doubles the routing surface for no product benefit.
- Language is a **per-user preference** (`user_preferences.language`, PRODUCT-DECISIONS 1.10), synced across a teacher's phone and the office PC — it is not tied to a URL a user navigates to, and a school with English- and Bengali-preferring staff shares the same links (invite links, print-job links, deep links) regardless of viewer language.
- SEO-indexed locale variants are not a requirement — only `(marketing)` is public, and it targets Bengali-speaking BD schools primarily; a URL-locale split isn't needed there either.

Implementation (next-intl's ["without i18n routing"](https://next-intl.dev/docs/getting-started/app-router/without-i18n-routing) pattern):

```
apps/web/
  i18n/
    request.ts        # getRequestConfig — resolves the active locale server-side
    routing.ts         # locales list + defaultLocale (no `localePrefix`/`pathnames`)
  messages/
    en.json
    bn.json
  middleware.ts         # NOT next-intl's middleware; existing auth/workspace middleware only
```

`i18n/request.ts` resolves locale in this priority order, entirely server-side, on every request:

1. **Signed-in user's `user_preferences.language`** (read via the existing `WorkspaceContext`/session lookup — this is the source of truth once a user has an account and is why sync-across-devices works).
2. **`NEXT_LOCALE` cookie** — set immediately on first language toggle (before any account exists, e.g. on the public marketing/login pages) and kept in sync whenever the DB preference changes, so a logged-out visitor and the first render before the DB round-trip both get the right language without flicker.
3. **`Accept-Language` header** — best-effort default for a brand-new visitor (maps `bn*` → `bn`, everything else → `en`).
4. **`en`** — final fallback.

```ts
// apps/web/i18n/request.ts
import { getRequestConfig } from "next-intl/server"
import { cookies, headers } from "next/headers"
import { getCurrentUserLanguage } from "@/lib/i18n/resolve-locale"
import { routing } from "./routing"

export default getRequestConfig(async () => {
  const locale =
    (await getCurrentUserLanguage({
      cookies: await cookies(),
      headers: await headers(),
    })) ?? routing.defaultLocale

  return {
    locale,
    messages: (await import(`../messages/${locale}.json`)).default,
    timeZone: "Asia/Dhaka",
    now: new Date(),
  }
})
```

```ts
// apps/web/i18n/routing.ts
export const routing = {
  locales: ["en", "bn"] as const,
  defaultLocale: "en" as const,
}
export type Locale = (typeof routing.locales)[number]
```

The language toggle (in `TopBar` / settings) is a **Server Action** that writes `user_preferences.language`, sets the `NEXT_LOCALE` cookie, and calls `router.refresh()` — no client-side locale switching library, no route change.

## 2. Message file layout

```
apps/web/messages/
  en.json
  bn.json
```

Single file per locale (not split per namespace on disk) — next-intl loads one JSON per request either way, and one file per locale keeps translation handoff (e.g. to a professional Bengali reviewer) a single diffable artifact. **Namespacing happens inside the JSON**, one top-level key per feature area, matching the route groups in `ARCHITECTURE.md` §2:

```jsonc
{
  "common": { /* shared actions/labels — see §5 rule on flat vs nested */ },
  "auth": { "login": {...}, "register": {...}, "verify": {...}, "reset": {...}, "logout": {...}, "session": {...} },
  "nav": { /* one key per nav item */ },
  "attendance": { "status": {...}, "summary": {...}, ... },
  "errors": { /* generic + field-level error copy */ },
  "academics": { "sections": {...}, "students": {...}, "admission": {...} },
  "timetable": {...},
  "exams": { "grades": {...}, "reportCard": {...} },
  "billing": { "invoice": {...}, "plans": {...} },
  "market": { "listing": {...}, "seller": {...} },
  "hiring": {...},
  "cover": {...},
  "messaging": {...},
  "reports": {...},
  "settings": {...},
  "ai": {...},
  "platform": {...}
}
```

Once a feature area grows past ~150 keys, split it out at build time only if bundle profiling shows a problem — next-intl already tree-shakes per-`useTranslations(namespace)` call at the RSC boundary, so a single large file is not a runtime cost; keep it as one file per locale until that changes.

## 3. Typed keys

Enable next-intl's built-in TypeScript augmentation so `useTranslations('attendance')` autocompletes keys and a typo fails `tsc`, not runtime:

```ts
// apps/web/global.d.ts
import en from "./messages/en.json"

type Messages = typeof en

declare global {
  // next-intl's official augmentation point
  interface IntlMessages extends Messages {}
}
```

CI enforcement (`packages/config` eslint + a small script run in the `typecheck` turbo task):

- **Key-set parity test** (`apps/web/scripts/check-i18n-keys.ts`, run in CI and as a pre-commit-adjacent `pnpm` script): flattens `en.json` and `bn.json` to dotted paths and fails the build if the sets differ in either direction (missing key in `bn` = untranslated string will ship; extra key in `bn` = dead translation, usually a rename that wasn't mirrored). This is the "missing-key lint" required by PRD Quality gates ("no mock data / no shortcuts ship").
- Because `en.json` is the type source, adding a key to `bn.json` only is a type error at the call site until it also exists in `en.json` — keeping `en.json` the canonical schema.

## 4. Pluralisation and ICU examples

Message values use ICU MessageFormat (next-intl's default, powered by `intl-messageformat`). **Bengali's CLDR plural rule set only has `one` and `other`**, and unlike English, `one` in Bengali covers _both_ `0` and `1` (`i = 0,1`), while `other` covers everything else. Do not assume English plural boundaries translate directly — always translate both categories even when the Bengali wording is identical for `one`/`other` (Bengali nouns don't inflect for number the way English does).

```jsonc
// en.json
"attendance": {
  "summary": {
    "presentCount": "{count, plural, one {# student present} other {# students present}}",
    "absentCount": "{count, plural, one {# student absent} other {# students absent}}"
  }
}
```

```jsonc
// bn.json
"attendance": {
  "summary": {
    // bn plural categories: one (i=0,1), other (everything else) — text is identical across
    // categories here because Bengali nouns don't inflect, but both keys are still required.
    "presentCount": "{count, plural, one {#জন শিক্ষার্থী উপস্থিত} other {#জন শিক্ষার্থী উপস্থিত}}",
    "absentCount": "{count, plural, one {#জন শিক্ষার্থী অনুপস্থিত} other {#জন শিক্ষার্থী অনুপস্থিত}}"
  }
}
```

Rich text / interpolation (e.g. a name inside a sentence) uses next-intl's `t.rich` with tags rather than string concatenation, so word order can differ between English and Bengali without breaking the translation:

```jsonc
"messaging": {
  "newMessageToast": "<b>{senderName}</b> sent a message in {channelName}"
}
```

```tsx
t.rich("messaging.newMessageToast", {
  senderName: student.name,
  channelName: channel.name,
  b: (chunks) => <strong>{chunks}</strong>,
})
```

Select format for role-dependent copy:

```jsonc
"nav.roleGreeting": "{role, select, owner {Welcome, Owner} admin {Welcome, Admin} teacher {Welcome, Teacher} other {Welcome}}"
```

## 5. Rules for developers

1. **No hardcoded UI strings.** Every user-facing string — including toast messages, empty states, `aria-label`s, and PDF templates — goes through `useTranslations` (client/server components) or `getTranslations` (Server Actions, route handlers, PDF renderers), never a literal string in JSX or template. Enforced by the key-parity script plus PR review (a follow-up `eslint-plugin-formatjs` rule can be added once the message volume justifies it — not required for the R0 starter set).
2. **Key naming: `feature.screen.element`.** Three segments, camelCase leaves: `attendance.rollCall.saveButton`, `exams.reportCard.gpaLabel`, `billing.invoice.downloadButton`. `common.*` and `errors.*` are the only two-segment exceptions (they're cross-cutting, not screen-scoped). Never key by the English text itself (`"Save changes"` as a key) — that breaks the moment the English copy is edited.
3. **`common` and `errors` are shared; everything else is feature-owned.** A feature namespace must not reach into another feature's namespace for a string — duplicate a short label rather than create a cross-feature dependency; `common` is the only place for genuinely reused atoms (Save/Cancel/Edit/Delete, statuses, pagination).
4. **Numbers, dates, and currency never go through message strings as pre-formatted text.** Pass raw values and format with `useFormatter` (see §6) inside the component, so the Bengali-digit user preference and Asia/Dhaka timezone are applied consistently everywhere instead of being baked into copy-pasted formatted strings.
5. **New terms go in the glossary first.** Before adding a Bengali string that isn't already in `docs/product/GLOSSARY-EN-BN.md`, add the term there with its BD-school usage note, then use that exact wording in the message file. This keeps report cards, notices, and in-app copy consistent — the glossary is reviewed by the owner; message files are not.

## 6. Date, number, and currency formatting (`Intl`, `Asia/Dhaka`)

Formatting goes through next-intl's `useFormatter` (client/server components) or `getFormatter` (Server Actions), backed by the Node `Intl` implementation — Node 24 (per `package.json` `engines.node >=24`) ships full ICU data by default, so `bn-BD` locale data (digit sets, date fields) is available without a `full-icu` polyfill.

Global formats are centralised in `i18n/request.ts`'s returned `formats`, not re-specified per call site:

```ts
formats: {
  dateTime: {
    short: { day: '2-digit', month: '2-digit', year: 'numeric' },       // 17/09/2026
    long: { day: 'numeric', month: 'long', year: 'numeric' },           // 17 September 2026 / ১৭ সেপ্টেম্বর ২০২৬
  },
  number: {
    currency: { style: 'currency', currency: 'BDT', currencyDisplay: 'narrowSymbol' },
  },
}
```

Two BD-specific realities the plain `Intl` config above does **not** fully solve on its own, per `GLOSSARY-EN-BN.md` §8:

- **Digit set is a user preference, not tied to the `bn` locale.** Do not rely on `Intl.NumberFormat('bn-BD')` to decide digit rendering, because the default for Bengali-language users is still **Latin digits** (only an opt-in preference switches to `০১২...`). Formatting calls always pass an explicit `numberingSystem` derived from `user_preferences.numbering_system` (`'latn'` default, `'beng'` opt-in), not from the active locale:
  ```ts
  format.number(amount, {
    style: "currency",
    currency: "BDT",
    numberingSystem: prefs.numberingSystem,
  })
  ```
- **Indian/Bangladeshi digit grouping (`1,23,456.00`) is what `Intl.NumberFormat('en-IN', …)` and `Intl.NumberFormat('bn-BD', …)` both already produce** (both locales share this grouping in CLDR) — use whichever active-locale string is passed to the formatter for grouping, but always override `currency: 'BDT'` and `currencyDisplay: 'narrowSymbol'` explicitly so the ৳ glyph renders instead of the ISO code "BDT" text.
- All calls set `timeZone: 'Asia/Dhaka'` (already the `request.ts` default above) so "today," attendance dates, and exam dates never shift across a UTC day boundary, matching `ARCHITECTURE.md` §4 ("today" computed in `school_profiles.timezone`).

```tsx
const format = useFormatter()
format.dateTime(exam.date, "short") // 17/09/2026
format.number(invoiceTotalPaisa / 100, "currency") // ৳1,23,456.00
```

## 7. Bengali font loading

- **UI:** `next/font/google` with `Noto Sans Bengali` as the primary Bengali-capable face, paired with the existing Latin UI face from `packages/ui` tokens for English strings in the same document (both loaded, CSS `font-family` fallback chain does the per-character selection — no manual script detection needed). `Hind Siliguri` is the fallback choice if Noto Sans Bengali's weight range or hinting doesn't match the design system's density on low-end Android (verify during `packages/ui` typography token setup).
  ```ts
  import { Noto_Sans_Bengali } from "next/font/google"

  const notoBengali = Noto_Sans_Bengali({
    subsets: ["bengali", "latin"],
    weight: ["400", "500", "600", "700"],
    display: "swap",
    variable: "--font-bengali",
  })
  ```
- `subsets: ['bengali', 'latin']` — both, because the same page mixes languages (brand name, numerals, loanwords in nav like "সেটিংস"). `display: 'swap'` — required for the PRD's LCP < 2.5s budget on low-end Android; a blocking Bengali webfont on first paint would blow the budget for every Bengali-preferring user, which is the majority target audience.
- Self-hosted via `next/font` (no runtime Google Fonts request) — consistent with `ARCHITECTURE.md`'s "no ad-hoc" performance stance and avoids a third-party network dependency for text rendering, which matters on 3G-fast conditions.

## 8. PDF font embedding

Server-rendered PDFs (`@react-pdf/renderer`, `ARCHITECTURE.md` §5, route `/api/pdf/[kind]`) run in a Node route with **no access to `next/font`** — fonts must be registered manually with `Font.register` from a static TTF/OTF file bundled in the repo, not fetched:

```ts
import { Font } from "@react-pdf/renderer"

Font.register({
  family: "NotoSansBengali",
  fonts: [
    {
      src: "apps/web/assets/fonts/NotoSansBengali-Regular.ttf",
      fontWeight: 400,
    },
    { src: "apps/web/assets/fonts/NotoSansBengali-Bold.ttf", fontWeight: 700 },
  ],
})
```

- Every PDF template (report card, mark sheet, attendance register, ID card, invoice, seller statement) sets this as its base font family — **do not** default to a Latin-only PDF font and special-case Bengali; a report card mixes a school's English brand header with a Bengali student name and grade letters in the same line, so the font must cover both scripts throughout.
- `PRD.md` §8 risk register flags this explicitly ("Bengali rendering in PDFs — mitigation: font embedding verified in R1 report-card part 1"). The report-card feature's Definition of Done must include a rendered-PDF visual check with a Bengali student/guardian name, not just an English fixture — glyph substitution failures (tofu boxes) only show up with real Bengali text.
- Keep the same two font files as the single source for both `next/font` UI use and `@react-pdf/renderer` PDF use (one `assets/fonts/` directory, referenced by both) so on-screen and printed Bengali render identically.

## 9. RTL

Not needed. Bengali is written left-to-right; no `dir="rtl"` handling, no logical-property CSS migration required for this language pair. Revisit only if a future language (e.g. Urdu, Arabic) is added — see §11.

## 10. Testing strategy

- **Missing-key lint (CI, blocking):** `apps/web/scripts/check-i18n-keys.ts` (see §3) runs in the `typecheck` or a dedicated `i18n` turbo task on every PR; fails on any key present in one locale file and not the other, and on any ICU syntax error (parsed with `intl-messageformat` at build time — a malformed `{count, plural, ...}` block fails fast instead of throwing at runtime for a Bengali-preferring user only).
- **Dual-locale Playwright snapshot:** the existing e2e suite (`apps/web/e2e`, `ARCHITECTURE.md` §9: Playwright at 360×800 and 1280×800 with axe) runs its **critical-path specs twice** — once with the `NEXT_LOCALE=en` cookie, once with `NEXT_LOCALE=bn` — for: login, take attendance, enter marks, generate report card, view timetable. This catches (a) Bengali text overflow/truncation on 360px cards, since Bengali strings commonly run 20–40% longer than English, (b) missing `t()` calls (English string leaking into the Bengali run), and (c) font tofu-boxing (visual snapshot diff catches missing glyphs that a text-content assertion would miss).
- **Unit tests for formatters:** `packages/domain` (or a small `packages/i18n` if formatting helpers grow beyond what belongs in `apps/web`) gets Vitest cases for the currency/date helpers in §6 — paisa-to-`৳1,23,456.00` grouping, Latin-vs-Bengali digit switching, and `Asia/Dhaka` day-boundary correctness are exactly the kind of off-by-one bugs that don't show up in manual testing but break a real report card.
- **Glossary-consistency spot check:** not automated in v1 — a PR review checklist item ("new Bengali strings match `GLOSSARY-EN-BN.md`?") per §5 rule 5, revisit automation if drift becomes a recurring review comment.

## 11. Migration plan for a third language

The cookie/preference-based, no-URL-prefix design means adding a third language (e.g. Hindi for a future market, or Arabic/Urdu for a madrasah-focused variant) is additive, not a routing migration:

1. Add the locale code to `routing.locales` in `i18n/routing.ts` and to the `user_preferences.language` check constraint / enum in a new migration (`ARCHITECTURE.md` §4: forward-only SQL).
2. Add `messages/<locale>.json` with the same key set as `en.json` — the key-parity script (§3) is extended to check **all** locale files against `en.json`, not just `bn.json`, so the CI gate scales automatically to N languages.
3. Add the font to §7/§8's font map if the new script isn't Latin/Bengali-coverable by the existing Noto Sans Bengali + design-system Latin pairing (e.g. Arabic needs a distinct `next/font` entry and a distinct `Font.register` PDF entry, plus `dir="rtl"` handling reintroduced at that point — §9's "not needed" assumption is revisited here, not before).
4. Extend the CLDR plural-category review in §4 for the new locale (Arabic has six plural categories, not two — every `{count, plural, ...}` message needs the additional `zero/two/few/many` branches, not just a translation pass).
5. No change to route structure, middleware, or the language-toggle Server Action — the third language is just a third option in the same preference field and the same `messages/*.json` loading mechanism.
